# ADR-043：视口手势标记不得进入元素渲染依赖（回退 ADR-042 的冻结与滞回）

- 状态：已实施
- 日期：2026-09-23
- 关联：ADR-042（图片档位切换时机与冻结边界，本批**部分回退**）、ADR-041（原图准入预算）、ADR-040（滚轮手感）、`docs/画布交互性能优化实施计划.md` P2

## 背景

主人反馈：**"为啥改完这一次滚动缩放反而更卡了？上一次还能流畅滚动缩放，只是图片一多才卡顿。"**

ADR-042 的收益是真的（换档从"整屏同步"变"逐图分散"），但它同时引入了**回归**：
把"视口手势中"这个**每滚一次就翻转的布尔标记**接到了每个画布元素上。

## 诊断

### 1. 主因：手势标记进入元素渲染依赖 → 每次手势让整屏元素重绘

ADR-042 给 `CanvasElement` 加了 `lodFrozen={viewport.transient}`，并在 memo 里写：

```ts
if (prev.lodFrozen !== next.lodFrozen) return false;   // 无条件重绘
```

`transient` 每次手势要翻转两次（手势开始 → true，收尾 → false）。于是**每滚一次滚动**，
当时可见的**每一个**元素都会被强制重绘一次 —— 与"这张图的档位是否真的变了"无关。

量化（`npm run benchmark:churn`，一次"从 0.25 放大到 1.6"的手势，10 格）：

| | 被迫/实际重绘次数 |
|---|---|
| 旧设计（手势标记进元素） | **440** |
| 本批（标记不进元素） | **15** |
| 比值 | **29.3×** |

图片越多、视野内元素越多，这个差就越大 —— 且它发生在**滚动开始时**（用户感知最明显的位置），
这也解释了"为什么图片少时也变卡了"（改动前图片少时是流畅的）。

### 2. 档位冻结让位图停在低档

手势开始时若 zoom 较小，档位就被冻结成"小代理/缩略图"，之后放大到 3×、5× 仍沿用同一张位图：
屏幕上要画 3000px，源位图可能只有 256~1024px —— 既更糊，也让每帧的大倍数重采样更贵。
ADR-040 当初特意让滚轮**不置** `isInteracting`，就是为了避免"越放大越糊"；冻结把这个问题以另一种形式带了回来。

### 3. `imageRendering` 被顺手改错了判据

ADR-042 把 `imageRendering` 从 `zoom > 1.0 ? 'auto' : 'optimizeQuality'` 改成按 `tier` 判定。
放大时（zoom 很大）只要档位不是 `original`（按像素口径这很常见）就用 `optimizeQuality`，
而改动前放大一律用 `auto`。本批恢复原判据（少一个变更变量）。

### 4. overscan 依赖手势标记 → 每滚一次重挂一圈元素

`viewportQueryPadding` 原本写成 `if (!viewport.transient) return undefined;`，
于是"手势开始 → 多挂一圈、收尾 → 卸掉一圈、下次滚动 → 再挂回来"。挂载一个 SVG `<image>` 是要解码的。
量化（1440×900，300 张，`npm run benchmark:churn`）：

| zoom | 无 overscan | 改动前 30% 短边 | 本批 150px | 改动前多挂 | 本批多挂 |
|---|---|---|---|---|---|
| 0.20 | 70 | 154 | 108 | **84** | 38 |
| 0.35 | 30 | 56 | 40 | 26 | 10 |
| 0.60 | 12 | 30 | 12 | 18 | 0 |
| 平均 | | | | **23 张/次** | **9 张** |

### 5. 滞回与 memo 不同源：升档被永久卡死（真 bug）

ADR-042 的滞回要求"记住上一次的档位"，而这份记忆只存在于 `useImageLOD` 内部的 `useRef` ——
`CanvasElement` 的 memo 比较函数**看不到它**。于是两边口径不同源：

- hook 口径（带滞回）：`1100px` 时因为没超过 `1024 × 1.15 = 1177.6` → 仍用代理；
- memo 口径（纯门槛）：`1100px` 已超过 `1024` → 认为"档位已变，需要重绘"。

两边不一致的直接后果是：**memo 会在滞回窗口内把"档位真的该升"的那次重绘拦掉**，
href 永远停在滞回前的值（画面一直糊着不换）。
自检实测：让两边口径不同源，60 张图 × 12 个缩放级别里有 **124 处判定不一致**。

### 6. 被证伪的假设："滚轮没有 mouseup，所以 transient 永不复位"

ADR-042 据此在 `stepSmooth` 收敛时复位 `transient`。但事实上 `useCanvasInteractions` **本来就有**收尾机制：

```ts
const WHEEL_GESTURE_IDLE_MS = 200;
wheelTimeoutRef.current = setTimeout(() => { wheelTimeoutRef.current = null; endWheelGesture(); }, WHEEL_GESTURE_IDLE_MS);
// endWheelGesture → viewportStore?.endInteraction()
```

滚轮空闲 200ms 就会正常提交并复位标记。ADR-042 的"修复"是多余的，而且因为收敛（约 167ms）
比空闲收尾（200ms）**更早**，它把收尾提前了，等于让手势标记多翻转一次 —— 又一份抖动。

## 决策

### 1. 手势标记不得进入任何元素的渲染依赖

删除 `lodFrozen` / `frozen` 整条链路（MainCanvas 传参、CanvasElement props 与 memo、LOD hook 参数）。
**规则**：任何"每次手势都会翻转的标记"都不能出现在 `CanvasElement` 的 props 比较里。

### 2. 选档函数保持无历史状态（删除滞回）

`resolveImageLODTier` 只接受"屏幕最长边 + 有哪些图源"，**不接受上一次的档位**。
这样 memo 与 hook 各自独立计算必然得到相同结果。
抖动缓解交给"按屏幕像素选档"本身：旧口径的门槛是**全局缩放级别**（抖一次整屏换），
按像素选档后每张图有自己的门槛（抖一次只波及正停在门槛上的那张）。
自检实测：zoom 0.245 → 0.255 这段抖动，旧口径换档 **300 张** → 按像素口径 **20 张**。

### 3. 裁剪 overscan 恒定，不依赖手势标记

`viewportQueryPadding = RENDER_PUBLISH_MOVE_PX × 1.25 / zoom`（≈150 CSS 像素）。
它由"渲染态发布最多滞后多少像素"推导而来，不再随手势开关伸缩。
副作用是"稳态挂载量"变大，但取值比改动前的"屏幕短边 30%"更小 —— 稳态挂载量**反而下降**，且抖动归零。

### 4. 恢复 `imageRendering` 的原有判据

`zoom > 1.0 ? 'auto' : 'optimizeQuality'`。

### 5. 状态收尾只在一处：交互层的空闲定时器

回退 `stepSmooth` 收敛时的 `transient = false` / `publishRender()`。
手势结束＝`endWheelGesture`（`WHEEL_GESTURE_IDLE_MS`）或 `endInteraction`，`viewport-store` 不抢。

### 保留（ADR-042 里真正有效的部分）

- **按屏幕像素选档**（`屏幕最长边 = 世界最长边 × zoom`，门槛 256 / 1024）；
- 尺寸未知时回退到旧的缩放级别口径（既有契约不回归）。
- ADR-041 的全部成果（准入预算、定向订阅、批量提交、优先队列）。

## 边界与未验证

- **滚动中仍会换档**（按像素口径：300 张里单格平均约 28 张、最坏 65 张）。
  但旧口径的换档是**整屏同步**的两次大停顿（单格 240 张 ≈ 130ms），按像素口径是**逐图分散**的小批量，
  体感上更接近"零星闪一下"而不是"卡一下"。再往下要平滑，正确方向是**预解码/摊帧**（下一批候选），
  而不是把手势标记塞给每个元素。
- **未在真实 Electron 窗口验证**：本批的量化全部来自纯函数与几何计算（可复现、不依赖浏览器），
  证明的是"每次滚动的工作量"，不是"帧率"。真机手感仍需主人确认。
- 若某个元素尺寸为 0（尚未测量），按像素口径会退回缩略图档；这与旧行为一致。

## 验证

- `npm run check` 9 项全绿。
- **四处反证**（确认守卫不是假绿）：
  1. 把 `lodFrozen` 加回元素 → `CanvasElement 不得接收手势标记` 失败；
  2. 让 overscan 依赖 `viewport.transient` → `不得依赖手势标记` 失败；
  3. 给 hook 口径加历史（滞回）而 memo 不加 → `判定必须逐点一致（实测 124 处不一致）` 失败；
  4. 在 `stepSmooth` 收敛处复位 `transient` → `不得抢手势收尾` 失败。
