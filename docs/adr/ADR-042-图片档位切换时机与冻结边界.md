# ADR-042：图片档位（LOD）的切换时机与冻结边界

- 状态：已实施
- 日期：2026-09-23
- 关联：ADR-038（相机瞬时通道）、ADR-039（拖动会话）、ADR-040（滚轮手感）、ADR-041（原图准入预算与定向通知）、`docs/画布交互性能优化实施计划.md` P2

## 背景

主人反馈：**"一个界面里出现几百张图时，滚动缩放还是会出现卡顿、不顺滑的感觉"**。
ADR-041 已经修掉了"准入广播 O(N²)"，但体感没有改善 —— 说明真凶还在别处。

## 诊断过程（含两次被推翻的假设，都值得记下来）

### 假设一：相机变换挂在 SVG `<g>` 上，每帧重新光栅化整层 → 改造挂载方式

ADR-041 的探针结论（"三种挂载方式完全一致"）是在**软件光栅 + 内容过轻**下做的，不足以定论。
本轮重做，在**真实 GPU**（RTX 5080）下测得：

| 场景（300 张位图、固定铺开面积） | 光栅 ms/帧 | 解码/帧 |
|---|---|---|
| `<g>` 上改变换（现状） | **0.16** | 0.3 |
| 静置不动 | 0 | 0 |
| 巨型网格背景底板（40 万 × 40 万 pattern 填充） | 0.34 | 1.6 |

**结论：真实 GPU 下光栅化根本不是瓶颈**（0.16ms/帧，rAF 跑到 166fps）。
假设一被推翻 —— 若照它去把渲染迁到 HTML 层，就是又一次大而无用的架构改造。

> 附带的测量教训（与 ADR-041 同一类陷阱）：
> ① `--disable-gpu`（软件光栅）下同一场景会报 10ms/帧、64 次解码/帧，**是软光栅的产物**；
> ② 同一配置在不同轮次里会飘（0ms ~ 16ms），因为合成层纹理缓存会随内存压力被丢弃 —— **单次结果永远不可信**，必须交替重复 + 每次独立浏览器进程；
> ③ rAF 间隔在无 vsync 的无头环境跑满 166fps，**测不出掉帧**。

### 假设二（成立）：跨 LOD 阈值时的"整屏换 href"

`resolveImageLODSource` 的档位由**全局缩放级别**决定（`zoom < 0.25` 全部缩略图 / `zoom > 1` 全部原图），
滚轮缩放中 `isInteracting` 为假（ADR-040 为了让缩放不降级图片而刻意如此），于是**每次跨阈值都会整屏换 href**。

实测（真实 GPU，300 张）：

| 动作 | 成本 |
|---|---|
| 整屏换档（href 赋值 + 等待解码） | **179.3 ms** |

模拟用户真实场景（连续缩放 1.5s，每 250ms 换一轮档，隔离页面、交替重复）：

| | 均值帧 | 最长帧 | 超 32ms 帧数 |
|---|---|---|---|
| 滚动中换档 | 11.0 ms | **78.3 ms** | **13 / 43** |
| 滚动中不换档 | **4.8 ms** | **16.9 ms** | **0 / 43** |

**结论：卡顿来自"换档的时机与规模"，不是"画得慢"。**

### 顺带发现一个真实 bug

`transient`（未提交手势标记）**只有 `endInteraction()` 会复位**，而**滚轮缩放没有 mouseup**。
于是"滚过一次"之后：裁剪 overscan 永久放大（可见集变大 → 更多解码）、工具条位置永久冻结、LOD 档位永远不会解冻。

## 决策

### 1. 档位按"屏幕像素需求"选，并带滞回（`resolveImageLODTier`）

- 选档依据改为 `屏幕最长边 = 世界最长边 × zoom`（"够用且最小"），不再按全局缩放级别；
- 门槛附近留 ±15% 滞回带：升档要超过门槛 ×1.15，降档要跌破门槛 ×0.85，**没有历史时用纯门槛**（无滞回）；
- 尺寸未知的调用点回退到原有的缩放级别口径，保证既有契约不回归。

效果（自检实测）：0.27 → 0.23 微缩跨过 0.25 阈值时，需要换档的图片数 **300 → 8**；
门槛附近来回滚动 8 次，换档次数 **8 → 0**。

### 2. 视口手势中冻结档位

`useImageLOD` 新增 `frozen`：手势中沿用上一次非冻结时提交的档位，**不换 href**，也不改动准入配额。
手势结束（`transient` 归位）后的第一次渲染按新相机值一次性结算。

把"换档"从"滚动过程中"移到"手势结束后"，是本次体感改善的主因。

### 3. 平滑追随收敛即结束手势

`stepSmooth` 收敛时复位 `transient` 并发布一次最终渲染态。**不引入新的提交点** —— 落盘时机仍是显式 `endInteraction` / `flush`（`check-wheel-zoom` 的"收敛不是提交时机"契约保持不变）。

### 4. memo 与档位判定同源

`CanvasElement` 的 memo 改用同一个 `resolveImageLODTier` 比较"理想档位是否变化"，
并新增"冻结开关切换必须重绘"。偏宽松是安全的：多给一次评估机会不会出错，漏掉一次才会"该换档却没重绘"。

## 边界与未验证

- **手势结束后的那一次结算仍是一次整屏换档**（实测 300 张约 179ms 的解码等待）。它发生在静止时，用户感受是"停下后画面变清晰"，而不是滚动中卡。若要进一步平滑，可把结算切成每帧若干张（本批未做）。
- **`transient` 复位依赖平滑追随收敛**。若某条路径只写 live 而不走 `setSmoothTarget`（例如未来新增的相机动画），需要自己负责结束手势。
- **`isInteracting` 的既有语义保留**（交互中不升原图）；真正的"手势中不换档"由 `frozen` 负责，两者叠加：`frozen` 期间计算结果被忽略。
- **未在真实 Electron 窗口验证**：无头环境测不出成帧率与手感；本批给出的帧数据来自隔离页面（真实 GPU、真实位图、无 React）。真实项目还有 React 重渲染与 DOM 属性更新成本，需要主人真机确认。
- 缩小时**不再整屏降级到缩略图**（按像素判定下，世界坐标很大的图在缩小后仍然需要代理）。纹理量比旧口径更大，但真实 GPU 下光栅化不是瓶颈，"不换档"比"用更小的图"更值。

## 验证

- `npm run check` 9 项全绿（新增 `check:lod-tier-stability`）。
- 反证（确认不是假绿）：去掉滞回 → 门槛断言失败；取消 `frozen` 冻结 → 源码守卫失败；不复位 `transient` → 收敛守卫失败。
