# ADR-002：以可逆 Element Operation Journal 替代全量历史快照

- **状态**：accepted（已实现）
- **日期**：2026-09-22
- **关联**：`FDD-002-Phase1a操作日志迁移.md`

## 背景

当前每个 `Board` 将 `elements` 与 `history: Element[][]` 一并放在 React state 中。拖拽、绘制、调整尺寸和导入会重复保留整块画布数组，导致内存、GC 与保存文件随历史长度线性膨胀。交互中的 `setElements(..., false)` 还会把临时状态写入当前快照槽位。

## 决策

采用通用、可逆的 element delta operation：

```ts
{
  id,
  beforeOrder?, // 仅 order 改变时存在
  afterOrder?,
  changes: [{ id, before?, after? }]
}
```

- `before` / `after` 仅保存新增、删除或变更的 element；未变 element 不复制；
- 新增、删除或重排才由 id order 明确记录；普通属性修改不复制全量 id 顺序；
- drag / draw / resize 的临时状态不进入 journal；在 interaction commit 时，使用该 interaction 的起始 element 集与最终 element 集生成一个 operation；
- undo/redo 只按方向重放 operation；
- 旧 JSON 中的 `history` / `historyIndex` 仅在加载时迁移，不再写回新保存文件。

## 边界

本 ADR 只解决 **Element runtime history**，不提前伪造完整持久化层：

- 不实现 SQLite、CRDT、autosave journal 或跨进程 operation protocol；
- 不记录 viewport、board name、skin 或 setting mutation；
- 不把 data URL 的资产内容误称为已迁移到 blob store；
- 不新增依赖；深拷贝使用平台 `structuredClone`，并保留 JSON-compatible fallback。

## 后果

- 历史内存从“每一步保留完整 `Element[]`”转为“每一步保留变更元素 + id order”；
- 旧项目可打开，下一次保存会使用 operation journal；
- 后续 SQLite `operations` 表、Worker protocol 和协作 replay 可复用 operation 形状，但仍需独立 FDD 定义持久化语义。

## 验证

- `npm run check:foundations`：operation delta、顺序、undo/redo、legacy migration；
- `npm run check`：TypeScript、Vite production build 与 foundation self-check；
- `npm run benchmark:history`：相同 fixture 对比 legacy snapshot JSON 与 property-only operation journal JSON。
