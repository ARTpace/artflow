# ADR-028：插件命令面板与工作区动作服务

- **状态**：accepted（verified）
- **日期**：2026-09-22
- **关联**：FDD-028、插件系统设计 §11 P2、FDD-025

## Context

The kernel already reserves a `commands` contribution slot and manifests already recognize `command`, but there is no typed command adapter, unified visible command surface, or safe way for a builtin to invoke a current App callback without importing UI siblings. Existing global keyboard handlers must remain stable, and command extension must not become an excuse to add a generic renderer backdoor, persistent configuration, or a new Electron capability.

## Decision

1. Add a typed `CommandContribution` adapter for the existing `commands` slot. It defines metadata, optional exact shortcut, enabled predicate and `run(kernel)`; list/search/shortcut resolution uses existing registry priority/id ordering.
2. Add one generic renderer-local Command Palette. It knows only contributions, search text and keyboard mechanics. `Ctrl/⌘K` opens it; `Alt+Shift+F/K/V/E` are initial builtin defaults. Editable, composing and presentation contexts do not dispatch command shortcuts.
3. Add a narrow renderer-local `workspace.command-actions` service. App supplies live callback proxies for already-existing Fit canvas/Finder/Saved views/Extensions operations. A plugin obtains the service only while running its command.
4. Add `builtin.commands-workspace`, a trusted builtin with `command` capability. It registers the four initial commands and owns their names, labels, keywords, shortcuts and service invocation.
5. A shortcut collision resolves to the first normal registry contribution. If that command is disabled, it does not silently run a lower-priority claimant. User remapping and conflict configuration are deferred.

## Consequences

- Users get a direct discoverable command workflow without duplicating existing UI behavior or changing persisted data.
- Commands become a reusable plugin contribution channel for later toolbar/menu/tool work.
- The host remains generic at the contribution boundary; its specific workspace action service is explicit, narrow and renderer-only rather than an unbounded `App` object.
- The initial service action set is intentionally not a generic command RPC protocol. Adding an action requires a new scoped review.

## Rejected alternatives

- **Put every command and palette entry directly in App**: user-visible but repeats the pre-plugin UI business pattern and cannot accept plugin contributions.
- **Let plugins import App callbacks / sibling components**: creates hidden dependency cycles and makes unload/testing boundaries meaningless.
- **Replace every existing keyboard handler now**: risks regressions in undo/redo/paste/presentation and is not needed for the first vertical.
- **Persist user bindings now**: expands profile/settings conflict semantics before command invocation behavior is validated.
- **Expose generic `invoke(action: string)` IPC**: turns a renderer UI feature into an unjustified capability expansion.


## Verification record

R28 implements this decision with a generic command registry/palette and one normal manifest-loaded trusted builtin. The real lifecycle fixture proves command ordering, shortcut matching, disabled collision behavior, service invocation and reverse disposal. The palette capture handler prevents dispatched plugin shortcuts from leaking into legacy keyboard listeners. No dependency, project document/schema, storage, IPC/preload capability or profile behavior changed; remote `typecheck`, `check:foundations` and production `check` passed on 2026-09-22.
