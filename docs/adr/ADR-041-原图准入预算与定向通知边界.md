# ADR-041：原图准入预算与定向通知边界

- **状态**：accepted（代码与自检已完成，真机帧率与手感待主人确认）
- **日期**：2026-09-23
- **关联**：ADR-036（多级图片 LOD 与 LRU 代理）、ADR-040（滚轮缩放手感与发布策略）；设计见《画布交互性能优化实施计划.md》P1-E 与 P2

## Context

主人反馈：**"现在图片一多，滚动就变得很卡。"** 这是 P1-D 修完滚轮手感之后暴露出来的下一层问题 —— 症状与"元素数量"相关，而不是与"某一次手势"相关。

### 先排除的错误假设（值得留档）

第一个怀疑对象是"相机变换写在 SVG `<g>` 上，每帧都要让浏览器重新光栅化整层内容" —— 听上去正好解释"图片越多越卡"，而且还有 `will-change: transform` 这种"看起来没生效"的细节佐证。

为避免凭直觉做一次大范围架构改造，先写了对照探针 `scratch/probe-transform-compositing.mjs`：同一份内容（含噪点图，避免被特殊优化）、同样逐帧只改一次相机变换，把变换分别放在三处 —— SVG 内层 `<g>`（当前做法）、`<svg>` 元素自身的 CSS transform、包裹 svg 的外层 HTML div：

| 图片数 | `<g transform>` | `<svg>` CSS transform | 父 div transform |
| --- | --- | --- | --- |
| 400（软件光栅化） | 16.7ms / p95 17.8ms | 16.7ms / p95 17.5ms | 16.6ms / p95 17.9ms |

**三者没有差异，也没有长帧。** 说明 Chromium 会复用 SVG 内容已光栅化的结果，`transform` 变化只更新变换矩阵，不触发整层重绘。假设被推翻，省下了一次大范围改造 —— 而且那个改法会连带破坏所有"用 `svg.getBoundingClientRect()` 换算世界坐标"的路径（变换一旦挂到 svg 之上，测量基准就跟着变，缓存机制还会掩盖错误）。

> 过程中还有两个测量学教训：无头浏览器没有 vsync（rAF 会跑到 160+fps，三种写法都"6.1ms"）；窗口移到屏幕外则根本不产生帧。**这种"都能测出好成绩"的环境不构成证据**，必须换到有真实光栅化的条件下测。

### 真正的根因

用真实 `ImageLRUCache` 复刻"跨过放大阈值时整屏图片同时准入"这一步（`npm run benchmark:lod`）：

| 图片数 | listener 调用 | 真实状态翻转（≈ React 重渲染） |
| --- | --- | --- |
| 300 | 90,000 | 550 |
| 800 | 640,000 | 1,550 |

调用量随图片数**平方**增长。原因是两处叠加：

1. **准入条件是"缩放级别"的代理**：

```ts
const eligibleForHighRes = Boolean(enabled && !isInteracting && zoom > 1.0 && originalHref);
```

`zoom > 1.0` 与"这一张到底需不需要更多像素"没有关系：一张 300px 的小卡片在 zoom = 2 时也只需要 600px。结果是 zoom 一过 1.0，**整屏图片同时 eligible**，一起去抢那 50 个配额。

2. **通知是广播**：`ImageLRUCache.request()` 每次向**全部**订阅者推送一份 `activeIds` 快照。容量只有 50，图片超过 50 张就必然"准入 → 驱逐 → 再准入"，于是每一次 request 都是一轮全体唤醒。

再叠加第三个放大因素：**每张图各自一个 180ms 定时器**。同一批变化落在几百个**独立任务**里，而 React 的自动批处理只合并同一个任务内的更新 —— 550 次状态翻转就是 550 次独立重渲染。

## Decision

1. **准入按屏幕像素需求，而不是缩放级别**：新增 `isFullResolutionWantedAtZoom(width, height, zoom)`，门槛 `FULL_RES_DISPLAY_PX_THRESHOLD = 1024` 与标准代理长边**同源**（代理本来就只有 1024px，屏幕用不到更多像素时换原图是纯浪费）。
   - 两个条件都保留：`zoom > DETAIL_ZOOM_THRESHOLD` 与"屏幕像素超预算"。只按像素放宽会制造"占着配额却渲染不出原图"的错配（`resolveImageLODSource` 仍以 `zoom > 1` 为准）。
2. **定向订阅取代广播**：新增 `subscribeAdmission(id, listener)`，`request` 只通知"新驻留的 id"与"被挤掉的 id"，复杂度 O(1)。旧的 `subscribe` 整体广播保留（测试与兼容用），热路径不再走它。
3. **准入队列 + 一次 flush**：`scheduleAdmission` 进队，180ms 后由一个任务统一 `request`。同一批 `setState` 因此落在同一个任务里，React 只提交一次。
4. **flush 按优先级升序请求**：优先级 = 屏幕最长边。LRU 的语义是"后请求者驻留"，**必须升序**才能让最需要清晰度的那批最终留在配额里；否则留下谁纯粹取决于遍历顺序（很可能留下最不需要原图的那些）。
5. **memo 重绘条件与准入判定同源**：`CanvasElement` 的图片比较器改调 `isFullResolutionWantedAtZoom`，替换掉原来"按 zoom 猜档位"的 `prev.zoom < 0.25 / > 1.0` 三元式。两边不同源就会出现"准入状态变了但卡片不重绘"（或反之）。
6. **小地图不再逐帧订阅 live**：投影与 marker 改用节流后的渲染态（O(元素数) 的工作不该每帧重做），只有**取景框**走 imperative 通道每帧写 4 个属性。旧实现每帧 diff 整棵树（含最多 240 个 marker 矩形）。

## Consequences

- 一次批量准入的调用量 **90,000 → 550（164×）**，量级 **O(N²) → O(N)**；准入范围在 zoom = 2 时从 300 张降到 90 张。
- 保留 ADR-040 的语义：滚轮缩放期间不降级 LOD；拖动（`isInteracting`）期间仍不准入并归还配额。
- **已知边界**：
  - 准入仍保留 `zoom > 1` 这道门（与 `resolveImageLODSource` 一致），因此"世界尺寸很大但 zoom ≤ 1"的图片仍不会用原图 —— 与改动前相同，本批刻意不扩大范围。
  - 原图配额（`FULL_RES_LRU_CAPACITY = 50`）仍是硬上限，超出部分用 1024px 代理，大图放大时略糊。这是资源约束，不是回归。
  - DPR 尚未纳入像素预算（计划 P2 条目）。
- **未验证**：真机帧率与手感、图片极多（数百张同时可见）时的实际表现、以及"按屏幕像素准入"在缩放来回抖动时是否会引起 LOD 反复切换（已有 1024 门槛 + 180ms idle 延迟，但阈值附近的行为未实测）。

## 验证

- 新增 `scripts/check-image-lod-budget.cjs`（并入 `npm run check`）：准入按屏幕像素（含边界 1023px / 1024.5px）、细节档门、交互中不准入、无原图不准入、**通知精确性**（只有自己状态变化才被唤醒）、**复杂度上界**（通知量 ≤ 图片数 × 2）、旧广播通道仍可用、以及源码接线守卫。
- 新增 `scripts/benchmark-lod-admission.cjs`（`npm run benchmark:lod`）：改前/改后对照。
- 两处关键断言做了**反证**：把 `request` 改回广播 → "a 准入时只该收到 1 次通知"失败；把准入改回"只看缩放级别" → "小卡片放大到 600px 屏幕尺寸时不应该准入原图"失败。确认不是假绿。
