# ADR-044：选中状态不得影响渲染驻留

- 状态：已采纳（2026-09-23，批次 P1-H）
- 相关：ADR-039（拖动会话瞬时通道）、ADR-041（原图准入预算与定向通知）、ADR-043（视口手势标记不得进入元素渲染依赖）
- 上游文档：`docs/画布交互性能优化实施计划.md`、`docs/实施迭代台账.md`
- 量化脚本：`scripts/benchmark-scale-hotpaths.cjs`、自检 `scripts/check-scale-hotpaths.cjs`

## 背景

前几批（P1-B'～P1-G）都在处理"手势路径"与"资源准入"的重复工作，并留下了 9 项全绿的自检。
真机测试仍然报告"几百张图时滚动缩放卡顿"。回到代码复核后发现，**上一批的结论覆盖不全**：
"9 项全绿 + 换档数量下降"只证明部分逻辑通过测试，不能证明整条缩放链路省下了足够的工作。

这次不做假设式优化，先把"与全量资产数成正比"的路径逐条量化（脚本不依赖浏览器，可复现）。

## 实测（合成场景，调用当前实现）

导入布局按真实代码复刻（`hooks/useFileHandlers.ts` 的等宽瀑布流，列宽固定 400）：

| 路径 | 测得的代价 |
|---|---|
| 裁剪被全选绕过 | 视口内只需 **8 张**；全选 1000/5000 张后返回 **1000/5000 张** |
| `getSelectionBounds` 旧口径 | 全选 5000 张 = **12,502,500 次**字符串比较（约 38ms 一次），而它有 10 个调用点 |
| 等宽布局换档同步性 | 最坏单步 **300 张同时换档**（尺寸分散布局只要 75 张，4×） |
| 滚轮增量覆盖 | 每帧 3 个事件时输入丢失 **94.7%** |
| 每个元素 memo 里的 `selectedElementIds.includes` | 0.19ms（全选 5000、挂载 30 个）—— **量级不足，本批不改** |

## 决策

### 1. 选中状态与渲染驻留解耦

`MainCanvas` 的裁剪白名单**不得**包含普通选中集，只放行"状态与挂载绑定"的三类对象：

- 拖动会话的 id（含组 / Frame 的后代）——拖动期间新位置只存在于拖动通道，视口索引仍是拖动前的位置；
- 文本编辑中的元素——编辑 UI 挂在元素自身，卸载就丢输入框；
- 裁剪中 / AI 旋转中的元素——交互过程不能中断。

理由：**选中是语义状态，不是"必须渲染"的声明**。手柄（`SelectionHandles`）与元素工具条（`ToolbarOverlay`）
都从全量 `presentElements` 取数据、按几何绘制，不依赖被选中元素是否挂载；屏幕外的选中元素本来也看不见。
白名单为空时不传 `includeElementIds`，省掉索引里一轮无意义的 id 查找。

保留"导入即全选"的既有交互（不改变用户可见行为）——它的代价已由本条与下一条消掉。

### 2. 选区边界改为索引口径 + 引用缓存

`getSelectionBounds` 从"每个选中 id 做一次 `allElements.find`"改为"建一次 id → 元素 索引"，
成本从 `O(选中 × 全量)` 降到 `O(全量 + 选中)`；并按 `(allElements, selectedElementsOrIds)` 两个引用做 1 槽缓存。

缓存前提与 `viewportIndexCache` 一致：元素几何改动都会产生新的数组 / 对象引用（已核查：无就地改写几何的代码），
因此两个引用都没变时结果必然相同。返回的 `Rect` 视为只读。

实测：全选 5000 张，38.5ms → 冷算 4.37ms → **命中缓存 0.029ms**。

### 3. 图片渲染需求必须单一真相源（不只是"共用选档函数"）

ADR-043 只保证"选档函数共用"，这不完整。影响输出的判定有三个，缺一个都会让 memo 拦掉 hook 真正需要的重绘：

| 字段 | 漏掉它的后果 |
|---|---|
| `desiredTier` | 该换 LOD 却没重绘 |
| `eligibleForOriginal` | 1600×900 图 zoom 0.9→1.1：准入 false→true，但选档结果没变 → **申请原图的更新被拦掉** |
| `samplingMode` | 400×225 图 zoom 0.9→1.1：档位都是 standard，但 `imageRendering` 该从 optimizeQuality 变 auto → **样式停在旧值** |

因此新增 `resolveImageRenderRequirement`（返回这三个字段）+ `isSameImageRenderRequirement`：
`CanvasElement` 的 memo 比较整个判定，`useImageLOD` 的准入条件取同一个函数的 `eligibleForOriginal`，
`imageRendering` 取 `samplingMode`。异步准入是否已落地由资源状态单独驱动，不进这个判定。

### 4. 滚轮 delta 必须累加（相对增量 ≠ 绝对样本）

同一 rAF 窗口内的滚轮事件，`deltaX/deltaY` 是**相对增量**，累加；`clientX/clientY` 是**绝对锚点**，保留最新。
旧实现整体覆盖，等于按"帧"丢弃输入，且机器越忙丢得越多。

`resolveWheelZoomFactor` 是指数模型、平移是线性模型，所以"累加后应用一次"与"逐个应用"**数学等价** ——
这是精确修复而非手感调参。实测：每帧 3 个事件时，旧口径最终只放大到应有值的 5.3%。
同帧内切换操作模式（触控板两指滑动 ↔ 捏合）时，先把旧模式的累积结清再用新模式，避免被覆盖。

## 后果

- 等宽导入布局的"同步换档"仍然存在（同尺寸图共用同一门槛），但裁剪修好后换档集合被收敛到视口内：
  最坏单步 1000 张 → **32 张（31.3×）**。
- 因此"有界预解码 + 分批换源"的优先级**下降**：它解决的是同批换档峰值，而当前峰值已被裁剪收敛。
  下一步应先录真实 trace 定位剩余瓶颈（脚本 / 图片解码 / Raster / 合成），再决定是否需要它。
- 已知边界：本节所有数字是合成场景下调用真实模块得到的，**不是真机 FPS**；真实项目还有 React 重渲染与
  DOM 属性更新成本，需要真机 trace 才能归因。

## 反证（确认断言不是假绿）

| 反证 | 结果 |
|---|---|
| 把选中集塞回裁剪白名单 | `check-scale-hotpaths` 断言失败 |
| `getSelectionBounds` 改回 `find` 口径 | 断言失败 |
| memo 退回"只比档位" | 断言失败 |
| 滚轮改回覆盖语义 | 断言失败 |
