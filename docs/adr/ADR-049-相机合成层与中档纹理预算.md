# ADR-049：相机合成层与中档纹理预算

- **状态**：accepted（代码与自检已完成，**真机帧率待主人确认**）
- **日期**：2026-09-23
- **关联**：ADR-041（原图准入预算，曾以无头探针"推翻了"本 ADR 的主假设）、ADR-042（档位切换时机）、ADR-043（手势标记不进渲染依赖）；探针 `scratch/probe-transform-compositing.mjs`（本次加了 `HEAD=1` 有头模式）

## Context

主人反馈：**"一屏出现几百个高清图片的时候，拖动和滚轮缩放都会卡。之前的优化没能根本解决。"**

ADR-041 修掉了准入广播的 O(N²)，但本症状依旧。重新排查渲染管线，两个根因：

### 根因 1：相机 transform 挂在 SVG 内层 `<g>` 上，每帧重栅格化整片内容

`MainCanvas` 把相机变换写到内层 `<g>` 的 `style.transform`（带 `will-change:transform`）。对 Chromium 来说这是**不产生独立合成层**的写法：

- SVG 内部元素（`<g>` 等）不参与 HTML 合成器建层，`<g>` 的 transform 每变化一次，整片 SVG 内容（几百张已解码的 1024px 图）就要重新光栅化一遍 —— pan/zoom 的每帧成本**随图片数增长**，这正是"图越多越卡"的形状；
- 且 `<g>` 上的 `will-change:transform` 对 SVG 内部元素会被显式拒绝（Chromium issue 40753139，"Don't pass will_change_transform to cc for SVG"）—— 提示等于没生效。

> **纠正 ADR-041 的一次误判**：当时用无头 Edge 跑三挂载方式对照，"16.7ms 无差异"于是推翻了该假设。但无头窗口不产生真实帧（ADR-041 自己记录了"这种都能测出好成绩的环境不构成证据"）——那次对照测不出差异是**测量环境失效**，不是假设被证伪。本 ADR 把探针改成 `HEAD=1` 有头模式（真实窗口 + GPU 光栅化）后重新对照，判定以真机为准。

### 根因 2：标准档固定 1024px，密集多卡场景纹理预算失衡

"一屏几百张"时每格屏幕像素只有 150~500px，却各自持有一张 1024px 纹理（300 张 ≈ 0.9GB）。pan/zoom 的合成带宽、以及手势收尾后整屏换档的重栅格，都按这份预算付费。

## Decision

### 1. 相机 transform 移到 `<svg>` 元素自身（GPU 合成层）

- `<svg>` 根是普通 CSS 盒子：`will-change:transform` 使其成为稳定合成层，pan/zoom 时合成器**只更新变换矩阵、不重栅格化**，每帧成本与图片数无关；
- 配套三件事缺一不可：
  1. `transform-origin: 0 0` —— 保持 `屏幕 = pan + 世界 × zoom` 的映射公式不变；
  2. `<svg>` 的 `overflow: visible` —— 关掉 svg 自身视口裁剪，否则裁剪跟着变换落到世界坐标系（裁到初始视口盒子而不是屏幕）；屏幕裁剪仍由外层容器 `overflow:hidden` 承担；
  3. 内层 `<g>` 保留结构占位，不再参与变换。
- **已知代价（接受的）**：大跨幅缩放期间，合成层按旧栅格比例合成、画面暂时偏软；变换稳定后浏览器按新比例重新栅格化。手势收尾后的 LOD 换档（180ms）正好落在这次重栅格上，观感与 PureRef 一致。
- **已知边界**：svg 合成层的栅格范围随"裁剪后可见世界区域"增长（远看时更大），但 Chromium 的栅格比例按屏幕有效缩放计算，显存占用有界；且裁剪 overscan 恒定（`RENDER_PUBLISH_MOVE_PX * 1.25 / zoom`），不会额外放大。

### 2. 坐标换算基准改为未变换容器

transform 挂到 `<svg>` 后，`svg.getBoundingClientRect()` 返回**变换后的盒子**（随 pan/zoom 漂移）。新增 `getCanvasScreenRect(svg)`（量 `svg.parentElement` —— 未变换、与 svg 未变换时盒子重合），全部换算点统一切换：

- `App.readCanvasRect`（`getCanvasPoint` 热路径，缓存 + ResizeObserver 改观察容器）、fit、finder、粘贴、中心点、`canFitCanvas`；
- `useCanvasInteractions` 悬浮工具条定位、**滚轮手势 rect 缓存**（缓存的正是不能漂移的盒子）；
- `useAIHandlers`（视频/图片生成落点）、`useFileHandlers`（导入锚点 ×3）、`usePresentation`（focus 居中）、`useSmartToolbar`（工具条定位）；
- `MainCanvas` 裁剪尺寸测量（保持"全文件只量一次布局"的既有守卫）。

### 3. 新增 512px 中档（texture budget tier）

- `IMAGE_LOD_CONSTANTS.MEDIUM_PROXY_MAX_DIMENSION = 512`；选档按屏幕像素：≤256 thumbnail / **≤512 medium** / ≤1024 standard / ≥1024 且 idle 且准入 original；
- `generateProxyDataUrls` 导入时生成 512px 中档（原图长边 >512 才生成，不放大）；`ImageReadResult` / `LoadedItem` / `FormatImageResult` / 元素 `mediumHref` / `AssetLocator.mediumRef` 全链路透传，v2 文档无损往返；
- 中档**不受**"交互中不升原图"限制：它比标准档省，手势中降级有收益；原图仍受 180ms idle 准入约束；
- 无中档源（旧项目/小图/矢量）时行为与引入前完全一致（选档函数按 `hasMedium=false` 走旧路径）；
- 显存收益：每格 ≤512px 屏幕像素的卡片，纹理从 1024² 降到 512²（**1/4**）；"几百张一屏"从 ≈0.9GB 降到 ≈0.2GB 量级。

## Consequences

- pan/zoom 每帧成本从 O(可见图片数)（重栅格化）降到 O(1)（合成器矩阵更新）—— **这是"根本解决"的主体**；
- 密集多卡场景纹理显存 ×1/4，手势收尾后的整屏换档重栅格也按 1/4 的像素量付费；
- 文档体积：每张 >512px 的图多一个 512px 中档 data-url（与既有 thumbnail 同量级，≈40~120KB 基64）；
- **真机帧率未验证**：本环境无法产生真实帧（无头探针失效的教训在前）。判定路径：
  1. 直接实测应用（几百张高清图一屏，拖动/滚轮）；
  2. `HEAD=1 node scratch/probe-transform-compositing.mjs`：对照 `<g transform>`（旧）/ `<svg> CSS transform`（新）/ 父 div 三种挂载的帧间隔与合成层归属，改动前后各跑一次。
- 若真机仍卡：下一步按 ADR-041 的边界清单走（DPR 纳入像素预算、准入 `zoom>1` 门放宽、RasterScale 提示），不再回头怀疑本批的几何/接线。
