# ADR-053：安全模式（工厂启动）的三条语义 —— 读空、只读会话、不采纳旧键

日期：2026-10-09
范围：`docs/用户数据层架构方案.md` §4 P3 第 1 项（`ARTFLOW_SAFE_MODE=1`，对标 Blender `--factory-startup`）

## 背景

P1/P2 把全部应用级用户数据从渲染层 `localStorage` 搬到了主进程文件
（`userData/config/preferences.json` + `secrets.json`、`plugin-profile.json`）。
搬完之后出现了一个**新的缺口**：用户数据一旦成为"真正的数据"，就必然会有"某一条数据
把应用搞坏了"的情况 —— 关不掉的插件、打不开的皮肤、启动就崩的配置。

在此之前这个问题无法可靠二分：数据住在浏览器存储里、按 origin 分三份，用户描述的现象
（"插件关了又自己开"）与"我的配置丢了"症状完全重合，排查只能靠猜。

需要一个**秒级二分手段**：以"全新安装的样子"启动一次，看问题还在不在。
Blender 的 `--factory-startup` 就是这个东西。

## 决策

新增环境变量 `ARTFLOW_SAFE_MODE=1`，判定收在 `main/safeMode.cjs` 一处，
由 `main.cjs` 解析后**注入**给各存储卷（存储层自己不读环境变量，回归脚本才能直接传
`safeMode: true` 做对拍）。语义三条：

### 1. 读空 —— 但不等于"读失败"

所有用户卷（preferences / secrets / plugin-profile）读到 **空值**，插件按默认装载。
关键细节：返回的快照是 `ok: true`、`source: 'safe-mode'`、**`degraded: false`**。

如果把它标成降级，设置页会按既有链路弹一条"配置异常"告警，把一个刻意为之的正常状态
报成故障，把用户引去修一个没坏的东西。降级语义必须留给"真的坏了"。

### 2. 只读会话 —— 宿主拒写，渲染层不抛错

- **宿主侧**：`createConfigStore` / `createPluginProfileStore` 的任何写入
  （`set` / `patch` / `reset` / `write` / `clear`）一律返回 `ok: false` + 说明原因。
  一次"顺手保存"就会把用户的真实配置覆盖成默认全集，而那是不可逆的。
- **渲染层**：`preferences-store` 在安全模式下**只改内存、不落盘，且不抛错**。

第二条是有意打破"写失败必须同步抛出"这条既有契约的，理由必须写清楚：
启动期有一批 effect 会把当前值（多数是默认值）"写回"一遍 —— 滚轮动作 / 用户特效 /
生成快捷键 / 放映快捷键 / 画布视图各一次。宿主必然拒写，若渲染层照旧抛错，
这几处会各自刷一条 `[启动错误]`，**用户拿到的第一份日志全是噪声** ——
而"拿到一份干净的日志"正是安全模式的全部意义。

这也不构成"假成功"：横幅明写"本次改动不会保存"，宿主同样拒写，用户面对的是一个
**被如实告知的只读会话**，而不是被悄悄吞掉的失败。

**刻意保留的不对称**：插件开关（`plugin-state-storage`）与密钥（`secrets-store`）
的写入仍然抛错。它们的写入只发生在**用户显式操作**时，抛出来就是有用的反馈
（"安全模式下这个改不了"），而不会在启动期自发刷日志。

### 3. 不采纳旧键 —— 且不写采纳标记

这是最容易漏、漏了就等于安全模式根本没生效的一条：

偏好卷读空 → 每个登记在 `LEGACY_KEYS` 里的键都"缺值" → 采纳逻辑会把用户真实的
旧 `localStorage` 值原样搬回来。于是"读空"被自己人填满了。

所以 `preferences-store` / `preference-storage` / `secrets-store` 在安全模式下
**整段跳过采纳**，并且**不打采纳标记**。留白是刻意的：这次"没查过"，
去掉环境变量正常启动时照旧采纳一次 —— 标记若在这里写下去，那份旧数据就**永远**不再被采纳了。

同一类问题在插件偏好上还存在第二处：`plugin-state-storage` 在"宿主为空"时会去
`localStorage` 做一次性迁移。安全模式必须在这条路之前短路，否则旧开关记录会被搬回来。

### 附带的两条

- **不装载用户安装的外部插件**：`listDeclarativePlugins` / `listInstalledPlugins` /
  `listSandboxedPlugins` / `readPluginClients` 一律返回空；安装 / 卸载 / 调用直接回绝
  （对标 `--factory-startup` 忽略用户 addons）。判据放在 **IPC 边界**而不是各扫描函数
  内部 —— 扫描函数仍只认一个 root，不必各自长出一条分支。
- **可见性**：安全模式**故意**不读用户配置，界面看起来就是"我的皮肤没了、插件开关全回来了、
  语言变回中文" —— 与"用户数据丢了"的症状一模一样。所以必须显式提示，且必须常驻：
  - 窗口顶部下方常驻横幅（`components/SafeModeBanner.tsx`，`data-bp-safe-mode-banner`，
    **不给关闭按钮**）；
  - 窗口标题后缀 —— 由渲染层改 `document.title`（Electron 默认让页面标题决定窗口标题），
    主进程再挂一道 `page-title-updated` **兜底**：安全模式最先要排查的就是"启动失败"，
    那种情况下 React 可能压根没挂起来；
  - 启动日志一条显式的 `⚠ 安全模式…`，并列出被忽略的文件路径；
  - 渲染层上报 `source=host-safe-mode` 时，主进程额外补一句"上面的 0 个键是刻意的"。

## 为什么是环境变量而不是命令行参数

打包后双击启动不会带环境变量，天然避免"用户不小心进了安全模式却以为自己的配置丢了"。
要排查就显式 `ARTFLOW_SAFE_MODE=1`，且必须是字符串 `'1'`（`'true'` 不算，避免误进）。

## 验证

- `scripts/check-safe-mode.cjs`（新增，注册进 `npm run check`）—— 9 组断言，
  覆盖判定入口、读空且不降级、宿主拒写且磁盘零变化、插件偏好卷、渲染层不采纳且不写标记、
  只读会话（不抛错 / 只改内存 / 宿主零变化）、存储适配器、插件状态存储的 safe-mode 源、
  密钥卷。
- `scratch/2026-10-09_p3-safe-mode/probe-safe-mode.cjs` —— 隔离实例端到端，
  **同一份 userData 的 A/B/C 三段对拍**：S1 播种 → S2 安全模式 → S3 对照。
  S3 的存在是必需的：若 S3 也读不到 S1 种下的东西，S2 的"空"就毫无证明力。

## 教训

1. **"空"与"坏"必须用不同的 source 表达**。两者都返回空值，但一个要弹告警、一个不能弹。
   靠 `source` 区分而不是靠消息文本，是这次能一次做对的原因。
2. **一个"忽略用户数据"的模式，必须同时管住四条流入路径**：文件读取、旧键采纳、
   旧键迁移、外部资源装载。只做第一条等于没做 —— 数据会从另外三条自己回来。
3. **端到端探针要拿同一份数据做对照**。第一轮 34/35 里失败的标题断言、以及事后从日志里
   读出来的"假启动错误"，都是单靠单测发现不了的：前者是"断言测错了对象"，
   后者是"没人断言日志干净度"。现在两者都有断言钉住。
