# ADR-040：滚轮缩放手感与发布策略边界

- **状态**：accepted（代码与自检已完成，实际手感、帧率与触控板表现待主人真机确认）
- **日期**：2026-09-23
- **关联**：ADR-036（多级图片 LOD 与 LRU 代理）、ADR-038（相机瞬时通道）；设计见《画布交互性能优化实施计划.md》P1-D

## Context

主人拿 PureRef 做对比实测：那边"滚动缩放完全没卡顿，1~2 次滚动就能放大看到整图"，本工具要滚 4~6 次，而且"不是很丝滑、有点掉帧"。

排查后发现是**三个独立问题叠在同一条路径**上，而不是一个"慢函数"：

```ts
// 旧路径（hooks/useCanvasInteractions.ts 的 handleWheel / applyPendingWheel）
const WHEEL_ZOOM_EXPONENT_PER_DELTA = Math.log(1.05) / 100;   // ① 一格只放大 5%
nextZoom = base.zoom * Math.exp(-pending.deltaY * WHEEL_ZOOM_EXPONENT_PER_DELTA);
viewportStore.setTransient({ zoom: nextZoom, panOffset: nextPan });   // ② 事件驱动直接写相机值
if (!isInteracting) setIsInteracting(true);                   // ③ 触发 LOD 全量降级
```

① **幅度**：Chromium/Windows 上一格滚轮是 `deltaY = 100`，按上式恰好放大 5%。PureRef 的量级约 1.25/格，所以观感差 5 倍 —— "要滚 4~6 次"是算术结果，不是主观感受。

② **不丝滑**：滚轮是**离散事件**（一格一个 `wheel`，间隔还不均匀）。把每个事件的结果直接写成相机值，视觉上就是"跳 → 停 → 跳"。触控板的多指滑动虽然 delta 更密，但仍受事件节拍影响。

③ **掉帧**：`isInteracting` 是图片 LOD 的降级开关 —— ADR-036 的 `useImageLOD` 里

```ts
const eligibleForHighRes = Boolean(enabled && !isInteracting && zoom > DETAIL_ZOOM_THRESHOLD && originalHref);
```

`eligibleForHighRes` 变 false 时，effect 会 **release 掉该元素的高清原图**并让 `resolveImageLODSource` 返回 1024px 代理。于是滚轮一进一出会发生：

- 第一个滚轮事件 → 所有可见图片降级到代理 → 已是 original 的图重新解码成 1024px 版本；
- 滚轮停 200ms → `setIsInteracting(false)` → 所有图片又开始请求高清原图（180ms idle 后）→ 再解码一轮。

**两轮全量解码**就是"掉帧感"的主要来源。叠加"每跨 8% 缩放就发布一次渲染通道"（重建裁剪 + 挂载/卸载卡片）。

## Decision

1. **倍率 1.05 → 1.25/格**，并把"滚轮量 → 缩放倍率"的换算抽到 `utils/wheel-input.ts`（`normalizeWheelDelta` + `resolveWheelZoomFactor`）。抽成纯函数是因为这两个数"改错却不报错"（倍率写错只是手感差，deltaMode 不折算会让滚轮在某些驱动上近乎失效），而它们都能被自检直接验证。
2. **deltaMode 归一化**：行模式（DOM_DELTA_LINE）按 16px/行折算。原实现直接读 `e.deltaY`，在给出行模式的鼠标驱动/触控板上，一格只有 3 个单位 → 缩放 0.7%，等于滚轮失效。
3. **平滑追随**：滚轮只写"目标相机"（`viewport-store.setSmoothTarget`），live 每帧向目标指数逼近（`SMOOTH_FOLLOW_FACTOR = 0.45`，相对差 0.4% / 0.4px 收敛），收敛后自动停 rAF。离散输入因此变成连续运动；连续滚动时表现为一阶低通。
4. **缩放基于目标累积**：新增 `getTarget()`，滚轮用它当基准而不是 live。追随期间 live 只走了一部分，若拿 live 当基准，"滚得越快、每格增量越小"，手感会越滚越黏。
5. **滚轮不再置 `isInteracting`**：缩放是 GPU 变换，继续使用已准入的高清纹理比"降级 → 解码 → 恢复 → 再解码"划算（PureRef 就是这个行为）。工具条冻结条件从 `isInteracting` 扩为 `isInteracting || isViewportGesture` —— 否则滚轮期间每次渲染通道发布都要读一次布局再 setState。
6. **方向感知的渲染通道发布**：缩小用 6% 阈值（可见世界范围在变大，裁剪滞后就会在边缘露出未挂载的空白），放大用 30% 阈值 + 250ms 时间上限。放大时可见集只会变小（多挂着的卡片不产生视觉问题），于是"连续放大"这条最常见的手势几乎不碰 React 渲染树。
7. **滚轮平移保持 1:1 跟手**：触控板两指滑动的平移不加平滑（那会有拖尾感），仍走 `setTransient`。平滑只服务于"离散的缩放输入"。

锚点稳定性（本批唯一的数学风险点）：滚轮缩放的目标值由"鼠标下的世界点不动"定出，即 `pan(z) = m - (m - p0) · z / z0`。zoom 与 pan 都用同一个系数从初值插值到目标值时，中间帧满足

```
pan_t = p0 + (p1 - p0)·f = p0 + (m - p0)(1 - z1/z0)·f
z_t   = z0 + (z1 - z0)·f
世界点 = (m - pan_t) / z_t = m    （与 f 无关）
```

即追随期间锚点**精确**不动。若两者用不同系数（很容易写成两份独立 lerp），画面会在光标下缓慢平移 —— 比不做平滑更难用。这条已写成自检断言。

## Consequences

- 滚轮手感：一格 1.25（原 5%），连续滚动平滑跟随，停止后自动收敛并一次性提交相机。
- 图片 LOD 在滚轮期间**不再抖动**：`zoom < 0.25` 用缩略图、`zoom > 1.0` 且经 LRU 准入用原图，这两条仍按 zoom 变化正常工作，只是不再被"手势中"强制压到代理。
- 放大方向的 LOD / 裁剪跟随按"30% / 250ms"滞后（手势结束立即补齐）：跨 1.0 阈值后图片可能晚一拍变清晰。
- 相机提交时机不变（滚轮静默 200ms / 手势被打断），服从 ADR-038 的三通道语义。
- 已知取舍（见 Revisit triggers）：平滑把"立刻到位"变成"约 0.1~0.15s 内到位"；快速连滚表现为低通跟随。

## Rejected alternatives

- **只调倍率、不做平滑**：幅度问题解决了，但事件节拍造成的顿挫仍在（触控板尤其明显），而"丝滑"是本次的主要诉求之一。
- **加滚轮速度自适应（越快越猛）**：PureRef 有类似行为，但会让手感不可预测、难以标定；先让倍率成为唯一旋钮。
- **用固定时长动画（如 120ms 线性）代替指数逼近**：连续滚动时每来一个事件就重启动画，动画互相打断会产生新的顿挫；指数逼近天然是一阶低通，不需要重启。
- **保留滚轮期间的 LOD 降级，改把 `isInteracting` 变成 store 订阅**：改动面大，而且降级本身在缩放场景下有害（切换代理 = 额外的解码与纹理上传，而缩放只是采样）。
- **缩放期间完全不发布渲染通道**：放大时 LOD 永远不会更新，图片一直是代理分辨率，用户会认为"放大没用"。
- **`syncDocument` 也走平滑追随**：文档侧（书签、Fit、载入项目）需要精确落位，加平滑只会让恢复视图变慢且不确定。

## Revisit triggers

- 1.25/格 在真机上偏快或偏慢 → 只改 `utils/wheel-input.ts` 的 `WHEEL_ZOOM_RATIO_PER_NOTCH`（唯一旋钮，自检会锁住行为）。
- 放大方向"30% / 250ms"造成可感知的"糊一拍" → 收紧 `RENDER_PUBLISH_ZOOM_GROW_RATIO`，或改为"跨越 LOD 阈值（0.25 / 1.0）时强制发布一次"。
- 追随期间在鼠标位置可看到漂移 → 先确认 zoom 与 pan 是否用了同一个系数（自检断言误差阈 0.01px，若失败即为两份插值分叉）。
- 连续滚动时 live 明显滞后于滚轮/手指 → 提高 `SMOOTH_FOLLOW_FACTOR`（代价：平滑感下降）。
- 若 profiling 证明"滚轮期间不降级 LOD"在大项目中反而更重 → 改为**只在缩小方向降级**（缩小时卡片在屏幕上更小，代理图更划算；放大时需要清晰度，不降级），而不是回到全手势降级。
- 触控板（尤其是 macOS 惯性滚动）出现"滚完还在追" → 缩短 `WHEEL_GESTURE_IDLE_MS` 或在收敛完成前不提交。
