# ADR-058 · 启动链解构完整性守卫与异步断言收口

- 状态：已采纳
- 日期：2026-10-10
- 关联：`main.cjs`、`scripts/check-plugin-openings.cjs`

## 背景

用户报障：「启动 Artflow.lnk 启动不了了」。

启动链本身**完全正常**——`.lnk → start-electron.vbs → scripts/launch-desktop.cjs →
vite + electron` 全在，文件都在。真正的失败在 `logs/launcher.log` 里：

```
[boot +  661ms] app ready
(node:41816) UnhandledPromiseRejectionWarning: ReferenceError: setArchiveReader is not defined
    at registerPluginStoreIpc (H:\AI-Tools\artflow\main.cjs:634:21)
    at H:\AI-Tools\artflow\main.cjs:1540:3
[boot + 2813ms] splash 显示
```

即：**splash 闪现一下就没了**。快捷方式双击后看起来「什么都没发生」，
唯一线索在日志里。

根因是一行之差 —— `main/pluginSandboxHost.cjs:173` 导出了 5 个函数，
`main.cjs:10` 的解构只写了 4 个：

```js
// 修复前
const { activateInstalledPlugins, invokePlugin, listPluginClients, setPluginStore } = require('./main/pluginSandboxHost.cjs');
// 修复后
const { ..., setPluginStore, setArchiveReader } = require('./main/pluginSandboxHost.cjs');
```

`main.cjs:637` 调用了 `setArchiveReader(comicArchive)` → ReferenceError。
这是插件沙箱那次改动（漫画档案仓接线）留下的漏项，与启动链无关。

## 为什么 `node --check` 抓不到

`node --check` 只验语法。这行**语法完全合法**（解构少一个字段不报错），
运行时才炸。而炸点在 `registerPluginStoreIpc()` 里，抛的是未捕获的 Promise 拒绝，
主进程随后退出 —— 这是**最坏的一类启动失败**：没有对话框、没有非零退出码透出，
用户只看到「双击了但没反应」。

## 决策

### 1. 修掉漏解构（`main.cjs`）

补上 `setArchiveReader`。实测启动后窗口标题 `Artflow` 稳定出现，
`electron.log` 中该报错 **0 次**。

### 2. 加「解构完整性」守卫，而不是靠人肉记住

守卫同时查**两个方向**，且都基于真实模块导出而非硬编码字符串：

- **漏解构**：`pluginSandboxHost.cjs` 导出了但 `main.cjs` 没解构 → ReferenceError；
- **多余解构**：解构了但模块没导出 → 拼错名字，同样 ReferenceError。

外加一条调用点检查：`main.cjs` 里出现 `setPluginStore(` / `setArchiveReader(`
调用时，必须有对应解构（覆盖「新增调用但忘了加进解构」）。

**已反向验证**：把解构改回错误状态，守卫精确报出
`main.cjs 未从 pluginSandboxHost.cjs 解构 setArchiveReader（该模块已导出它）`，
`EXIT=1`。一个永远 PASS 的守卫等于没有守卫。

### 3. 顺手修掉「写了但从未执行」的异步断言

改守卫时暴露出更严重的问题：`check-plugin-openings.cjs` 里所有
`performPluginHostOp(...).then(r => assert(...))` **都是裸 `.then`** ——
脚本是 CommonJS 顶层同步流，进程在 promise settle 前就退出，
**这些断言从来没有真正跑过**（2026 引入的插件沙箱测试，一直是空转）。

改成`assertHostOps()` 异步函数 + 末尾 `.then/.catch` 收口（`.catch` 里
`process.exitCode = 1`，CI 才拦得住）。

**守卫一真正生效就立刻抓到第二个真实 bug**：测试把
`performPluginHostOp(fileDir, services, request)` 的第一个参数传成了
**目录字符串**，而契约是**插件描述对象** `{ dir, permissions }`
（`sandboxedPlugins.cjs:257-268`）。传字符串 → `plugin.permissions` 与
`plugin.dir` 都是 undefined → 直接落到 `'file read is not permitted'`。
这个错误入参一直存在，只因断言从未执行才没被发现。

## 后果

- 顺带修正了 `check-plugin-openings.cjs:285` 那条过期断言
  （`pluginSandboxHost.cjs` 的 parse 上限已从 8 MiB 提到 512 MiB，
  断言仍写旧值 → `check:plugin-openings` 长期 FAIL）。
  改后断言跟到新值，并把「上限数值」明确标为**不是回归点**，
  避免它变成「必须改回旧数字」的枷锁。
- 解构完整性守卫目前覆盖 `pluginSandboxHost`。其余 `main/*.cjs` 依赖
  若将来出现同类漏项，需同样加守卫 —— 本 ADR 只修真实故障点，不铺开做。

## 排查经验（本机）

- **启动失败先看 `logs/launcher.log`**，它会打印崩溃时 electron.log 最后 20 行，
  比翻代码快得多。
- Electron 主进程崩溃**不一定有退出码透出**：日志里的
  `UnhandledPromiseRejectionWarning` 才是真凶。
- 读 `.lnk` 指向时 `WScript.Shell` COM 被沙箱拦（安全策略），
  改从 VBS 注释里推断启动链更快 —— VBS 头部把 chain 和陷阱都写在注释里了。
