# ADR-038：相机瞬时通道与文档状态解耦边界

- **状态**：accepted（代码与自检已完成，实际手感待主人真机确认）
- **日期**：2026-09-23
- **关联**：ADR-011、ADR-014、ADR-020、ADR-021、ADR-023、ADR-031、ADR-038 设计见《画布交互性能优化实施计划.md》P1-B' 与 P1-B

## Context

画布平移（pan）、滚轮缩放（zoom）与卡片拖动（drag）是最高频的交互热路径。改动前这三者都逐帧写入顶层 `boards`（`updateActiveBoard`）：

- App 是整个工作区的所有者，`boards` 变化 → App 整棵函数体重跑 → TopBar / Toolbar / PromptBar / 侧栏面板 / 插件 widget 宿主全部重绘（全项目只有 `CanvasElement`、`SVGDefs`、`GalaxyStarLayer` 三个组件做了 memo）。
- 每帧伴随 O(元素总数) 的派生工作：`workspaceMetrics` 对 boards 全量 reduce+filter、`viewport-index.update` 的逐项 identity 扫描、`isElementVisible` 用 `find` 线性找 parent。
- 每帧伴随强制同步布局：悬浮工具条的 effect 依赖 `zoom/panOffset`，每帧 `getBoundingClientRect()` + setState；滚轮**每个事件**都量一次布局并写一次 boards；`getCanvasPoint` 每次调用都量布局（交互中每帧两次）。
- 相机写入还会把项目标记为"有未保存改动"，于是"只挪一下视角"会在 1.5s 后触发一次自动保存。

代价因此与"整个工作区规模"成正比，而不是与"移动了多少"成正比。P0/P1-A 已完成（LOD、媒体 preload、准入延迟），但未触碰这条根因。

## Decision

1. 新增 `utils/viewport-store.ts`：画布相机（`panOffset`/`zoom`）的**瞬时通道**，与 Board 文档状态解耦。三条通道分工：
   - **live**：手势中的真实相机值，`subscribeLive`，每帧只通知即时消费者（相机图层 transform、导航器小地图）。
   - **renderState**：React 渲染用相机值，只驱动裁剪 / LOD / 叠加层这类需要重绘的东西。发布策略是"位移优先、时间兜底、节流下限防抖"：位移累计 ≥120px 或缩放变化 ≥8% 立即发布（裁剪滞后会在快速平移时露出空白带），否则按 ≤100ms 时间上限兜底，40ms 下限保证任何情况下都不退化成逐帧渲染。**进入手势不额外发布**（手势起点没有位移，发布只会让裁剪白算一轮并多挂载一圈卡片，那正好是最不该卡的 mousedown 瞬间）；退出手势立即发布最终值。
   - **document(committed)**：已提交到 Board 的值。手势结束（或显式 `flush`）时**只写一次**。
2. `MainCanvas` 的相机图层 `<g>` 的 transform 改为 **imperative 独占**：React 不再渲染 `translate3d`，由 `subscribeLive` + rAF 直接写 `style.transform`；React 用节流后的渲染态决定裁剪候选、LOD tier 与叠加层缩放。App 必须把 store 传进 `MainCanvas`（SSR 检查锁定该契约）。
3. 交互入口改造（`hooks/useCanvasInteractions.ts`）：
   - 平移：mousedown 记录基准相机与起点指针，逐帧只写瞬时值（绝对值，不再累加），mouseup 提交一次；
   - 滚轮：事件按 **rAF 合并**，一个手势只量一次 SVG 布局，静默 200ms 后提交一次；缩放改用指数模型 `exp(-Δ·ln(1.05)/100)`，保证"传统鼠标一格"的缩放总量与旧实现完全一致，同时让触控板连续小 delta 变平滑；
   - 悬浮工具条在交互期间不再做布局计算：拖动期间冻结、相机手势期间隐藏，手势结束后重算一次；
   - 无 store 时保留旧的逐帧写入路径（向后兼容，便于回滚与局部复用）。
4. 手势中的裁剪用 **overscan** 兜住 ≥120px 的发布滞后：按屏幕短边 30% 折算到世界单位（最小 200），只覆盖 120px 阈值所需的余量，不按"半个视口"放大面积（那会把可视卡片数放大约 5 倍）。
5. 背景底板（`CanvasBackground`）改为世界原点锚定的固定跨度矩形：网格 pattern 是 `userSpaceOnUse`，底板不需要相机值，否则会与 imperative transform 抢同一帧。
6. `usePresentation.zoomToBounds` 的动画（600ms，原先每帧写 boards）改走瞬时通道，结束时提交一次；被打断时先提交当前位置。
7. `getCanvasPoint` 改为"缓存 rect + 读 live 相机"：布局变化由 ResizeObserver/window resize 失效，交互中不再每帧强制回流。
8. 切画板前必须先 `endInteraction()` 提交旧画板的相机（提交走的是 `activeBoardId` 闭包，必须在 `setActiveBoardId` 之前），`window.beforeunload` 把未提交的 live 相机补进保存快照。
9. 变更追踪（`utils/projectChangeTracker.ts`）按"忽略相机键"逐项引用比较：只有 `panOffset`/`zoom` 变化不算内容变化；未知/新增字段仍按内容对待（保守）。

## Consequences

- 平移/缩放/帧间动画期间，**App 与工作区外壳不再重绘**；每帧工作降到"一次 rAF 字符串赋值 + 一次裁剪发布（≤8.3 次/秒）"。
- 相机仍然持久化：落在 Board 上、随常规保存/导出生效，只是"改为手势结束时提交一次"。
- 体验变化（需主人真机验收）：
  1. 相机手势期间悬浮工具条（SmartToolbar）隐藏，松手/滚轮静默后回到选区旁；
  2. 手势中 LOD 与叠加层描边按"位移 ≥120px / 缩放 ≥8% / 100ms"跟随，快速跨阈值缩放时图片层级切换可能晚一拍；
  3. 只挪视角不再触发自动保存与"未保存"标记，但相机随下一次保存落盘；
  4. 导航器小地图改为跟随 live 相机（比之前更跟手）。
- 拖动（dragElements）本批未改：它仍然逐帧写 elements，因此每帧仍会有一次 App 重绘；那是 P1-B（拖动会话临时态）的范围，本批只做基建与共享同一通道。

## Rejected alternatives

- **给工作区外壳整体加 `React.memo` + 稳定化所有 props**：App 自身函数体仍在每次相机变化时重跑，且 Toolbar/PromptBar/面板有大量内联 handler，稳定化成本高于本方案且收益不确定。
- **把手势状态放进 React Context + `useSyncExternalStore` 只订阅画布子树**：仍会因裁剪/LOD 需要而逐帧渲染整棵画布子树；本方案把"每帧都要变"（transform）与"只需偶尔变"（裁剪/LOD）分开，前者根本不进 React。
- **彻底把手势期间的画布也改成不渲染（纯 transform）**：平移超出已挂载集合会露出空白，除非预挂载全量元素，代价与资产量成正比。
- **相机写入沿用逐帧、只优化派生数据**：无法解决 App 全树重绘这个主要成本项。
- **把 pan/zoom 从 Board 移出、改为全局会话级（不持久化）**：会改变 ADR-021/ADR-023 的 camera-only 持久化语义与用户预期，本批不做。
- **拖动也一并在本批改成临时态**：回归面过大（吸附/分组/Frame/嵌套/撤销矩阵），按批次切分。

## Revisit triggers

- 需要让拖动也走同一瞬时通道（P1-B）时，复用本 ADR 的 store 与"手势结束提交一次"语义，并补拖动专属回归矩阵。
- 裁剪/LOD 的发布策略（120px / 8% / 100ms 三个数）在真机上被感知为"滞后露白"或"仍太重"时，按实际 pan 速度重新标定这三个常数，而不是改回逐帧渲染。
- 引入 WebGL 批量渲染（P3）时，相机通道可直接复用（渲染后端无关），但届时必须重新定义"裁剪集合"的所有权。
- 若出现"用户只挪视角、希望立即落盘"的需求，需要新增显式保存触发点，而不是恢复相机写入即脏的旧语义。
