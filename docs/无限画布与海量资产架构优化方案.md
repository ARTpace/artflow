## 1. 结论摘要

Artflow 当前可以作为优秀的产品与交互原型继续发展，但**不能在保持现有核心数据层和渲染层不变的情况下**稳定支撑数千至数万混合资产。

目前已有的可复用资产包括：

- 世界坐标、平移、缩放、选择、框选、套索、分组、图层、画板等交互；
- 图片、PSD、TIFF、TGA、EXR、RAW、PDF、视频、音频、3D、代码、Markdown、字体、链接与通用文件卡片；
- 视口过滤、`React.memo`、图片低/高清 LOD 的初步性能意识；
- `plugins/kernel.ts` 中的 `format_handlers`、`canvas_node_types` 等可扩展插槽雏形。

必须替换或重构的核心是：

1. **全量 React 数组状态**：不能把整块画布、历史快照、Base64 内容都放在 `Board.elements` 内；
2. **SVG/DOM-only 渲染**：不能同时保留大量 `<foreignObject>`、视频、音频播放器和 Three.js 卡片；
3. **全量扫描交互**：可见性、吸附、框选、套索、分组边界都必须改为基于空间索引的局部查询；
4. **JSON 项目文件持久化**：必须升级为“SQLite 元数据 + Blob/原文件仓库 + 派生缩略图”的本地资产库；
5. **主线程格式解析**：大文件解析、缩略图生成和元数据提取必须异步化到 Worker / utility process；
6. **组合式插件治理**：格式、卡片、面板、皮肤、命令与 AI provider 可以按 profile 组合，但不能把每帧的渲染与数据一致性基础设施变成任意插件。

## 2. 已核验的当前架构

### 2.1 运行时结构

```text
React + Vite renderer
  ├─ App.tsx / hooks/*
  ├─ SVG MainCanvas
  ├─ CanvasElement（SVG + foreignObject + React cards）
  ├─ useFileHandlers（格式判断、解析、创建画布元素）
  └─ useFileSystem（读写 artflow-data.json）

Electron
  ├─ main.cjs：BrowserWindow、trusted-storage IPC、`artflow-asset` protocol
  ├─ preload.cjs：十三个 task-specific managed-storage / preview-job / import-job / bounded-list / saved-viewport-query capability
  └─ main/projectStorageController.cjs：当前单窗口 ProjectRepository transport
```

当前已有 SQLite/blob/derivative repository、受控 Electron storage bridge，以及可恢复的 preview/import single-worker journals；R19 已在 browser 与 desktop canvas 上显示 workspace mode、project/action/status 和 current-canvas metrics，managed save 已消费 single-file import job，R18 已显示有界、脱敏的恢复/状态/cancel-request UI，R11 已降低 flat renderer interaction 的 viewport index rebuild 成本，R12 已为 saved snapshot 补上可查询 R-tree seam；仍没有完整 durable raw-file 后台资产服务、crash-safe project transaction、真实缩略图/媒体任务队列、live incremental spatial service、range streaming 或 Worker 文件服务层。

### 2.2 关键事实与瓶颈

| 位置 | 当前事实 | 海量场景影响 |
|---|---|---|
| `types.ts` | `Board` 持有 `elements: Element[]` 与 `history: Element[][]` | 每次修改与撤销历史都可能复制/保留大量数组 |
| `hooks/useCanvasState.ts` | React `useState` 保存整个 boards / elements；历史为全量数组快照 | 操作次数增加后内存、GC 与保存成本快速上升 |
| `components/MainCanvas.tsx` | R1 grid query + R11 mount-scoped flat incremental cache；相机只 query，group/structural edit 保守 rebuild | 相机不再全量扫描；R12 saved query 尚未接管 live state，仍无 group incremental propagation 或 DOM/LOD budget |
| `components/CanvasNavigator.tsx` / `utils/canvasNavigator.ts` | R20 renderer-local 240-marker overview、current viewport outline、click recenter / Fit canvas；only `updateActiveBoard` camera fields change | 不是 persistent spatial query、tile/Worker/minimap thumbnail、viewport drag/inertia 或 multi-board map |
| `storage/projectRepository.cjs` | R12 v5 saved v2 snapshot AABB metadata + SQLite R-tree，atomic save/backfill、bounded descriptor query | 不是 live operation mutation、cursor/Worker service 或 exact rotated hit-test |
| `utils/canvasUtils.ts` | group bounds 会再 `filter` 子元素 | 嵌套分组可能导致 O(n²) 计算 |
| `hooks/useCanvasInteractions.ts` | R15 flat drag snap、R16 proved-static group guides、R14 box/lasso 已复用 live index；R17 已验证优化 commit-time frame candidates | dynamic/invalid group snap 仍 full scan；frame exact parent semantics 不变 |
| `components/CanvasElement.tsx` | SVG、`foreignObject`、视频、音频、卡片、3D renderer 混合存在 | DOM、媒体解码器和 WebGL 资源无法无限挂载 |
| `hooks/useFileHandlers.ts` | 格式分支和解析逻辑集中在 renderer；图片常以 data URL 保存 | 大文件处理阻塞 UI；内容和布局耦合 |
| `hooks/useFileSystem.ts` | Electron 优先保存 managed v2 project；R18 emits safe save-job progress and polls bounded recovery summaries；R19 returns truthful save outcome for a visible Workspace panel；web 保留 JSON download fallback | managed import 仍是单次 full-buffer；没有 batch/retry、direct raw-file UI、derivative orchestration 或 project transaction recovery |
| `utils/formatDetector.ts` / `hooks/useFileHandlers.ts` | registry-first import；中心分类/parse branch 仅保留未迁移类别 fallback | R7 已禁止新增 image/document format 继续走中心 branch；后续 handler 走 contribution 契约 |
| `main.cjs` / `preload.cjs` | thirteen fixed storage / preview-job / import-job / bounded import-job-list / saved-viewport-query IPC + custom asset protocol；无 generic Node / path capability | 单窗口、full-buffer；R18 only adds bounded poll UI, still no live cursor/Worker、batch/retry/parser import、range streaming or project transaction recovery |

### 2.3 当前性能优化为何不足

现有 viewport filtering、`React.memo` 与图片 LOD 值得保留，但它们只是“减少重绘”的局部优化：

- 相机 query 已避免全量扫描，但 group/structural element update 仍需保守 full rebuild，且没有 persistent index；
- 可见 `CanvasElement` 仍接收全量 `elements`；
- SVG `<foreignObject>` 内的复杂 React 卡片并不适合大量实例；
- drag snapping 会在每个 pointer move 生成/比较其它元素的吸附点；
- 图片、原图和 data URL 跟着画布对象进入内存和 JSON 序列化；
- 视频、音频、3D 预览没有激活上限和资源回收预算。

因此“再加一点 memo 或节流”不能解决根问题。

## 3. 目标与非目标

### 3.1 产品目标

1. 无限世界坐标与平滑相机移动；
2. 同一画布容纳至少数千个资产节点，并可扩展到万级概览；
3. 支持多种格式通过可注册的 handler 接入，而不是继续扩大中心 `if/else`；
4. 原文件、元数据、缩略图、画布节点与派生数据分层持久化；
5. 导入/缩略图/元数据任务不阻塞 renderer；
6. 视频、音频、3D、Markdown 等富媒体节点按需激活；
7. 可恢复、可撤销、可增量保存，崩溃后不丢失整个项目。

### 3.2 非目标

- 不要求所有格式都能原生编辑；未知格式可以先作为可靠的文件卡片；
- 不要求第一期支持多人实时协作；
- 不要求第一期把所有低层绘制完全迁移到 WebGL；
- 不应以牺牲原文件、元数据或恢复能力来换取“看起来能导入”。

## 4. 可量化性能契约

“不卡”必须变成可测量指标。以下为建议的首期验收基线；最终阈值应在固定测试机器上通过 benchmark 校准。

| 场景 | 建议目标 |
|---|---|
| 1,000 个普通缩略图节点平移/缩放 | 连续交互期间 ≥55 FPS，主线程长任务 <50ms |
| 10,000 个轻量节点的概览视图 | 相机移动期间不全量挂 DOM；视口查询与绘制稳定 |
| 100 个可见缩略图 | 从 viewport 查询返回到首批绘制 <100ms |
| 选择/框选/套索 | 仅查询候选节点，而非扫描全库 |
| 拖拽吸附 | 在空间索引邻域内查询，单帧计算预算 <4ms |
| 单次导入 1,000 个文件 | renderer 可继续响应；后台有进度、取消与失败记录 |
| 历史记录 | 不复制整个 `Element[]`；按操作记录可逆 diff |
| 富媒体激活 | 同时运行的视频/3D/音频实例有明确上限和回收策略 |

建议从第一天起为以下指标埋点：FPS、frame time、长任务数、可见节点数、DOM 节点数、GPU/纹理预算、缩略图命中率、空间索引查询耗时、导入队列延迟、Renderer heap。

## 6. Harness 式组合层：Runtime Core 与 Plugin Boundary

### 6.1 架构决策

参考 DeepSeek Harness 的价值在于“把产品组合描述成配置树”，而不是把每一行高频代码都变成可随意替换的插件。Artflow 采用下面的边界：

```text
Profile / Patch Resolver
  → 校验 manifest、依赖图、配置 schema、resource budget
  → 生成 immutable resolved profile（可 dump）
  → 在启动时 materialize 已启用的贡献

Plugin Capability Layer
  → format handlers / canvas node cards / commands / panels / skins / AI / exporters

Artflow Runtime Core
  → camera / viewport / spatial index / renderer / LOD / operation log
  → storage protocol / worker lifecycle / IPC security / resource scheduler
```

> **规则**：一切产品能力可以组合；性能与数据正确性的基础设施不可由普通 plugin patch 替换或禁用。

### 6.2 三类能力的归属

| 层 | 典型成员 | 是否可由 profile / user patch 启停 | 约束 |
|---|---|---:|---|
| Runtime Core | camera、scene/renderer、viewport virtualization、spatial index、operation dispatcher、undo journal、storage protocol、IPC security | 否 | 必须有稳定时序、性能预算和端到端测试 |
| Builtin capability plugin | PSD/PDF/RAW handler、3D card、video card、AI provider、exporter、panel、skin | 是 | 通过 manifest、依赖、权限和 budget 校验后装载 |
| User configuration | active skin、默认格式策略、快捷键、可选面板、活跃媒体上限 | 是 | 只能覆盖已声明 schema，不能注入任意代码或关闭 core |

因此，用户可以禁用 `builtin.format-raw`、`builtin.card-model3d` 或 AI 面板，但不能用一个 patch 关闭资产事务、空间索引、基础 renderer 或安全 IPC。

### 6.3 Manifest、profile 与 patch

现有 `plugins/kernel.ts` 的 `format_handlers`、`canvas_node_types`、`ui_panels`、`skins` 等 slot 应保留，并升级为可验证的 manifest 驱动组合。

```ts
interface ArtflowPluginManifest {
  id: string;
  version: string;
  host: 'worker' | 'renderer' | 'main';
  requires?: readonly string[];
  optionalRequires?: readonly string[];
  capabilities: readonly (
    | 'format.handler'
    | 'canvas.card'
    | 'ui.panel'
    | 'ui.skin'
    | 'command'
    | 'ai.provider'
    | 'exporter'
  )[];
  contributions: Record<string, unknown>;
  configSchema?: unknown;
  resourceBudget?: {
    maxActiveInstances?: number;
    maxMemoryMB?: number;
    maxConcurrentJobs?: number;
  };
}
```

建议的层叠优先级：

```text
base profile
  < mode profile（desktop / creative / media-review / minimal）
  < machine or workspace policy
  < user patch
  < temporary CLI / debug patch
```

每层都通过 plugin id 定位；后层只能覆盖该插件已声明的配置字段与 enabled/disabled 状态。解析器必须：

1. 校验 schema、重复 id、未知字段和依赖环；
2. 对禁用但被必需依赖引用的插件报出可读错误；
3. 生成不可变 resolved profile；
4. 提供 `artflow --dump-profile` 或诊断页面，显示最终启用的插件、来源层、版本、依赖与 resource budget；
5. 在启动时完成组合，不允许在 render / pointermove 热路径中反复查询 registry 或合并 patch。

### 6.4 性能热路径禁区

以下逻辑不得变成每帧动态 plugin dispatch：

- Camera 更新、viewport diff、空间索引查询；
- pointermove、hit test、snap candidate 查询；
- Canvas2D/WebGL batch draw 与纹理淘汰；
- operation commit、undo/redo 与 storage transaction；
- renderer / worker 的 IPC schema 验证与权限边界。

插件的 renderer contribution 应在启动时 materialize 成受控 descriptor；Runtime Core 根据 node type、LOD 与资源预算决定它是低清 draw call、静态缩略图、DOM card，还是可激活富媒体实例。插件不能自行绕过 virtualization 或无限创建 video / WebGL / DOM 实例。

### 6.5 信任分级与 Cordis 采用策略

DeepSeek Harness 把 npm package 当作插件包的做法适合成熟生态；Artflow 应分级演进：

| 阶段 | 允许的插件 | 运行策略 |
|---|---|---|
| v1 | 同仓 builtin、可信代码 | 当前轻量 kernel 足够，先完成 manifest 与 profile resolver |
| v1.5 | 内置 profile / user patch | 只切换声明式配置和 builtin contributions |
| v2 | 审核或签名的 package plugin | Worker / renderer 分 host 装载，严格版本与权限校验 |
| v3 | 第三方富 UI / parser | parser 放隔离 worker；UI 放受限 iframe / declarative card，不能获得 generic Electron 或 Node 能力 |

不应仅因为 dsh 使用 Cordis 就立即重写 Artflow 的 mini kernel。当前最紧急的是冻结 contracts、建立 storage/render runtime 和 benchmark；当插件依赖图、service scope、异步激活和外部生态确实需要时，再将**组合控制面**迁移到 Cordis，而不把 Cordis 调用放进 renderer 热路径。

## 7. 数据模型与持久化

### 7.1 资产与画布节点分离

不要把二进制内容、data URL 和位置数据混在同一个 `Element` 对象中。

```ts
interface AssetRecord {
  id: string;
  sourceKind: 'managed-copy' | 'external-reference';
  originalRef: string;       // content hash 或受控外部路径引用
  mimeType: string;
  extension: string;
  byteSize: number;
  contentHash?: string;
  metadata: Record<string, unknown>;
  previewState: 'pending' | 'ready' | 'failed' | 'unsupported';
  createdAt: number;
  updatedAt: number;
}

interface BoardNodeRecord {
  id: string;
  boardId: string;
  assetId?: string;
  nodeType: string;
  x: number;
  y: number;
  width: number;
  height: number;
  rotation: number;
  zIndex: number;
  parentId?: string;
  properties: Record<string, unknown>;
  updatedAt: number;
}
```

画布只持有轻量 node；节点通过 `assetId` 关联文件。预览、原图、缩略图、派生音频波形、PDF 首页等均作为 asset derivative 管理。

### 7.2 建议持久化表

```text
assets
asset_derivatives            # thumbnail / poster / waveform / extracted text
boards
board_nodes
board_node_bounds            # R-tree / 空间索引辅助表
board_edges                  # 可选：连线或关系
operations                   # 可撤销操作日志 / autosave journal
import_jobs
format_handler_state         # 可选：解析器版本与失败状态
```

### 7.3 内容存储原则

- 原文件不转为 Renderer 的 Base64；
- 小型派生缩略图可以缓存，但不塞进 React 全局 state；
- 使用内容哈希避免重复文件占用；
- 支持两种导入模式：托管拷贝、受控外部引用；
- 项目保存只写 metadata / layout / operation journal，不能把全量原始媒体重新 JSON 化；
- 文件访问通过 capability-limited IPC，不暴露通用 Node / filesystem 能力给 renderer。

## 8. 空间索引与视口查询

### 8.1 必须替代的模式

R1 / R11 live 当前模式：

```ts
const index = viewportIndexCache.update(elements);
const visible = index.query(viewport, { includeElementIds: selectedIds });
```

R14 live interaction seam（已验证；只缩小候选，保留精确选择判断）：

```ts
const candidates = queryInteractionCandidates(interactionIndexRef.current, elements, selectionRect);
const selected = candidates.filter(existingExactSelectionPredicate);
```

R12 / R13 saved-snapshot seam（非 live UI API）：

```ts
const nodes = [];
let page = await window.artflowStorage?.queryViewport({ boardId, rect, limit: 500 });
while (page) {
  nodes.push(...page.nodes);
  if (!page.nextCursor) break;
  page = await window.artflowStorage?.queryViewport({ boardId, rect, limit: 500, cursor: page.nextCursor });
}
// Pages share a saved revision; stale cursors restart rather than replace unsaved live elements.
```

R14 does not call this saved-snapshot API from selection interaction. R15 / R16 do not call it from drag snapping, and R17 does not call it from frame-parent commit: live state needs the renderer snapshot, not saved viewport rows. R17 only narrows candidates under the same-elements identity gate, then preserves exact containment and the pre-existing frame comparator; stale/null reader full-scans current elements. Remote foundation verifies R14 freshness plus R15 rank/tie/strict, R16 group-dependency fallback and R17 parent-result equality. 10k synthetic benchmarks only record exact candidate/result equality and current-run data, not a general FPS promise。

目标模式：

```ts
const page = await canvasApi.queryViewport({
  boardId,
  worldRect,
  lod,
  cursor,
});
```

### 8.2 索引策略

1. **持久索引**：SQLite 中为 node 的 AABB 建立 R-tree 或等价空间索引；
2. **运行时索引**：当前 board 的已加载节点维护 uniform grid、R-tree 或 quadtree；
3. **旋转节点**：先用 AABB 取得候选，再做精确 hit test；
4. **分组**：维护 parent/children map 与缓存 bounds，不能每次递归 `filter` 全量数组；
5. **吸附**：索引边、中心点、基线；拖动时只查询阈值邻域；
6. **选择/套索**：先按 selection rect 查询候选，再对候选做几何计算。

### 8.3 视口缓存

- 以 board + tile / world-region 为缓存键；
- camera 移动时预取当前视口外一圈；
- 节点更新只失效受影响 region；
- 远距离只请求聚合信息或低 LOD representation；
- 不在 renderer 中永久缓存整个万级 board 的富媒体内容。

## 9. 渲染策略：Hybrid Canvas

### 9.1 分层

```text
Layer A：Canvas2D / WebGL
  - 背景、网格
  - 远距离节点占位
  - 缩略图、简单图片、形状、边、连接线
  - 批量绘制与 texture atlas

Layer B：React / DOM overlay
  - 当前选中、hover、编辑中的节点
  - Inspector、toolbar、context menu
  - 少量激活的视频、音频、3D、Markdown、Code 卡片
```

### 9.2 LOD 规则

| LOD | 示例呈现 | 资源规则 |
|---|---|---|
| LOD0：极远 | 色块、类型图标、聚合计数 | 不加载缩略图和 DOM 卡片 |
| LOD1：远 | 小缩略图 / 简单标签 | 低分辨率 derivative |
| LOD2：中 | 标准缩略图、名称、基本状态 | 批量 Canvas/WebGL 绘制 |
| LOD3：近 | React 交互卡片 | 仅 viewport 内有限数量 |
| LOD4：激活 | 视频播放、音频、3D、编辑器 | 有上限、离开视口即暂停/销毁 |

### 9.3 富媒体预算

必须定义硬预算，例如：

- 同时播放的视频数量；
- 同时保留的 WebGL/Three.js viewer 数量；
- 活跃音频 player 数量；
- DOM 卡片最大数量；
- 缩略图显存 / texture atlas 预算；
- 超出预算时的降级顺序。

没有预算时，单个 3D 或视频节点也许可用，但多个节点会把性能与稳定性拖垮。

## 10. 交互与状态管理

### 10.1 临时态与提交态分开

拖动、缩放、旋转过程中：

- 只更新 transient interaction state；
- 使用 `requestAnimationFrame` 合并 pointer updates；
- 从空间索引查询附近 snap candidates；
- 不在每次 pointer move 创建整块 `Element[]` 的新数组；
- 鼠标抬起后提交一条 `moveNodes` / `resizeNodes` operation。

### 10.2 操作日志替代全量历史快照

```ts
interface CanvasOperation {
  id: string;
  boardId: string;
  kind: 'create' | 'move' | 'resize' | 'delete' | 'update' | 'group' | 'ungroup';
  before: unknown;
  after: unknown;
  createdAt: number;
}
```

Undo / redo 保存最小 reversible diff，而不是保存 `Element[][]`。批量导入和自动布局应为单个事务操作，避免产生数千条独立历史记录。

### 10.3 数据访问形态

Renderer store 推荐拆为：

```text
camera state              # 高频、短生命周期
selection / hover state   # 高频、短生命周期
viewport node cache       # 按 region / cursor 管理
node entity map           # normalized、按 id 更新
asset metadata cache      # normalized、惰性加载
UI panels / settings      # 普通 React state
```

禁止让“所有 board nodes + 原始文件内容 + 所有 undo snapshots”进入一个 React state atom。

## 11. 格式插件架构

### 11.1 现状到目标

现有 `plugins/kernel.ts` 已声明 `format_handlers` 插槽，但目前 `utils/formatDetector.ts` 与 `hooks/useFileHandlers.ts` 仍是中心硬编码分支。

迁移目标是让每种格式声明自身能力：

```ts
interface FormatHandler {
  id: string;
  pluginId: string;
  host: 'worker'; // 解析、metadata 与 preview 一律不堵塞 renderer
  priority: number;
  extensions?: readonly string[];
  mimeTypes?: readonly string[];

  sniff(input: AssetProbe): Promise<boolean>;
  extractMetadata(input: AssetSource): Promise<Record<string, unknown>>;
  createPreview(input: AssetSource, request: PreviewRequest): Promise<PreviewResult>;
  createNodeDraft(asset: AssetRecord): Promise<BoardNodeDraft>;
  rendererKind(asset: AssetRecord, lod: number): 'thumbnail' | 'card' | 'media' | 'file';
}
```

### 11.2 导入流程

```text
文件选择 / 拖放
  → 轻量 sniff
  → 创建 AssetRecord（pending）
  → 后台格式 handler job
  → metadata / thumbnail / derivative
  → 写入存储
  → renderer 收到 asset-ready 事件
  → 当前画布生成或更新轻量 BoardNode
```

### 11.3 降级原则

- 格式未知：创建通用文件卡片；
- 解析失败：保留原文件与错误状态，不丢资产；
- 不支持预览：显示类型图标、大小、名称、可打开入口；
- 大型格式：先显示 placeholder，再异步生成 preview；
- 外部插件：先以受限、声明式贡献为主，不给 renderer 通用 Node 权限。

## 12. 后台任务与 Electron 边界

### 12.1 需要新增的后台任务

- 文件复制 / 哈希；
- MIME / signature sniff；
- EXIF / 元数据读取；
- 缩略图与多级 preview 生成；
- PDF poster、音频波形、视频 poster、3D poster；
- PSD / RAW / EXR / TIFF 等昂贵解析；
- 搜索索引与空间索引维护；
- 清理未引用 derivative 与缓存。

### 12.2 进程原则

- Renderer 不直接打开 SQLite、不解析大文件、不保留原始大媒体；
- Main 不持有数据库驱动，只作为受限 broker；
- 数据库和资产任务放入 Library Worker / Electron utility process；
- worker 与 main 的消息必须 schema-validated、请求可取消、具备进度与失败码；
- preload 只暴露具体能力，例如 `assets.import`、`canvas.queryViewport`、`canvas.commitOperation`，不暴露 generic IPC。

## 13. 分阶段迁移路线

### Phase 0：基线与护栏

**目标**：先把性能问题量化，避免盲目重写。

- 增加 1k / 5k / 10k synthetic node fixtures；
- 记录相机移动、吸附、框选、套索、导入的性能 profile；
- 建立 DOM 节点数、long task、heap、FPS 的开发诊断面板；
- 明确 benchmark 机器、浏览器 / Electron 版本与阈值；
- 修复当前 smoke / test 基础，防止性能工作没有回归门禁；
- 写出 Runtime Core / Plugin Capability / Profile Patch 三层 ADR，并冻结“热路径禁区”。

**完成标志**：可以重复比较优化前后的 frame time、内存和查询耗时；任何后续插件设计都不能绕过热路径与安全边界。

### Phase 0.5：组合控制面

**目标**：先把 DeepSeek Harness 式组合能力落在声明与诊断层，而不是抢先重写所有运行时。

- 定义 `ArtflowPluginManifest`、profile schema、patch schema 与依赖图校验；
- 将现有 builtin cards / skins 纳入 manifest；
- 实现按 id 的 enabled/disabled 与覆盖优先级；
- 输出 resolved profile，提供诊断页面或 `--dump-profile`；
- 保持 Runtime Core 固定，禁止 patch 替换 renderer、storage、spatial index 和 IPC security。

**完成标志**：同一插件池可以形成不同 product profile，且最终配置可复现、可解释、可测试。

### Phase 1：数据模型解耦

**目标**：不改变主要 UI，先让“资产”和“节点”分离。

- 引入 `AssetRecord`、`BoardNodeRecord`、`CanvasOperation`；
- 将 data URL 从长期 board state 中移除；
- 现有格式卡片改为读取 asset reference；
- 历史记录从 `Element[][]` 迁移为 operation diff；
- 提供旧 `artflow-data.json` 到新 schema 的一次性迁移器。

**R2 / R3 已验证的最小边界**：operation journal 已替代 `Element[][]`；新 save 已输出 `artflow-project` v2，AssetRecord 与 BoardNodeRecord 在 persisted schema 中分离，legacy `Board[]` 可读取。Asset locator 仍可能是 data URL / blob URL / 外部 URL，Renderer 仍投影为 `Element[]`；这不是 binary store，也尚未满足最终“JSON 不再嵌入原始媒体”的完成标志。

**最终完成标志**：大项目 JSON 不再嵌入原始媒体，undo/redo 不再复制全量画布。

### Phase 2：本地资产库与后台 Worker

**目标**：建立可靠持久化和异步导入基础。

- SQLite 元数据与 layout；
- 原文件 / derivative store；
- Electron main ↔ worker ↔ renderer 的受限 IPC；
- 导入队列、任务进度、取消、失败重试；
- viewport query、cursor / region cache API。

**R4 / R5 / R6 / R8 / R9 / R10 / R12 / R13 / R18 已验证的最小边界**：Node-side `ProjectRepository` 已在项目私有 `.artflow/` 中建立 SQLite asset metadata、SHA-256 immutable original blob tree、managed v2 snapshot 与 read-time hash validation；schema v2 将 completed derivative 存入独立 SHA-256 tree 并以 `(asset_id, recipe)` metadata 映射，schema v3 在同一 SQLite 内持久化 derivative job intent/outcome，schema v4 在同一 SQLite 记录 sanitized raw import job intent/outcome 并将 raw bytes stage 到 project-private content-addressed tree，schema v5 从 saved v2 nodes 原子重建 AABB metadata + SQLite R-tree projection，schema v6 为该 projection 增加同 transaction advance 的 revision 和 keyset cursor consistency。Electron 通过 thirteen fixed preload operations、trusted main-frame IPC 和 `artflow-asset` protocol 接入；R18 `listImportJobs` 只返回最多 25 个 active-first/recent-terminal safe summaries，仍不暴露 path/SQL/raw bytes。managed save 会将 data/blob asset bytes 以 request/get/cancel 消费 single-file import job 的 completed result，并向 managed-only UI 观察者报告状态；renderer 不获得 staging path/hash。`AssetDerivativeController` 与 `AssetImportController` 各保持 single-worker FIFO；queued/stale-running journal 在 reopen 时重排，explicit cancel 与 controller close 区分，main/repository 是唯一 writer。该路径仍为单窗口、full-buffer transfer，没有 batch/retry/parser raw import、live incremental spatial mutation/cursor/Worker、真实 raster/media derivative、range streaming、GC 或 project transaction recovery。

**最终完成标志**：重启应用后可恢复大项目，导入大文件不冻结 UI。

### Phase 3：空间索引与 Hybrid Renderer

**目标**：解决数千节点的交互与渲染瓶颈。

- R-tree / grid 查询；
- 视口虚拟化；
- Canvas2D 或 WebGL base layer；
- React DOM overlay；
- LOD、texture / media budget；
- 所有选择、套索、吸附改为候选集查询。

**完成标志**：10k 轻量节点概览可持续平移缩放，复杂卡片按需激活。

### Phase 4：格式插件化

**目标**：把硬编码格式分支迁移为可注册 handler。

**R7 / Plugin P0（已验证）**：已冻结 `FormatHandler` / ParseResult contract、minHostVersion、stable priority dispatch 和 conflict candidate enumeration，并把 PSD/PDF/audio/image family 移到 `builtin/formats-image-doc`。这是插件化的最小纵切，不实现漫画/小说、PanelHost、external plugin 或 media Worker。

- 落地 `FormatHandler` 契约，并作为 `format_handlers` slot 的唯一消费入口；
- 将 Phase 0.5 的 base / desktop / creative / media-review / minimal profile resolver 扩展到所有 format contribution，并保持 resolved profile 可 dump；
- 先迁移现有 image / PDF / audio / video / 3D / generic file handlers；
- 为 PSD、RAW、TIFF、EXR 设定后台解析与 preview 策略；
- handler version、失败状态和降级结果可持久化；
- 对 node card、panel、format handler 强制声明 host、权限、依赖和 resource budget；
- 为未来第三方插件增加权限、隔离和签名设计。

**完成标志**：新增格式不需要修改中心导入分支。

### Phase 5：压测与产品硬化

**目标**：把“可演示”提升为“可长期使用”。

- 1k / 10k / 50k 节点 benchmark；
- 混合媒体压力测试；
- 低内存、GPU 不可用、缩略图失败、损坏文件、网络盘等降级测试；
- autosave / crash recovery；
- 迁移、备份、数据清理与可观测性。

## 15. 技术决策原则

### 15.1 Canvas2D 与 WebGL

- 首期可先采用 Canvas2D 做批量缩略图与简单形状层，降低改造风险；
- 当 10k+ 视口节点、texture atlas、复杂缩放成为瓶颈时，再升级 WebGL；
- React DOM 仍用于可编辑、可访问、富交互的小集合，不与 WebGL 对立。

### 15.2 SQLite 与文件仓库

- SQLite 只存 metadata、关系、layout、索引与操作日志；
- 大二进制文件、原图和 derivative 不应膨胀数据库表；
- 文件仓库可按 hash 分层存储，支持去重、清理和备份；
- 数据库 schema 演进要有迁移与备份机制。

### 15.3 第三方格式插件

- 先支持内置可信 handler；
- 后续第三方 handler 不应获得无边界 filesystem、database 或 Electron IPC；
- handler 以声明格式能力、请求受控 source handle、返回结构化结果为主；
- 不允许 renderer 侧插件自行 import 原生驱动或长期占用媒体资源。

## 16. 风险与降级

| 风险 | 处理策略 |
|---|---|
| RAW/EXR/PSD 等解析耗时或失败 | 后台 job、placeholder、失败状态、保留原文件和通用卡片降级 |
| 大量视频/3D 节点耗尽资源 | 激活预算、离屏暂停、近距离才启动、poster 降级 |
| 旧 JSON 项目巨大或包含 data URL | 一次性迁移工具、分批导入、导入前备份 |
| 空间索引与实际节点不一致 | 所有 node mutation 经统一 operation pipeline；事务内同时更新 record 与 bounds |
| 复杂 group / frame 语义 | parent-child map、缓存 bounds、明确 invalidation 规则 |
| 把所有能力都插件化导致帧预算失控 | 固定 Runtime Core；禁止热路径动态 plugin dispatch；通过 LOD 与 resource budget materialize contribution |
| profile / patch 产生隐式覆盖或依赖环 | schema 校验、id 唯一性、拓扑解析、resolved profile dump、来源追踪与冲突错误 |
| 过早引入过多框架 | 先冻结 domain contracts 和 benchmark；保留轻量 kernel，Cordis 仅在组合控制面确有需要时引入 |
| Electron 安全边界被破坏 | contextIsolation 保留；preload 最小能力暴露；无 generic IPC、无 renderer Node access |

## 17. 开工前的验收问题

开始代码迁移前，至少确认：

1. 资产是否默认复制到项目库，还是允许外部引用？
2. 是否需要离线优先、项目备份与跨机器迁移？
3. 目标规模是“数千个可见缩略图”还是“数万节点概览、数百个可见缩略图”？
4. 3D、视频、PDF 是预览、播放还是可编辑工作区？
5. 是否计划第三方格式插件，及其安全边界？
6. 是否需要未来协作 / CRDT；若需要，operation model 要提前保持可序列化与可重放。

## 18. 当前推荐的第一件工程工作

不要立刻把所有 SVG 改成 WebGL。Phase 0、0.5、1a、1b、2a、2b、2c、2d durable derivative journal/recovery、2e raw import staging/single-file recovery、2f managed-save job consumption、3a incremental viewport cache 与 3b saved-snapshot persistent spatial query 已完成；Plugin P0 `format_handlers` registry 已完成。不得重建 storage schema、durable journals、R11/R33 live cache、R12 snapshot R-tree 或 R13 cursor consistency；R17 的 frame-parent candidate narrowing、R18 bounded durable import jobs UI 与 R33 Group incremental propagation 已验证收束；其后才根据新 FDD 进入 hit-test/live mutation/cursor cache/Worker、Hybrid renderer、transaction/batch/retry/parser import 或 Plugin P1。以下是原始路线清单，其中已完成的部分不得重复实现：

1. 写出 Runtime Core / Plugin Capability / Profile Patch ADR，并明确哪些服务不可被用户 patch 禁用；
2. 建立 1k / 10k synthetic node benchmark；
3. 为现有 `Element` 增加可迁移的 asset reference 形态；
4. 将单次拖拽改为“临时 interaction state + 最终 operation commit”；
5. 抽出 viewport query 接口，即便第一版底层仍临时扫描数组；
6. 落地最小 profile resolver，让内置 skin / card / format handler 都能通过 manifest 组合；
7. 让现有 `format_handlers` 真正成为导入路由的唯一入口。

这样可以先锁定未来架构边界，同时保留当前 UI 与已有格式能力，再逐步接入 SQLite、后台任务、空间索引和 Hybrid Renderer；当组合复杂度真实达到需要时，再把控制面演进到 Cordis。
