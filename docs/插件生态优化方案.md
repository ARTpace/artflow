# 插件生态优化方案（对标 Obsidian）

> 状态：方案待评审 ｜ 2026-10-11
> 关联文档：《插件系统设计》《插件平台V2开发规格与迁移路线》《皮肤系统升级开发文档》
> 关联代码：`plugin-runtime/kernel.ts`（插槽表）、`plugin-runtime/manifest.ts`（内部清单）、`sandbox/module-table.cjs`（沙箱契约）、`main/sandboxedPlugins.cjs`（外部清单）

---

## 0. 一句话结论

对标 Obsidian 后可以确认：**artflow 现在缺的不是语言能力（加不加 Python 都一样），而是三件东西——**

1. **一层「插件能安全摸到的宿主对象」**（Obsidian 是 `this.app.vault / workspace / metadataCache`）；
2. **一套「准入 + 披露 + 扫描」的分发治理**（Obsidian 是 Restricted mode + 社区插件目录 + 安全评分）；
3. **一条「别的生态的插件能低成本搬过来」的通道**（Obsidian 插件产物里保留着字面量 `require("obsidian")`，这让「同名 shim 接管 API」在技术上成立，见 §6）。

Obsidian 恰好同时给出了这三件事的做法，而且**都不需要动摇现有信任模型**。本方案分四刀：A `ArtflowHost` facade → B 声明式 UI schema → C 分发治理 → D Obsidian 移植通道（D 是贯穿前三个的横向目标，见 §6）。

> 第 3 条是本次新增的设计目标（用户要求「改完之后，后续很容易把 Obsidian 的插件转成我的插件」）。它反过来把 A 和 B 的技术要求定得更死了：**凡是 Obsidian 有、我们没有的管道，都必须补成同名同语义**，否则 shim 接不上。§6.3 给出了必须补齐的清单与优先级，来自本机 45 个真实插件的实测统计。

## 1. 现状盘点（先确认基准事实）

### 1.1 四条插件通道

| 通道 | `runtime.mode` | id 规则 | 谁能写 | 运行方式 | 权限 |
|---|---|---|---|---|---|
| 内置 | `builtin` | `builtin.*` | 我们自己 | 编译进本体（TS） | 全权 |
| 可编辑 | `editable` | `builtin.*` | 我们自己 | 受信求值 `Artflow.*` | 全权 |
| 声明式 | `declarative` | 无限制 | 第三方 | 纯 JSON，零代码 | 无代码 = 无权限 |
| 沙箱 | `sandboxed` | 必须 `local.*` | 第三方 | V8 受限上下文，锁死 20 个全局 | 7 个能力面 |

> `runtime.mode` 的联合类型见 `plugin-runtime/manifest.ts:107`：`'builtin' | 'declarative' | 'editable'`。
> **注意 `sandboxed` 不在这里** —— 见 1.3 的发现。

### 1.2 现有契约面

**15 个插槽**（`plugin-runtime/kernel.ts:12`，写死在类型里，第三方无法新增）：

```
skins · locales · canvas_node_types · format_handlers · ai_providers · asset_sources
commands · node_actions · ui_panels · canvas_widgets · canvas_overlays
settings_sections · ui_toolbar · ui_menus · hooks
```

**11 项能力声明**（`manifest.ts:18`，用于安装时向用户展示 + 依赖校验）：

```
format.handler · canvas.card · ui.panel · ui.settings · ui.menu · ui.skin
command · ai.provider · asset.source · node.action · exporter
```

**沙箱 7 个能力面**（`sandbox/module-table.cjs:83-144`，第三方实际能调的全部）：

| 能力面 | 做什么 | 局限 |
|---|---|---|
| `formats` | 注册文件格式解析 | 只能登记，拿不到文件对象 |
| `commands` | 注册命令 | 只能登记 |
| `panels` | 注册面板 | **只能塞裸 HTML 字符串（≤8000 字符）** |
| `cards` | 注册自定义卡片 | 4 种返回类型 |
| `assets` | 注册资产源 | 只能登记 |
| `files` | 受控读写 | 限定受信目录 |
| `net` | 网络请求 | 由主进程代劳 |

### 1.3 顺带发现的两个结构性问题

**问题 A：清单契约有两套，且字段集不一致。**

| | 内部（`manifest.ts`） | 外部（`main/sandboxedPlugins.cjs:17`） |
|---|---|---|
| 允许字段 | `manifestVersion / id / version / minHostVersion / name / nameI18n / description / category / sourceDir / author / license / host / runtime / requires / optionalRequires / capabilities / configSchema / resourceBudget / mcp` | `id / name / version / runtime / description / permissions / capabilities` |
| 校验方式 | TypeScript 类型 + 运行时严格校验，**未知字段一律拒绝** | 手写白名单 `ALLOWED_KEYS` |
| 依赖声明 | 有 `requires` / `optionalRequires` | **没有** |
| 版本门 | 有 `minHostVersion` | **没有** |
| 权限 | 无 `permissions` 字段 | 有 `permissions` |

也就是说：**第三方插件无法声明依赖、无法声明最低宿主版本、无法被依赖冲突机制保护**——这三样在内部通道都有，外部通道全缺。第三方插件目前的"隔离度"是更高了，但"可管理度"比内置插件低一档。

**问题 B：`minHostVersion` 存在但没有对外生效。**（来自问题 A 的连带：外部清单根本不解析这个字段。）

## 2. 对标 Obsidian：哪些该抄、哪些不该抄

| 维度 | Obsidian 做法 | 对 artflow 的判断 |
|---|---|---|
| **宿主对象访问** | `this.app` 类型化 facade → `Vault / Workspace / MetadataCache / FileManager`；可 `app.vault.read(file)`、`workspace.getActiveViewOfType(MarkdownView)`、`registerEditorExtension()` 塞原生 CM6 扩展 | ✅ **最该抄**。受控、有类型、有版本门的对象图，而非把内部结构全摊开。与现有沙箱不冲突（每个方法都可在主进程校验） |
| **生命周期回收** | `Plugin extends Component`，`addCommand / addRibbonIcon / addSettingTab / registerEvent / registerDomEvent / registerInterval` 由基类**隐式记账**，卸载统一撤销 | ⚙️ **已有等价物**。我们用「返回 disposer」显式契约，更强（能防同 id 互删）。可补一组 `register*` 辅助方法降低第三方漏返回的概率 |
| **SDK 分发** | npm 包 `obsidian`，内容基本就是一份 `obsidian.d.ts` | ✅ **已对齐**。`types/artflow-plugin.d.ts` 是同一个动作（0.1.8 已落地） |
| **设置界面** | `addSettingTab()` + `Setting` 声明式控件 API，宿主负责渲染 | ✅ **该抄**。直接解掉「面板只能塞 8000 字符 HTML」这个手感瓶颈 |
| **清单规则** | `id` 只允许小写字母和连字符、不能含 `obsidian`、不能以 `plugin` 结尾、**必须等于文件夹名** | ⚙️ 我们的 `^[a-z0-9][a-z0-9_-]*\.[a-z0-9][a-z0-9_.-]*$` 已足够；「id 必须等于文件夹名」这条值得抄（见 5.2） |
| **插件位置** | 装在 `<库>/.obsidian/plugins/`——**跟着库走** | ❌ **别抄**。开一个共享库就带进别人的代码。我们放 `<userData>/plugins/` 更安全。它这么设计是为了多设备同步，我们已有 profile JSON 管状态 |
| **安全模型** | 官方明确承认「**做不到隔离**」（插件同 JS realm，能 `require('fs')`/`child_process`），于是把风险转移到**分发治理**：Restricted mode 默认关 + 人工/机器人审查 + 自动扫描 + 安全评分卡 | ✅ **第二该抄**。在承认沙箱覆盖不到的地方，用治理补位 |
| **插件更新** | Release tag 必须**精确等于** manifest 的 version（无 `v` 前缀）；release 资产只允许 `main.js` + `manifest.json` + `styles.css`；`versions.json` 做版本门 | ✅ 值得抄，用于将来的插件目录 |

## 3. 方案 A（P0）：`ArtflowHost` facade

### 3.1 设计原则

1. **受控对象图**：暴露的是 facade，不是内部对象。插件拿不到 `board.elements` 的原始引用，只能通过方法读写。
2. **每方法带权限校验**：调用前查插件的 `permissions`，越权即拒绝并记录。
3. **版本门**：facade 每个命名空间带 `since` 版本号，与 `minHostVersion` 比对。
4. **只读优先**：`assets` / `collections` 默认只读；写操作要显式声明权限（`assets.write`）。
5. **对齐 disposer 契约**：所有 `on*` 订阅返回 disposer，语义与现有 kernel 一致。

### 3.2 接口草案

```ts
// types/artflow-plugin.d.ts 追加
declare namespace Artflow {
  /** 沙箱插件第 8 个能力面：host（受控宿主对象图） */
  interface HostApi {
    readonly meta: { pluginId: string; hostApiVersion: string };

    /** 资产库（默认只读） */
    readonly assets: {
      list(): Promise<AssetRef[]>;
      get(id: string): Promise<AssetRef | null>;
      /** 需权限 assets.write */
      updateTags(id: string, tags: string[]): Promise<void>;
    };

    /** 当前画布（默认只读） */
    readonly board: {
      snapshot(): Promise<BoardSnapshot>;
      selection(): Promise<BoardElementRef[]>;
      /** 需权限 board.write */
      move(ids: string[], delta: { x: number; y: number }): Promise<void>;
      /** 需权限 board.write */
      remove(ids: string[]): Promise<void>;
    };

    /** 收藏与分组（默认只读） */
    readonly collections: {
      list(): Promise<CollectionRef[]>;
      /** 需权限 collections.write */
      add(collectionId: string, assetId: string): Promise<void>;
      /** 需权限 collections.write */
      remove(collectionId: string, assetId: string): Promise<void>;
    };

    /** 变更订阅，返回 disposer */
    readonly events: {
      onAssetsChanged(cb: (ev: AssetsChangedEvent) => void): Disposer;
      onBoardChanged(cb: (ev: BoardChangedEvent) => void): Disposer;
    };

    /** 声明式设置界面（见方案 B） */
    readonly ui: {
      registerSettingsTab(tab: SettingsTabSpec): Disposer;
    };
  }
}
```

接入方式：`Artflow.modules.definePlugin((api) => { api.host.assets.list()... })`——即第 8 个能力面 `host`，与现有 7 面并列，**不动现有 7 面的任何语义**。

### 3.3 权限模型

把现有两处拼起来：

- 内部清单的 `capabilities: PluginCapability[]`（11 项，用于分档展示）；
- 外部清单的 `permissions`（`main/sandboxedPlugins.cjs` 已在解析、安装时会弹授权框）。

新增一组 **host 权限**（细粒度、可带作用域）：

```
assets.read · assets.write
board.read  · board.write
collections.read · collections.write
files.read@<目录> · files.write@<目录>
net@<域名白名单>
```

**规则**：manifest 未声明 → 方法调用直接抛 `PermissionDenied`。这比 Obsidian 强（它承认做不到），因为我们的 facade 是**唯一入口**——插件没有别的路径摸到 `board.elements`。

### 3.4 与现有七能力面的关系

| | 七能力面 | 新增 `host` 面 |
|---|---|---|
| 方向 | **登记**（我提供一个命令/面板/格式） | **读取/操作**（我拿到画布状态并改它） |
| 粒度 | 条目级 | 对象级 |
| 是否需要沙箱改造 | 否 | 否（每方法在主进程/宿主校验） |

一句话：**七面是"投稿"，`host` 面是"拿到编辑权限"。** 两者正交，可并存。

### 3.5 实施步骤与工作量

| 步骤 | 内容 | 涉及文件 |
|---|---|---|
| A1 | 定义 `HostApi` 类型 + `since` 版本字段 | `types/artflow-plugin.d.ts` |
| A2 | 在 `module-table.cjs` 冻结上下文里加第 8 面（先只暴露 `assets.list/get` + `events`） | `sandbox/module-table.cjs` |
| A3 | 主进程实现 RPC 方法（`host:call` 通道）+ 权限校验 + 目录作用域校验 | `main/sandboxedPlugins.cjs`、`main.cjs`、`preload.cjs` |
| A4 | manifest 统一：外部清单支持 `requires` / `minHostVersion` / `permissions`（合并问题 A） | `main/sandboxedPlugins.cjs` |
| A5 | 示例 + 文档：`examples/local.asset-rename` 升级为用 `host` 面；《插件开发指南》加一节 | `examples/`、`builtin-plugins/ui-plugin-manager/dev-guide.tsx` |
| A6 | 守卫：断言 `host` 面只在声明权限后可达 | `scripts/check-plugin-openings.cjs` |

估算：**A1~A3 约 300~400 行**（不含 A4/A5）。不碰渲染层，不动信任模型。

### 3.6 实施状态（2026-10-11 已落地 A1~A4）

| 文件 | 改动 |
|---|---|
| `sandbox/module-table.cjs` | 第 8 面 `host`（`meta` + `assets.list/get/rename`）。宿主信封（`{assets}` / `{asset}`）在沙箱侧剥掉，插件看到的是 `AssetRef[]` |
| `sandbox/guest.js` | 注入宿主 API 版本；`console.*` 转发回主进程 —— 沙箱窗口是隐藏的，不转发就没有任何插件输出可见 |
| `main/hostFacade.cjs`（新） | 命名空间目录 + 逐方法权限校验 + 参数归一化。**`assets` 在主进程闭环**（`storageController` 本就在主进程，不必绕渲染层多一跳） |
| `main/sandboxedPlugins.cjs` | `permissions.host` 封闭白名单、`minHostVersion`、`requires`；`host` op 分发；`hostCompatible` 标记；host 权限进 `permissionLabels` |
| `main/pluginSandboxHost.cjs` | 注入 `storageController`；激活时做版本门（不兼容 → 明确报错，而不是静默消失） |
| `main.cjs` | 授权框文案改为「额外权限」，并让**只声明 host 权限的插件也弹确认**（否则用户对"这插件能改我的资产名"毫不知情） |
| `types/artflow-plugin.d.ts` | `HostApi` / `HostAssetsApi` / `AssetRef`；清单的 `permissions.host`、`minHostVersion`、`requires` |

**与 3.2 草案的两处偏离**（核实宿主能力后改的）：

1. **`assets.updateTags` → `assets.rename`**：宿主只有资产**改名**能力，没有 tags 概念。凭空造一个 tags API，插件作者写完后会发现无处可读。facade 只暴露宿主真有的东西。
2. **~~`events` 未实现~~ → 已实现（1.1.0）**：事件走「双侧订阅」模型 —— handler 永远留在沙箱窗口（`module-table` 的 `eventHandlers` 表），主进程 `hostEvents.cjs` 只存 `pluginId → subscriptionId → 事件名`；宿主变更点（导入/改名/回收三个 IPC handler）调用 `emit()`，命中订阅时向沙箱推一条 `{ type:'host-event', subscriptionId, name, payload }`，沙箱按 id 找回 handler。payload 逐字段重建，`hashPrefix`/存储路径出不去。当前事件：`asset.added` / `asset.renamed` / `asset.removed`（对应 Obsidian `vault.on('create'/'rename'/'delete')` 的 B-vault 核心面）。`on()` 同步返回订阅 id，登记失败（最常见是没声明 `events.subscribe`）会撤销本地 handler 并 `console.error` —— 不静默哑掉。

**已知缺口**：`assets.rename` 改的是宿主仓储里的显示名，渲染进程画布元素的 `name` 是打开时的快照 —— 改名后画布上要重载才刷新。`patchAssetDisplayNames` 已实现，缺的是把结果回推渲染进程的通道，属 P1。

## 4. 方案 B（P1）：声明式 UI schema

### 4.1 问题

沙箱插件出面板的唯一途径是塞裸 HTML 字符串（≤8000 字符），**不能写 React、不能复用宿主组件**。这是"手感不像 Blender"的主因。

### 4.2 做法：抄 ComfyUI 的反射思路 + Obsidian 的 `Setting` API

插件声明控件 schema，**宿主负责渲染**：

```ts
api.host.ui.registerSettingsTab({
  id: 'local.my-plugin.settings',
  title: '我的插件',
  controls: [
    { key: 'threshold', type: 'slider', label: '阈值', min: 0, max: 1, step: 0.01, default: 0.5 },
    { key: 'mode',      type: 'dropdown', label: '模式', options: ['a', 'b'] },
    { key: 'enable',    type: 'toggle', label: '启用' },
    { key: 'pattern',   type: 'text', label: '规则' },
  ],
});
```

宿主渲染成与内置设置页**完全一致的外观**（复用自己的 `settings_sections` 组件），插件一行 UI 代码都不用写。取值通过 `api.config` 读回。

> 这与 ComfyUI 的 `INPUT_TYPES()` 是同一思路：**插件自定义接口，宿主照着画**。区别是 ComfyUI 从 Python 反射，我们从 JSON schema。

### 4.3 价值

- 解掉 8000 字符 HTML 的硬限制；
- 面板外观与宿主统一，不再有"插件面板长得像外包"的观感；
- 不碰沙箱（schema 是纯数据）。

## 5. 方案 C（P2）：分发治理

Obsidian 的经验：**在承认沙箱覆盖不到的地方，用治理补位。** 三层。

### 5.1 总开关（对标 Restricted mode）

artflow 已有等价物：插件管理器里的启用开关 + 「本次启动」语义。**待补**：首次启动时把"第三方插件默认关闭、需显式开启"讲成一句明确的风险提示，而不是默认全开。

### 5.2 插件目录（Registry）

现在第三方只能"我发你一个文件夹、你手动选目录装"。补齐：

- 一个 registry JSON（可放 GitHub raw / 自建端点），条目 `{ id, name, author, description, repo, homepage }`；
- 从 registry 一键安装 = `git clone` 或下载 release 资产；
- **`id` 必须等于安装后的文件夹名**（抄 Obsidian 这条硬规则，避免路径与 id 不一致导致的加载失败）。

### 5.3 准入 + 披露 + 扫描

| 层 | 内容 |
|---|---|
| **准入** | 提交 registry 前审查：禁止代码混淆、禁止静默自更新、禁止远程拉取可执行代码、禁止客户端遥测 |
| **披露** | manifest 必填一段 `disclosure`：是否联网 / 是否读写受信目录外的文件 / 是否开源 / 是否有付费或账号要求。**安装对话框必须展示**——正好接在现有 3.4 的权限授权框上 |
| **扫描** | 每个版本自动扫（可疑 API 使用、超大体积、动态 `eval`），registry 页面展示安全评分 |

## 6. 方案 D：Obsidian 插件移植通道

> 目标：**改完之后，把一个 Obsidian 插件搬过来应该是"跑一条命令 + 看一眼报告"，而不是"重写一遍"。**
> 本节所有数字来自本机库（`J:\资产库\知识库\.obsidian\plugins`，**45 个真实插件**）的实测扫描，扫描器已入库：`scripts/obsidian-compat-scan.cjs`（`npm run scan:obsidian`）。

### 6.1 结论：机械层可以自动化，语义层不能

| 层 | 内容 | 能否自动 |
|---|---|---|
| **机械层** | 清单格式、`require("obsidian")`、生命周期钩子、注册/回收、数据持久化、设置界面 | ✅ **可以做到接近零改动** |
| **语义层** | 插件操作的对象是「一堆 Markdown 笔记」（vault/metadataCache/editor） | ❌ 我们操作的是「一堆图片资产 + 画布」，**没有 Markdown 编辑器** |

所以真实目标不是"100% 兼容"，而是：**把能自动的那部分做到全自动，把不能自动的那部分在安装时就说清楚。** 下面这张表就是"说清楚"的依据。

### 6.2 关键技术前提（这条路为什么成立）

三个事实叠在一起，缺一不可：

1. **Obsidian 官方构建约定要求把 `obsidian` 标为 external**（连同 `electron` / `@codemirror/*` / `@lezer/*` / Node builtins）。因此插件的 `main.js` 里**保留着字面量 `require("obsidian")` 调用**，而不是被打包器内联。实测本机 45 个插件中 31 个能直接检出该调用。
   > 这意味着**不需要插件源码**，也不需要重新构建 —— 我们能从产物外部接管它的 API。
2. **我们的沙箱现在把 `require` 注入成 `undefined`**（`sandbox/module-table.cjs:12-16` 的 `LOCKED_GLOBALS`，第 158-159 行以同序参数传 `undefined`）。
3. 因此**改动点是一个参数槽**：把 `require` 那一格从 `undefined` 换成一个**只解析白名单的 require**，其余 19 个全局维持 `undefined`。

这三条合起来 = 「同名 shim 接管 API」成立，且**不放开沙箱**。

### 6.3 实测覆盖率：45 个插件分成 6 档

| 档 | 数量 | 占比 | 含义 | 需要做什么 |
|---|---|---|---|---|
| **A-auto** | 4 | 9% | 只用命令 / 工具栏按钮 / 设置页 / 网络请求 / 数据持久化 | **跑 shim 就能用** |
| **B-ui** | 0 | 0% | 需 Notice / Modal / 自定义 View | 补 UI 桥 |
| **B-vault** | 7 | 16% | 要读写"文件"（`vault.create/read/modify/delete/rename`） | **把资产库映射成 vault** |
| **B-metadata** | 8 | 18% | 要读 frontmatter / 链接缓存（`metadataCache`） | 笔记语义，需专门设计 |
| **C-editor** | 16 | 36% | 依赖编辑器 / Markdown（`MarkdownView` / `Editor` / CM6 扩展） | **artflow 无对标物** |

### 6.5 三层落地设计

**D1 · 补齐"我们有、Obsidian 也有"的管道**（与方案 A/B 同期做，不额外起工程）

| 要补的 | 形态 | 为什么必须同名 |
|---|---|---|
| `registerEvent` / `registerDomEvent` / `registerInterval` | `Plugin` 基类上的**隐式记账**方法（抄 Obsidian 的 `Component`），同时保留显式 disposer | shim 无法模拟"自动回收"，只能由宿主真做 |
| `loadData()` / `saveData()` | 按插件隔离的 KV（落 `<userData>/plugins/<id>/data.json`） | 41/45 插件第一件事就是读设置 |
| `Notice` | `host.ui.notice(msg, ms)` | 23 个插件用它做反馈 |
| `Modal` / `SuggestModal` | 最小实现：`host.ui.modal({title, controls, onConfirm})` | 14 个插件；也可收敛到方案 B 的 schema |
| View 注册表 | `registerView(type, factory)` → 对齐 `ui_panels` / `canvas_widgets` 插槽 | 15 个插件注册自定义视图 |
| 状态栏区域 | 新的 `ui_statusbar` 插槽 | 3 个插件；成本极低 |

**D2 · shim 模块 + 白名单 require**

```
sandbox/obsidian-compat.cjs   ← 实现上表"D2/SDK 面"的导出
sandbox/module-table.cjs      ← require 那一格从 undefined 换成 boundedRequire
```

```js
// sandbox/module-table.cjs 改动（示意，唯一的结构性改动）
const MODULE_ALLOWLIST = {
  'obsidian': obsidianCompat,                    // 同名 shim
  '@codemirror/state': makeUnsupported('editor'), // 明确抛"artflow 无 Markdown 编辑器"
  '@codemirror/view':  makeUnsupported('editor'),
};
function boundedRequire(id) {
  const mod = MODULE_ALLOWLIST[id];
  if (!mod) throw new Error(`module "${id}" is not available in the plugin sandbox`);
  return mod;
}
// 第 159 行：LOCKED_GLOBALS.map(g => (g === 'require' ? boundedRequire : undefined))
```

**要点**：白名单是**显式枚举**，不解析、不落盘、不做路径解析。`fs` / `electron` / `child_process` / `path` 全部**不在**表内 —— C-node 档那 10 个插件会得到一个明确的错误信息，而不是静默失败。

**D3 · 转换器 `artflow-import-obsidian`**

一条命令完成"搬家"，并**当场给出难度报告**：

```
$ npx artflow-import-obsidian ./path/to/obsidian-plugin
读取 manifest.json …… id=calendar  version=1.5.10
重写 manifest.json …… id=local.calendar  runtime={mode:"sandboxed",entry:"main.js"}
扫描 main.js ……… 使用 API 23 项，宿主对象 8 项
移植定级 …………… B-vault（可用，依赖 assets 写权限）
待处理 ……………… vault.create/modify → 映射到资产库写 API
                     ⚠ 未发现 require("electron")/("fs")，无原生依赖
输出 ………………… ./local.calendar/  （可直接"安装插件"选中）
```

三件事：① 清单转换（`id` 加 `local.` 前缀、`main.js` → `entry`、`isDesktopOnly` → 权限声明）；② 用 6.3 的分类器出难度报告；③ 直接产出可安装目录。**扫描内核已入库**（`scripts/obsidian-compat-scan.cjs`），转换器是它的外壳。

### 6.6 安全边界（这一段是取舍，不是遗漏）

放开 `require` 听起来危险，但这里的边界**比 Obsidian 严格得多**，且规则可一句话说清：

| | Obsidian | 本方案 |
|---|---|---|
| 插件能 `require` 什么 | **任意**（`fs` / `child_process` / `electron` 全可用） | **只有 `obsidian`** 和白名单里的几个模块 |
| 插件能碰 DOM 吗 | 能（全权 DOM） | **不能**（`document` / `window` 仍是 `undefined`） |
| 风险 | 官方明说"做不到隔离" | 白名单之外一律抛错，**能力面与现在完全相同** |

**注意 `registerDomEvent` 与 `usesDom` 的落差**：实测 7 个插件调 `registerDomEvent`，而大量插件在源码里直接 `document.createElement`。沙箱不给 DOM，所以这类插件**在 shim 之后仍然会报错** —— 这正是 B-ui 档为 0 的原因（它们都被上游的 `vault` / `editor` 依赖先分走了）。

**替代方案（需单独决策，默认不做）**：给 `runtime.mode` 加一个 `trusted` 档，像 Obsidian 那样给全额 Node/DOM 能力，安装时弹强提醒。这等于**在信任模型上开一个洞**，与现有沙箱的立意相反。建议：**先不做**，等 A/B 档覆盖率跑满再评估。

### 6.7 明确接不上的部分（写进安装报告，别让用户猜）

- **Markdown 编辑器相关**（16/45）：`MarkdownView` / `Editor` / `MarkdownRenderer` / `registerEditorExtension` / `registerMarkdownCodeBlockProcessor` / `EditorSuggest` —— artflow 没有笔记编辑器，**不打算为了兼容而造一个**。
- **元数据与链接**（8/45）：`metadataCache.getFileCache` / `getFirstLinkpathDest` / `processFrontMatter` —— 依赖"笔记之间的链接图"，我们连概念都没有。
- **原生能力**（10/45）：`fs` / `path` / `child_process` / `electron` —— 与沙箱设计正面冲突，且这些插件做的事（本地文件系统操作、调外部程序）在 artflow 里本来就该走主进程受控 API。

## 8. 明确不做（写下来避免反复）

| 不做 | 理由 |
|---|---|
| **内嵌 CPython 到主进程共用解释器** | ComfyUI 的教训（235 个插件共用解释器 → `pip` 依赖战争）。若要加 Python，**必须走子进程 + 每插件独立 venv** |
| **追 Blender 的 `bpy.types` 级自由度** | 需要把宿主内部数据模型整个摊开，等于重新设计对外契约，工作量是 facade 的 5~10 倍，且会动摇沙箱信任模型 |
| **把插件装进作品库** | Obsidian 的坑；我们放 `<userData>/plugins/` |
| **开放插件自定义插槽** | `SLOTS` 是写死的联合类型，是"登记式"契约的根基；开放它等于放弃贡献 id 的冲突检测 |
| **为了兼容 Obsidian 而造一个 Markdown 笔记系统** | 那 16 个 C-editor 插件的问题不是"跑不起来"，是"artflow 不是笔记软件"。造编辑器的成本远超收益，且与产品定位冲突 |
| **给沙箱插件开原生 Node/Electron 能力**（`trusted` 档） | 那 10 个 C-node 插件要的是 `fs`/`child_process`/`electron` 直通，等于取消沙箱。**默认不做**，等 A/B 档覆盖率跑满再评估 |
| **在 shim 里"假装"支持编辑器 API** | 把 `MarkdownView` 做成空壳会让插件静默失效，比明确报错更糟。**不支持的就抛清晰错误** |
