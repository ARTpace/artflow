## 1. 用户问题与目标

### 1.1 用户问题

- 导入图片、视频、音乐等资产时，整个画布无法正常操作。
- 没有清晰的文件级进度、速度、当前阶段及剩余任务信息。
- 导入速度慢，而且往往要等全部导入后才看到卡片。

### 1.2 产品目标

G1：导入任务进行时，已有画布仍能平移、缩放、拖动、选中和编辑。

G2：提交文件后快速出现真实的任务反馈；支持查看失败项、取消剩余任务、重试失败文件。

G3：小文件和轻量结果尽快可见，不被一个巨型文件完全阻塞。

G4：主线程不承担可迁移的重型解析/编码；任务并发、解码内存和 UI 提交均有上限。

G5：新增导入流程与现有受管资产库、项目恢复、插件格式处理器和保存契约兼容。

G6：速度与交互流畅度分别测量。优先维持可操作性，不以无界并发换取短时间吞吐数字。

### 1.3 非目标

- 本次不改为全 WebGL 画布。
- 不重建资产数据库或替换全部格式解析器。
- 不承诺所有格式都支持精确百分比、即时取消或崩溃后恢复。
- 不自动修改原始文件格式或永久降采样原图。
- 不为了大文件而简单取消 IPC 限额。

## 3. 目标架构

```text
用户拖放 / 文件选择
  │
  ▼
ImportCoordinator（会话、目标画板、任务与资源所有权）
  ├─ ImportStore → 非阻塞任务栏/详情面板（节流订阅）
  ├─ SourceAdapter（Browser File / Electron 授权引用）
  ├─ BoundedScheduler（I/O、轻任务、重解析、预览）
  │     ├─ 复用受管入库与衍生任务
  │     └─ Browser Worker / Electron Worker 或 utility process
  ├─ PreparedResultBuffer（有界，背压）
  └─ CanvasCommitQueue（目标画板、稳定布局、小批提交）
         └─ 现有画布/文档/操作历史
```

职责边界：
- Coordinator 不渲染 React UI，不直接解析每种格式。
- Scheduler 不修改画板；只管理执行、取消、并发和预算。
- Parser 返回元数据/资产引用/结果，不直接调用 setBoards。
- Store 存轻量状态；不把 File、ArrayBuffer、Data URL 大字符串塞进频繁发布的状态快照。
- CanvasCommitQueue 是唯一将结果加入画板的入口。
- 文件名可以显示；本地绝对路径不得进入任务展示、日志导出或插件可读快照。

### 建议新增模块（可根据项目组织调整）

```text
imports/
  contracts.ts
  ImportCoordinator.ts
  ImportStore.ts
  BoundedScheduler.ts
  CanvasCommitQueue.ts

```

无需一次创建全部文件。每批只添加该阶段真正使用的模块，避免空壳架构。

## 4. 数据与状态契约

以下 TypeScript 为设计骨架，不可未经适配直接替代现有类型。

```ts
type ImportPhase =
  | 'queued' | 'reading' | 'metadata' | 'preview'
  | 'awaiting-commit' | 'ready' | 'failed' | 'cancelled' | 'skipped';

type BatchState =
  | 'running' | 'paused' | 'cancelling'
  | 'completed' | 'completed-with-errors' | 'cancelled';

interface ImportTarget {
  projectSessionId: string;  // 会话 epoch，不只是磁盘路径
  boardId: string;
  anchor: { x: number; y: number }; // 提交文件时的世界坐标
}

interface ImportItemSnapshot {
  id: string;
  batchId: string;
  ordinal: number;
  attempt: number;
  generation: number;       // 拒绝取消/重试之前的迟到结果
  displayName: string;
  sourceBytes: number;
  phase: ImportPhase;
  stageBytesDone?: number;
  stageBytesTotal?: number;
  stageStartedAt?: number;
  emittedNodeCount: number;
  committedNodeCount: number;
  previewState: 'pending' | 'ready' | 'failed' | 'not-needed';
  durability: 'session-only' | 'staged' | 'stored';
  error?: { code: string; message: string; retryable: boolean };
}

interface ImportBatchSnapshot {
  id: string;
  target: ImportTarget;
  state: BatchState;
  discoveredFiles: number;
  terminalFiles: number;    // ready + failed + cancelled + skipped
  readyFiles: number;
  failedFiles: number;
  cancelledFiles: number;
  skippedFiles: number;
  committedNodes: number;  // 不能与文件数混同
  totalSourceBytes: number;
  revision: number;
}
```

### 4.1 状态语义

- reading 是读取或受管复制；metadata 是必要信息提取；preview 是首次可用预览，不强制包含高清预览。
- ready 只在该文件必需结果成功提交画布后成立；解析完成但未提交必须是 awaiting-commit。
- 文件的画布可用性、预览质量和持久性是三个维度，不能用一个百分比混在一起。
- 后续高清预览失败，不应把已可用文件从 ready 变成全盘 failed；记录 previewState 和警告。
- 多页文件可以逐页出现，但 ready 需要定义必需页范围已全部提交；超出页数预算必须让用户确认或明确显示截断。
- 失败重试增加 attempt/generation；旧任务回调即使随后成功，也不得提交。
- 所有状态转移集中在 reducer/coordinator，UI 不得随意改状态。

### 4.2 批次状态

- running → paused：只暂停新任务调度；已运行任务可完成并提交，UI 必须说明。
- paused → running：恢复调度。
- running/paused → cancelling：不启动新任务，取消可取消任务，拒绝后续无效结果。
- 所有任务 settled 且无待提交结果后，才进入终态。
- 无失败/取消时 completed；有失败/跳过时 completed-with-errors；明确取消剩余导致取消项时 cancelled。
- 展示“已完成 X、已取消 Y”，不把 cancelled 显示为成功 100%。

### 4.3 事件契约

建议事件包含 `batchId/itemId/generation/sequence`，事件类型包括 phase、byte-progress、result-ready、warning、failed、cancelled。

规则：重复事件幂等；旧 sequence 不覆盖新状态；项目 session 不匹配时拒绝事件；任意 observer 抛错不能中断真实任务。

## 5. 生命周期、并发与背压

### 5.1 初始配置，仅供测量起点

| 资源 | 建议起点 | 约束 |
|---|---:|---|
| I/O 活跃任务 | 2 | 必须受读/写带宽与字节预算约束 |
| 普通图片解析/预览 | 1–2 | 大图不能仅按任务个数控制 |
| PSD/RAW/大型文档重任务 | 1 | 独立重任务许可，不与其他池叠加成无界总数 |
| 进度快照发布 | 最多 5–10 次/秒 | 状态终结、错误、用户操作可立即发布 |
| 画布提交间隔 | 100–200ms | 每批最多 8–16 节点起步；按测量调节 |
| 待提交结果缓冲 | 有界 | 按节点数及估算字节数限制，满后暂停生产者 |

具体内存上限必须集中配置并说明估算规则；不能依据机器 RAM 自动使用绝大部分内存。

### 5.2 内存预算

普通栅格图可使用 `width × height × 4 × workingCopyFactor` 估算工作内存；这不是精确浏览器/GPU 内存测量。对未知尺寸先获取头部信息或使用保守重任务通道。

任务只有同时获得执行槽与内存许可才启动；finally 中必须释放。错误/超时/取消都不能泄漏许可。

图片尺寸、页数、解压大小和压缩比都应有安全限制。不能因为文件只有几 MB 就认为解码后也很小。

### 5.3 交互优先

已有指针交互活跃时，可暂停启动低优先级高清预览和减少提交频率。不得每次鼠标移动都更新全局 React 任务状态；交互信号应为轻量订阅/ref。

“暂停启动”不能中断已在主线程执行的同步解析。因此重型工作外移与有界回退仍是必要条件。

### 5.4 线程与回退

- Electron 主进程负责权限、调度与事务边界，不承担长时间同步图像解析。
- 优先复用已有衍生 Worker；先核对支持的输入、输出和取消协议。
- Browser 使用可支持的 Worker/OffscreenCanvas 路径；不能直接把依赖 document 的函数放进 Worker。
- 旧插件解析器使用 legacyAdapter 标注执行能力；无法搬移的同步重活不能宣称已非阻塞。必要时限制文件大小/提醒用户，而不是隐藏限制。
- yield 能拆分循环，但不能切开一次耗时很长的同步函数。setTimeout(0) 不是通用性能修复。

## 6. 文件来源与持久化边界

### 6.1 Browser 模式

File → Object URL/可转移缓冲 → metadata/preview → RuntimeAsset。

- 不因导入大视频调用 readAsDataURL。
- Object URL 仅是会话内引用，不能直接成为持久化 locator。
- 保存前仍需 materialize；若当前受管字节路径超过 128 MiB，应明确告知能力限制，不静默生成无法恢复的项目。
- 网页重载后不能保证重新访问 File；任务状态必须显示 session-only，不伪称可恢复。

### 6.2 Electron managed 模式

建议新增独立的授权来源入口：

```text
用户选择/拖放 File
   → preload 的窄接口获取受授权来源能力
   → 主进程登记 session-scoped source token
   → 后台流式复制/哈希到受管 staging
   → 受管资产引用
   → renderer 仅接收元数据与预览 locator
```

安全要求：
- 不允许 renderer 传任意路径字符串让主进程读取。
- source token 绑定窗口/项目 session/生命周期，取消、切项目或关闭后失效。
- 保留 frame/origin 检查、类型校验、队列大小限制、文件与磁盘配额。
- 解析文件路径的方式按实际 Electron 版本及 preload 能力实现；不得假定浏览器 File.path 可用。
- 复制期间限制字节数、处理源文件改变/消失、磁盘满、权限失败。
- 写入临时文件，验证完成后原子提交；不把半文件标为 stored。
- 哈希流式计算；去重以内容哈希/受管资产身份为依据，不以文件名或大小当作内容相同证明。

### 6.3 现有入库实现的演进限制

当前 requestImport 接收整块字节；资产任务单活跃执行；列表仅返回有界最近任务。新方案不能把这些接口当作已存在的流式并发能力。

先复用其状态、staging 所有权、恢复和结果模型，再以版本化窄 API 增加流式 source-token 导入。后台 journal 与 UI 批次进度分开：UI 批次总数不得依赖最近 25 条任务列表。

### 6.4 资产协议与大视频

检查 `artflow-asset` 是否支持 Range 请求、206/Content-Range、无效 Range、Content-Length、正确 MIME、取消读取与 seek。若不支持，作为大视频可靠导入的前置缺口处理。

不得为解决播放而暴露任意 file:// 路径或任意磁盘读取端点。

interface ParseContext {

## 8. 音视频元数据与资源管理

### 8.1 元数据读取统一封装

实现有超时、取消和清理的 metadata helper：
- 成功返回宽高/时长，过滤 NaN/Infinity/非法尺寸。
- 解码错误可降级为默认尺寸/未知时长，并记录 warning。
- 超时停止等待；不能让一个媒体文件卡住整个批次。
- settle 必须幂等；成功、error、timeout、abort 中只有一次生效。
- 清理 timer、事件监听和临时媒体元素；按需要 pause/removeAttribute('src')/load。
- 用于最终卡片的 Object URL 不得在 metadata 读取结束时误 revoke。

超时起点可设 10–15 秒，允许配置；不能把远程/本地不同来源混为一个永远等待的策略。

### 8.2 ResourceRegistry

每项资源声明 owner：task、prepared-result、canvas-node、save-operation 或 history。

任务提交成功时将资源所有权转移给画布/资产层；取消和失败释放任务所有资源。保存仍在读取时不得释放。撤销后是否立即释放取决于 redo 是否仍需该资源；没有处理历史引用前，不能按“元素消失就 revoke”实现。

ImageBitmap.close、Object URL revoke、Worker terminate/归还池、AbortController 和临时 staging 清理都要有对应路径。

波形、视频封面等可延后生成；不能在首次导入时为每条音频完整解码波形。

## 9. 分批上画布、布局与并发编辑

这是高风险阶段，必须独立交付。

### 9.1 目标捕获

导入开始时固定 projectSessionId、boardId、世界坐标 anchor。禁止每一批完成后用当前 activeBoardId 或当前鼠标坐标作为目标。

- 切换画板：继续导入到原画板，并在任务栏标明目标。
- 删除目标画板：取消待提交项；不自动改投其他画板。
- 切换项目：停止/分离旧任务，拒绝跨 session 提交；旧项目可恢复后台任务是否继续应显式设计。

### 9.2 稳定布局

推荐第一版使用基于输入 ordinal 的固定槽位：
- 列数在批次创建时确定；slot 宽高固定，图像在槽内等比显示。
- 完成顺序不影响位置；大文件排队不会阻挡后续文件显示。
- 后补 metadata 不重排整个批次。
- 不为所有待处理文件一次性创建数万 DOM 占位卡；用任务面板/轻量批次区域表示等待。

保留 Masonry 外观时，应单独实现确定性增量布局；不能等待所有文件全部解析才能计算布局，也不能完成一个文件就重新排列已被用户拖动的卡片。

多页文件使用稳定子区域/分页槽位，避免页数晚到导致所有后续卡片重排。页数与节点数均需上限。

### 9.3 小批提交

PreparedResultBuffer → 按时间/节点数预算 flush → 对目标 board 提交新增节点。

- 一次 flush 使用一次状态更新；不逐文件 setBoards。
- pending 队列必须有界；画布提交慢时暂停生产者。
- 已开始指针操作时可延迟非紧急 flush，避免抢夺操作工具/选区。
- 导入不反复 setActiveTool('select')；只在明确用户动作需要时切工具。
- 第一版默认不自动全选批次资产；可提供完成后“定位导入区域/选中本批”。
- 对 Frame parenting 保留现有语义，并明确按提交时画板状态计算；不能复用已过期的全局 elements 闭包。

### 9.4 撤销语义：不能粗暴做长事务

用户可以在导入期间拖动旧卡片、输入文本。将“导入开始的整个 boards”存为快照，取消时还原，会抹掉这些编辑，严格禁止。

推荐渐进交付：
1. 第一版分批提交沿用现有历史，每个 flush 一条可撤销操作；文档和 UI 明确说明，不冒充单步撤销整个批次。
2. “取消剩余”仅阻止待处理/待提交项，保留已导入节点。
3. 后续再实现显式“移除本批已导入节点”：按该批拥有的 node IDs 做正常可撤销删除，不回滚整个画板，不删除与其他节点共享的资产文件。
4. 如需真正单条历史的增量导入 transaction，必须先扩展 operationHistory 并证明并发编辑不被吞并；单独 ADR 和测试，不能简单 begin/commit 包住几分钟任务。

用户删除或撤销了已出现节点后，迟到的高清预览只能 patch 仍存在且身份匹配的节点，不能重新创建被删节点。redo 是否恢复某个已释放资源要有明确契约。

### 9.5 幂等

提交键至少包含 batchId + itemId + generation + subresourceId。重复 worker/恢复消息不得创建重复卡片。

“资产去重”不等于“节点去重”：用户故意再次拖入同一文件，可以复用资产但仍创建新卡片。

## 10. 进度、速度与任务 UI

### 10.1 UI 结构

- 常驻右下角可收起任务条，不遮挡整个画布，不自动抢焦点。
- 展开详情面板复用/扩展 ImportJobsPanel 的视觉能力，但明确普通会话任务与 durable 存储任务的区别。
- 展示批次目标画板、总文件数、已就绪、处理中、排队、失败、取消、已生成卡片数。
- 大量任务明细必须窗口化或分页，不创建无限长列表。
- 操作：暂停队列、继续、取消剩余、重试失败、查看错误、定位结果。
- 暂停标注“已运行任务仍可能完成”。尚未实现的操作不能放一个无效按钮。

示意：

```text
导入到：灵感画板                  [收起]
500 个文件 · 128 已就绪 · 2 处理中 · 367 排队 · 3 失败
读取 1.8 / 6.4 GB · 85 MB/s
最近处理 12 个文件/秒 · 当前：生成图片预览
[暂停队列] [取消剩余] [查看详情]
```

以上仅为示例，不应写成实际测试结果。

### 10.2 进度定义

- 文件就绪进度 = readyFiles / discoveredFiles。
- 队列结算进度 = terminalFiles / discoveredFiles；标签必须写“已处理/已结算”，不能把失败当成功。
- 字节进度只能针对确实有字节反馈的阶段；reading 完成不等于整个导入完成。
- 解码/解析没有精确进度时，显示阶段、文件名、已耗时与不确定进度，不伪造缓慢增长的百分比。
- 0 字节文件、空批次、不支持格式和目录递归发现中的分母变化必须定义；第一版若不支持目录递归应明确拒绝。
- 后台补高清是独立预览状态，不能让主导入条一直卡在 99%。

### 10.3 速度算法

对同一阶段的单调累计字节采样，用 monotonic clock（performance.now 或等价时钟），例如最近 3–5 秒窗口：

`bytesPerSecond = (latestBytes - oldestBytes) / elapsedSeconds`

- 读、写、哈希不能重复计入同一个“导入速度”。可以分别显示复制吞吐和文件处理速度。
- 暂停时显示已暂停，不沿用之前速度。
- retry 使用新 attempt 的计数，防止累计字节回退或重复统计。
- 缓存命中/去重跳过显示已复用，不把未实际读取的数据算作瞬时超高速。
- 初始样本不足显示“统计中”。

### 10.4 ETA

剩余读取字节 / 平滑读取速度只能称为“预计读取剩余”，不能称为导入完成时间。复杂混合格式总 ETA 不可靠时不显示；后续可按格式和阶段历史估计，并显式标记约值。

### 10.5 渲染隔离

ImportStore 通过选择器/useSyncExternalStore 等方式提供快照；同 revision 返回稳定引用。任务更新只通知任务 UI。不能把每个文件每个 chunk 的进度写进 App 的高频顶层 state 并传遍画布。

用合并事件/节流限制进度消息与 React commit；订阅清理必须支持 StrictMode 双挂载。

## 11. 错误、超时、取消与重试

建议错误码：UNSUPPORTED_FORMAT、SOURCE_UNAVAILABLE、READ_FAILED、METADATA_TIMEOUT、DECODE_FAILED、SIZE_LIMIT、MEMORY_BUDGET、DISK_FULL、PERMISSION_DENIED、TARGET_GONE、PROJECT_CHANGED、WORKER_CRASH、STORAGE_FAILED。

- 单文件错误局部处理；同批其余文件继续。
- 异常消息对用户友好，详细诊断可展开但过滤本地路径及敏感内容。
- 取消先设置 generation/tombstone，再发 abort；防止竞态窗口中的结果被提交。
- 不可中断的同步 parser：不再提交其结果，任务结束后清理；不能显示“已立即释放资源”。
- Worker 可终止但需区别独占任务 Worker 与共享池，不能终止一个任务时破坏其他文件。
- retry 不复用旧 AbortSignal、旧 timer 或旧进度；幂等键更新。
- 任务取消后仍被其他节点使用的内容寻址资产不能删除。
- staging 清理遵守已有所有权/恢复契约，不通过全目录删除解决孤儿文件。

## 12. 保存、恢复与关闭

### 12.1 自动保存

画布只包含可保存的已提交结果；待解析结果留在任务系统。Browser runtime locator 保存时沿用受控 materialize 流程；managed 已 stored 资产保存只引用，不重复 fetch→arrayBuffer→重新入库。

自动保存不能把未完成批次误报为“全部导入已保存”；UI 可分别提示“已显示”“已入库”“已保存”。

保存过程中继续导入时，以文档 revision/引用基线判断是否仍有未保存变化，沿用现有变更跟踪规则。

### 12.2 恢复

- session-only：关闭后可能丢失未完成任务；明确提示。
- staged：只有已持久化输入、目标与任务意图足够恢复时，才承诺继续。
- durable job 完成不代表对应画布节点已经加入项目文档；需要记录并测试“完成待消费”的状态或幂等消费机制。
- 崩溃恢复后重复事件不能重复上画布。
- 不在 beforeunload 中依赖一串未等待的异步调用保证完成保存。

这些要求如超出第一阶段范围，必须在 UI 降级说明和台账中列出，不默认保证恢复。

### D0：基线、保护与测量

阅读现有 ADR/FDD，尤其 R05/06/08/09/10/18 相关存储与任务边界；确认近期修改。运行原有检查并备份。

### D1：最低风险正确性与反馈

- 修复 imageFrom 缩略图字段丢失，增加全链路测试。

- 注意 isLoading 可能仍被 AI/其他功能使用，不全局删除。

### D2：大媒体与资源生命周期

- 视频使用 Object URL 临时方案替代 Base64，并实现资源所有权。

- 审查 asset 协议 Range 与播放器 seek。

### D3：有界调度与分批提交

- 引入 scheduler、预算与背压。
- 稳定布局，绑定原目标画板。
- 分批提交，不自动全选，不抢工具。
- 采用第 9.4 节明确的渐进撤销语义。
- 实现取消剩余、失败重试和迟到结果屏蔽。

验收：一个慢文件不阻塞后续轻文件显示；切画板不串板；取消不抹除用户编辑；pending 结果有界。

### D4：后台解析与预览统一

- 复用现有 derivative worker；将可迁移的同步解析/编码移出 renderer。
- 为 legacy parser 标记能力并提供安全回退。
- 将普通任务与受管存储任务关联到同一批次展示，避免两份进度互相矛盾。
- 不把最近 25 条 durable jobs 当作批次总账。

验收：profile 证明主要重处理离开 renderer，交互期间长任务显著减少；后台取消/崩溃不破坏主进程与项目。

### D5：性能回归、文档和发布

固定场景比较修改前后。记录失败/恢复/保存与 UI 体验矩阵，更新本规格状态。保留安全开关或 legacy 路由以便回退；回退不删除已成功入库资产。

## 17. 常见错误实现：禁止清单

- 把 for-await 改为无界 Promise.all。
- 只在循环里 setProgress，重活仍同步跑在主线程。
- 只加 setTimeout(0) 就宣称所有大图解析非阻塞。
- 把 toDataURL 换成 toBlob 就认为所有解码/缩放已离开主线程。
- 将重型解析搬到 Electron 主进程同步执行。
- 为了大文件简单移除 128 MiB 限制，把几 GB ArrayBuffer 通过现有 IPC 发送。
- 用任意路径读取 API 取代安全 source token。
- 任务完成后向“当前画板”追加，未捕获原目标。
- 分批完成后每次重新瀑布流排序已被用户移动的卡片。
- 每个进度事件 setBoards/setElements。
- 导入结束自动选中上万对象。
- 取消时恢复整个旧 boards 快照。
- URL 用完 metadata 就 revoke，但画布/保存仍需要它。
- 保存 blob URL 字符串然后宣称项目可重开。
- 把入库成功、卡片显示成功、预览完成和项目保存成功混为一谈。
- 从最近 25 条 durable jobs 计算整个 1,000 文件批次的进度。
- 重试后旧任务回调重新创建节点。
- 声称“文件去重”就应该禁止用户多次放置同一资产。

## 18. 回滚与发布策略

- 每阶段备份当时的原文件；记录新增文件与 API。
- 优先通过配置开关切换新旧导入入口，开关默认值按该阶段验证结果决定。
- 新旧路径共享稳定资产格式，回滚不需要删除/迁移用户媒体。
- 流式入库与 journal 扩展需要独立 schema/API 兼容策略，不与 UI 小修改混为一批。
- 重启前提示保存用户当前工作，不擅自关闭应用或清空缓存。
- 未完成测试的功能在台账标为待验，不写成已完成性能优化。
