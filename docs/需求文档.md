## REQ-001 画布自动保存 + 启动自动恢复

**状态**：已完成（R34 verified）　**优先级**：高　**归属**：本体（宿主 App 层）功能开发——不涉插件机制　**提出**：2026-09-22（主人发现画布内容不持久，重启即丢）

### 背景（现状查证结论）

持久化后端已完备（FDD 线产物），缺的只是触发机制：

| 组件 | 现状 |
|---|---|
| 主进程存储桥 | ✅ `preload.cjs` 暴露 `window.artflowStorage`：saveProject / loadProject / chooseProject / importAsset（sha256 内容寻址资产仓 `artflow-asset://sha256/`） |
| 项目文档格式 | ✅ Project Document v2（`utils/projectDocument.ts`），boards 与二进制定位分离 |
| 手动保存 | ✅ Ctrl+S / 保存按钮（App.tsx `handleSaveProjectClick`） |
| **自动保存** | ❌ 无——未手动保存即关闭 = 丢失编辑 |
| **启动恢复** | ❌ 无——打开应用不自动载入上次项目，需手动选 |
| 浏览器版 | 无 managedStorage，回落 File System Access API / 手动导出，无持久性 |

### 方案

> **与架构方案对齐（r2）**：《无限画布与海量资产架构优化方案》§7.3 规定项目保存只写 metadata/layout/operation journal，禁止全量重序列化；R2 已验证 operation journal 替代全量历史。因此自动保存的落盘对象是 **operation journal（高频）+ v2 快照（节流）**，而非全量 boards。

1. **自动保存**：
   - 编辑产生 operation commit → 防抖 1~2s → 冲刷 operation journal（轻量、增量）
   - v2 快照（managed save）节流触发：每 30s 有变更时一次 + 应用关闭前一次 + 手动 Ctrl+S 不变
   - 参照 litevideo 导演台草稿模式（localStorage + 400ms 防抖），此处写 managedStorage
   - 仅 managedStorage 可用时启用；浏览器版保持手动（能力受限属预期）
   - 保存中显示轻量状态提示（不阻塞交互），失败静默重试一次后提示
2. **启动自动恢复**：应用 mount → `getStatus()` → 项目处于打开状态 → 自动 `loadProject` 并渲染，实现"关闭再开 = 原样"；journal 中未入快照的操作在加载后重放
3. 关闭前确认可不做——自动保存落盘后无未保存状态（若后续发现保存耗时抖动，再评估 beforeunload 兜底）

### 验收标准

- [x] 拖入素材 / 编辑 / 移动元素后 2s 内无操作，不按 Ctrl+S，直接关闭应用重开 → 内容原样恢复（R34 verified）
- [x] Ctrl+S 保留且不受影响；浏览器版行为不变（R34 verified）
- [x] 自动保存不卡顿交互（防抖生效、无逐帧写入、非阻塞后台保存）（R34 verified）
- [x] 与 FDD-008/009 的后台导入/预览恢复共存无冲突（导入中途关闭重开，导入任务恢复 + 画布状态恢复叠加正常）（R34 verified）

### 关联

- 复用：`useFileSystem.ts` 的 saveProject/loadProject、`window.artflowStorage`、FDD-004 资产仓
- 风险：大项目（海量资产）下序列化耗时应随 FDD-011 viewport 增量缓存优化，本期只做防抖，不做增量序列化

## REQ-002 画布星系视图（远缩 LOD：卡片变星星）　⚠️ 已废弃

> **2026-09-27 废弃（主人决定移除）**：实测"星系视图切换瞬间卡顿，还不如去掉"，决定整体移除。已删除 `utils/galaxyView.ts`、`components/GalaxyStarLayer.tsx`，以及 `MainCanvas.tsx` 的星系渲染分支与 `onFocusElement` 契约、`App.tsx` 的 `handleFocusElement`、`check-core-foundations.cjs` 的 `runGalaxyViewChecks`、`check-bulk-image-safety.cjs` 的星系预热断言。代码副本留存 `.galaxy-backups/2026-09-27-galaxy-removal/`；ADR-035 与 FDD-035 已标记 deprecated，台账 R35 标 `reverted`。
> **代价（未解决）**：极远缩放（`zoom < 0.08`）不再降级为轻量星点，恢复为直接渲染图片元素 —— 仅靠 REQ-003 的多级图片 LOD 代理（按屏幕像素选 256/512/1024/原图）与视口裁剪兜底。下方背景中"海量画布（十万元素级）唯一可用的远缩视图"这一前提随之取消。

**状态**：~~已完成（R35 verified）~~　**已废弃（2026-09-27 移除）**　**优先级**：中（依赖 FDD-011/012）　**归属**：混合——LOD 机制归内核（本体开发），星系美学归插件（canvas_overlays，随 P2 后）　**提出**：2026-09-22（主人想要"缩小后像宇宙星系，每个卡片是一颗星星"）

### 背景（现状查证结论）

- 缩放无硬钳制（useCanvasState/useCanvasInteractions 无 min/max zoom），"不能无限缩小"的体感来自**可用性**：远缩时所有卡片仍全量 DOM（foreignObject）渲染——糊且卡
- 需要远缩 LOD（细节层次）机制，星系视图是其最漂亮形态；同时它也是海量画布（十万元素级）**唯一可用的远缩视图**——性能方案与视觉合二为一

### 职责划分（核心决策：机制归内核，美学归插件）

> **与架构方案对齐（r2）**：本需求即《无限画布与海量资产架构优化方案》§9.2 **LOD0（极远=色块/类型图标/聚合计数）的美学实例**，§8.3 "远距离只请求聚合信息或低 LOD 表示" 为其数据通道。按架构方案 §6.4 热路径禁区，星系视觉插件**不自持渲染循环/overlay 组件**，而是**启动时 materialize 成受控 descriptor**（星色映射、星座分组规则、背景样式——数据形态，同皮肤 token），由内核 LOD0 渲染器消费。

| 部分 | 归属 | 理由 |
|---|---|---|
| LOD 切换机制（远缩时卡片渲染降级为星点） | **内核**（MainCanvas 渲染管线，架构方案 §6.2 Runtime Core 成员） | LOD 按 zoom 阈值接管全局渲染；插件只渲染单卡，无法接管渲染循环 |
| 星系美学（星云背景/星色/星座分组样式） | **插件**（样式 descriptor 贡献，内核渲染） | 视觉数据可插件化：星色=卡片类型、同画板聚成星座、背景=皮肤 |

### 方案

```
zoom < 阈值(如 0.05) → 星系模式
  1. 卡片 foreignObject 全部卸载（渲染负担骤降）
  2. 从空间索引（FDD-011 ViewportIndexCache / FDD-012 SpatialQuery）读元素 {位置, 类型, 画板}
  3. 渲染星点层：星星=元素，颜色=类型，大小=重要度，同画板聚成"星座"
  4. 拖拽/缩放连续不中断；放大回阈值 → 平滑淡入回卡片；点击星星 → fly-to 动画定位到卡片
```

- 阈值与淡入淡出曲线做成常量/设置项；星系模式下保留框选星点批量操作（放大落位）
- 视觉层做成 `builtin/theme-galaxy` 类插件：贡献星点样式 descriptor（数据形态），由内核 LOD0 渲染器消费，星星样式可被其他皮肤插件覆盖

### 依赖与验收

- **硬依赖**：FDD-011（增量 ViewportIndexCache）、FDD-012（持久 ViewportSpatialQuery）——星点数据源；无索引则星系模式随元素数线性变卡。**依赖状态（r2 对齐）**：对应架构方案 Phase 3a（R11 mount-scoped 增量缓存）与 3b（R12 saved snapshot R-tree）**已验证完成**；但 R12 只覆盖 saved snapshot，live state 接管与 Worker 化（R12 后续）仍在路线中，星系模式 v1 可先建基于 R11 live index 的星点查询，Worker 化后再升级
- **时序**：排在架构方案 R15（drag axis guide）与 Hybrid renderer 线之后或并行，不与其抢渲染管线改造窗口
- ~~[x] 十万元素级画布远缩流畅（星点层为索引驱动，不随元素数全量渲染 DOM）（R35 verified）~~
- ~~[x] 阈值往返无闪烁：卡片 ↔ 星星平滑过渡（R35 verified）~~
- ~~[x] 点击星星 fly-to 定位准确；星座分组与画板归属一致（R35 verified）~~

- **（2026-09-27 移除）** 以上验收标准随本需求废弃而失效：极远缩放现为直接渲染图片元素，无星点层。

## REQ-003 图片渲染性能优化（渲染代理 + 分级缓存 + 视口卸载）

**状态**：已完成（R36 verified）　**优先级**：高（海量素材体验的地基，且是 REQ-002 星系视图的性能前提）　**归属**：本体（内核渲染管线 + 导入管线），衍生任务调度复用 FDD-008　**提出**：2026-09-22（主人问"PureRef 拖几千张超高清图为什么不卡"）

### 背景（PureRef 机制查证 + Artflow 现状差距）

PureRef 官方手册 / changelog / 论坛实测证实其丝滑的来源——**运行时永远不渲染原始分辨率**：

| PureRef 机制（实证出处） | 内容 |
|---|---|
| 导入时自动降采样（Settings: Auto optimize imported images） | 宽/高/面积/体积超限即生成缩放代理用于渲染；**原图完整存入 .pur**，只在聚焦/放大时取用 |
| 分级缓存 + 流式加载（2.0 changelog: image caching and streaming system） | Performance mode 四档：No cache / Cache on disk / In memory / In memory low zoom quality——本质是 mipmap 金字塔 + 视口流式，放大到哪才加载哪一级 |
| 远缩降画质（In memory, low zoom quality） | 远缩时主动用低分辨率版本，换取平移缩放丝滑 |
| 视口外卸载（2.1: resource loading and unloading） | 不可见图从显存/内存卸载；加载走后台线程（CPU core allocation 可控） |
| 论坛实测数据（170 图对照） | 全内存原画质 2GB RAM；降采样 512px = 270MB 且流畅——丝滑是用"远缩低画质、聚焦才看原图"换来的，无魔法 |

Artflow 现状差距：图片元素以 blob URL **全分辨率**直接进 SVG DOM 渲染；无多级缓存、无视口裁剪卸载、远缩仍全量 DOM。卡顿来源不是"图多"，是"每一张都在用原始分辨率参与渲染"。

### 方案（三层，按依赖排序）

1. **渲染代理（第一优先，收益最大）**
   - 导入管线新增衍生任务：原图落 FDD-004 内容寻址仓后，生成 2~3 级渲染代理（如 256 / 1024 / 原图三级），存衍生资产
   - 元素渲染默认引用代理级（按元素显示尺寸上限选取），原图仅在放大到超代理分辨率时惰性换载
   - 代理生成走 FDD-008 衍生任务池（后台、崩溃可恢复），不阻塞导入主流程
2. **按 zoom 取用（接 REQ-002 的 LOD 机制）**
   - 渲染时按当前 zoom × 元素显示尺寸选择代理级别：远缩用低级（对应 PureRef low zoom quality），放大逐级换载
   - 换级做成异步平滑（先显低级，高级就绪后淡入替换），避免闪烁
3. **视口裁剪 + 卸载**
   - 依赖 FDD-011/012 空间索引：视口外元素不渲染 DOM（星系模式下自然全部卸载，两需求共用该基建）
   - 平移/缩放时按可见性增量挂载/卸载，卸载同时 revoke 暂不用的 blob 引用（代理资产仍在仓中，随时可再取）

**边界与预期**：本需求三层（代理/换级/卸载）全部在现有 SVG 渲染上实施，定位为**架构方案 Phase 3（Hybrid Canvas2D/WebGL）落地前的止血层**——架构方案 §1 明确 SVG/DOM-only 最终须替换，但代理生成、LOD 取级、富媒体预算等概念会被 Hybrid renderer 原样继承，本需求为其**前置子集而非并行方案**；最终渲染策略以《无限画布与海量资产架构优化方案》Phase 3 为准。时序上排在 R15 与 Hybrid 线之后或并行。Web 技术上限：SVG 合成器方案目标补到 PureRef 的 ~80%；若未来海量纯图片场景仍不够，WebGL 图层渲染（GPU 纹理直绘）即架构方案 §15.1 的升级路径本身，不再单独立项。

### 验收标准

- [x] 导入 500+ 张 4K+ 图片后平移/缩放流畅（代理生效，内存占用对比原方案下降 ≥5 倍量级）（R36 verified）
- [x] 原图永不丢失：放大到超代理分辨率时能平滑换载原图级（对应 .pur 行为）（R36 verified）
- [x] 代理生成不阻塞导入（纯前端双代理快速生成，原图无损存储）（R36 verified）
- [x] 远缩/放大往返无闪烁（0.25 / 1.0 稳定阶梯与交互期代理锁定）（R36 verified）
- [x] 与 REQ-002 共用空间索引与 LOD 阈值，无重复基建（R36 verified）

### 关联

- 复用：FDD-004 内容寻址资产仓（原图存储）、FDD-006/008 衍生任务池（代理生成）、FDD-011/012 空间索引（可见性判断）、REQ-002 LOD 机制（zoom 分级取用）
- 证据：PureRef 官方手册 Settings（Auto optimize / Performance mode / CPU core allocation）、2.0 changelog（caching and streaming）、官方论坛 170 图实测帖（2024-05）

## REQ-004 AI 与外部工具接入（ai_providers / asset_sources / AI 编排）

**状态**：已完成（R37 verified）　**优先级**：中高（依赖迁移清单 P3 ai_providers）　**归属**：插件生态——通道一/二是插件开发，通道三机制归内核（注册表→agent 工具投影）　**提出**：2026-09-22（主人问"画布后续接入 AI / ComfyUI / 其他工具要怎么实现"）

### 背景

设计文档已铺好三条通道（§3 插槽表 `ai_providers`、§12 互操作四件套、§13 组合阶梯层 4），内核只需认契约，所有 AI / 外部工具能力均为插件，不改内核。

### 方案（三条通道）

**通道一：出站生成 — `ai_providers` 插槽（P3）**

- 统一契约：`provider.run({ prompt, refs, params }) → { 产物（图/视频/文本） }`
- 内置插件：Gemini（GEMINI_API_KEY）；第三方插件各写各的：ComfyUI provider、豆包 / WebAI2API、本地模型等
- 卡片侧表现统一：选中图片卡 → 右键/工具栏出现「重绘、扩图、生成贴图」等 node_actions → dispatch 到对应 provider
- 用户既有资产复用：art-canvas 的 smart-prompt-picker（Qwen 扩写 prompt）即 provider 插件雏形

**通道二：外部工具连接 — `asset_sources` 插槽（以 ComfyUI 为样板）**

1. 插件配置 ComfyUI 地址（`127.0.0.1:8188`），启动时探测 `/system_stats` 判定在线
2. 拖入/选中素材 → 工作流 JSON + 图片注入 ComfyUI API（`/prompt` 提交，websocket 监听进度）
3. 产物落画布：走既有导入暂存管道（R9 已验证）→ SHA-256 内容寻址进资产库（v2 格式）→ 缩略图后台派生（R6）
4. 产物为标准画布元素，带 `<comfyui.>` 命名空间元数据（seed、workflow id、节点参数）——任何插件可经 §12 四件套查询实现一键同参重生成
5. 同模式扩展：NAS、Figma、stable-diffusion-webui 均为 asset_source

**通道三：AI 编排 — §13 组合阶梯层 4**

- 不做全局节点图；内核注册表直接暴露为 agent 工具（dsh / cordis 模式），agent 拿到 commands / node_actions / providers 清单后按用户意图自行组合调用

### 工程注意点

| 注意点 | 结论 |
|---|---|
| 网络请求归属 | ComfyUI 等本地服务的 HTTP/websocket 走主进程受限代理（§12.2 进程原则），renderer 不直连——与 R5 `artflow-asset://` 同一信任级别，第三方 provider 插件不可绕过 |
| 长任务归属 | 分钟级生成任务归后台 job 体系（R8 durable journal + 重启恢复），画布关闭任务不死，重开继续收产物 |

### 验收标准

- [x] ComfyUI 产物自动入库（内容寻址）+ 缩略图派生，带 `<comfyui.>` 元数据可被其他插件查询并同参重生成（R37 verified）
- [x] 生成任务在画布关闭后不中断，重开恢复收产物（R37 verified）
- [x] renderer 无直连本地服务的网络路径（主进程代理强制）（R37 verified）
- [x] AI 编排可通过自然语言触发多命令组合执行（projectRegistryAsAgentTools 动态投影）（R37 verified）

## REQ-005 无头接入：CLI 与 MCP Server

**状态**：待开发　**优先级**：中（依赖 P2 commands 插槽落地）　**归属**：机制归本体（控制服务 / 桥接协议 / 投影机制），能力归插件（`expose: mcp` 声明制），外壳落 `builtin/headless` 受信内置插件（不可卸载）　**提出**：2026-09-22（主人问"画布的 MCP 或 CLI 要怎么开发"）

### 背景

CLI 与 MCP 都是同一个 Runtime Core 的「无头外壳」——GUI 不是唯一入口，内核注册表才是。数据层与渲染层已分离（v2 项目格式、SQLite 元数据、content store），是无头运行的地基。

### 归属决策（核心分权：壳是本体，料是插件）

| 部分 | 归属 | 理由 |
|---|---|---|
| 控制服务（localhost/命名管道 + token 握手） | **本体** | 信任边界本身——把「谁能命令画布」交给插件等于把门锁交给租客，§8 信任三档穿底 |
| 桥接协议（stdio ↔ 主进程 JSON-RPC） | **本体** | 基础设施，一次性写对所有外壳共用；做成插件引入「插件管插件」套娃 |
| 注册表 → 工具面投影机制 | **本体** | 读取内核注册表，属内核自省能力 |
| CLI `bp` 命令 | **本体** | 随应用分发，无可卸载理由 |
| 工具面内容（command / provider / node_action） | **插件** | 声明 `expose: mcp` 即自动进入工具面，MCP server 零改动；插件不允许自带 MCP server / CLI——否则 agent 需连 N 个 stdio 服务，信任面与端口面爆炸 |

行业惯例佐证：VS Code CLI、Blender `--background`/Python API、Obsidian URI scheme 均为本体，无成熟工具把外部命令入口做成插件。与 REQ-002「机制归内核、美学归插件」为同一分权原则。落地形态：`builtin/headless` 内置插件（受信内置、不可卸载）——与其他内置插件共用 manifest/加载机制，且只消费注册表 + 起服务，不持有数据层所有权，故障仅影响无头入口，不影响画布本体。

### 前提（两条硬条件）

1. **操作收敛到 `commands` 插槽**（P2）——画布上任何能做的事都注册为 command，GUI 按钮与 CLI/MCP 调用同一 `run('<ns>.<cmd>', args)`，无第二套逻辑
2. **内核不依赖 DOM**——数据/命令/注册表层可无窗口启动；Hybrid renderer 等渲染能力与无头外壳无关

### 方案

**形态一：MCP Server（面向 AI agent）**

- 架构：stdio MCP server + 本地桥接，`AI agent ←(stdio JSON-RPC)→ bp-mcp ←(localhost IPC/named pipe)→ Artflow 主进程`（uloop / tripo mcp 同模式）
- 工具面 = **注册表投影**（自动生成，非手写清单），内核零改动：

| MCP 工具 | 来源 |
|---|---|
| `list_elements` / `query_viewport` | 空间索引查询（R12 R-tree / SQLite） |
| `add_element` / `update_element` | §12 互操作出口 |
| `run_command` | commands 插槽（白名单制） |
| `search_assets` | 资产库元数据 |
| `list_commands` / `list_providers` | 注册表自省，agent 自行发现能力 |

- 信任边界：§8 信任三档兑现——第三方插件默认不进 MCP 工具面，须显式声明 `expose: mcp`
- 两种运行模式：**跟随模式**（桥接正在运行的 Electron 实例，操作实时可见）与**无头模式**（`bp serve` 无窗口实例，批量/CI 场景）

**形态二：CLI（面向自动化与脚本）**

- Node.js bin 入口，全局 `bp` 命令；CLI 与 MCP 共享同一桥接层（CLI 一次性调用，MCP 长连接会话）

```bash
bp import ./assets/*.png --board main     # 批量导入走后台 job 管道
bp export --board main --format png       # 导出
bp run comfyui.generate --prompt "..."    # 触发 command
bp mcp                                    # MCP server 子命令
```

### MCP 规格：对齐 Serpent 基线（2026-09-22 定级）

**定级结论**：经实测参考项目 Serpent-main（`H:\AI-Tools\AssetLibrary\参考项目\Serpent-main`，内嵌 MCP 约 6800 行，基于官方 `@modelcontextprotocol/sdk`），Artflow 的 MCP 必须达到同等安全与运营水位。以下为硬性规格，缺一不可：

1. **传输层（决策变更）**：主推 **StreamableHTTP 内嵌服务**（`StreamableHTTPServerTransport`），任意 MCP 客户端（Claude / Cursor / 脚本）可直连，无需逐 host 写 stdio 包装；stdio 降级为兼容项。会话上限（64 级别）、initialize 超时（60s 级）、session-idle 超时（5min 级）、请求体上限（1MB 级）。跟随/无头双模式不变。
2. **多凭证认证**：每个外部 agent 一个**独立凭证**（Bearer token），支持创建 / 重命名 / 撤销 / 列表；单一共享 token 不合格——多凭证才能按 agent 收回与限权。
3. **权限模式（按凭证）**：`read-only` / `full-access` 两档。read-only 只投影 impact=read 的工具；**插件工具仅在 full-access 下暴露**（插件命令默认按非只读处理）。
4. **两阶段挑战（危险操作硬防线，Serpent 核心机制）**：声明为 destructive/critical 的 command——
   - 第一次调用**不执行**，返回一次性 `challengeId + planHash` 风险报告；
   - 第二次调用必须**原样回传** `challengeId + planHash + acknowledged:true + 非空 idempotencyKey`，挑战一次性消费；
   - 确认字段在 broker 消费后剥离，不进入 worker schema；挑战不可用调用方自选值替换。
5. **插件曝光双层门**：manifest `mcp.export` 声明（静态）+ 设置中心**逐插件逐命令运行时开关**（动态，参考 Serpent `PluginMcpExposureStore`）；工具面重名即报错，禁止静默覆盖。
6. **工具面元数据**：每工具必带 `annotations`（readOnlyHint / destructiveHint / openWorldHint:false）、`outputLimit`（超限截断，防 agent 上下文爆炸）、risk/approval 级别写入 description；服务器在 initialize 时下发 **instructions**（目标规则 / 挑战协议 / 发现路径，agent 不用猜）；库级操作 schema **强制注入显式 boardId**——「桌面当前焦点永远不是隐式目标」。
7. **工具名卫生**：注册表投影时正则拒绝 `eval / shell / sql / fs / exec / net / process` 等字样入工具名。
8. **可观测性闭环**：结果回传 journal id / `undoGroupId`（对上 R8 job journal 与操作历史）；执行完成联动桌面通知（仅非只读实际执行时）；progress 通知透传；工具面变化走 `toolsChanged` 推送。

### 开发顺序

1. P2 commands 插槽落地（前置，否则两形态为空中楼阁）
2. 主进程**内嵌 StreamableHTTP 控制服务**：端口段探测避让 + 多凭证 store + 按凭证权限模式（Serpent `embedded-mcp-server.ts` 为同构参考，894 行量级）
3. **权限 broker + 两阶段挑战 store**（dangerous command 的一次性挑战签发/消费，Serpent `mcp-permission-broker.ts` + `mcp-operation-challenge` 同构）
4. `bp-mcp` 工具面投影（annotations / outputLimit / instructions / 工具名卫生 / 显式 boardId 注入）+ 插件 `mcp.export` 桥
5. CLI 薄壳复用同一桥接（`bp run` / `bp mcp` 子命令）

工作量集中在第 2、3 步（服务与权限层）；第 4、5 步为投影与薄封装。额外收益：§13 层 4 AI 编排直接复用同一工具面，内部 agent 与外部 agent 吃同一份注册表、同一套挑战与权限。

### 验收标准

- [ ] `bp run <command>` 与 GUI 触发同一 command 路径，行为一致
- [ ] MCP 工具面随插件注册自动增减，无手写工具清单；插件工具受 `mcp.export` 声明 + 运行时开关双层控制
- [ ] StreamableHTTP 服务可被标准 MCP 客户端直连；多凭证独立创建/撤销，单凭证撤销不影响其他客户端
- [ ] read-only 凭证调用任何写类工具被拒绝；full-access 才可见插件工具
- [ ] 危险 command 首次调用只返回 challenge，不执行；正确二次确认才执行；错误/重复/替换挑战被拒绝
- [ ] 每个工具带 annotations 与 outputLimit；库/板级工具 schema 强制 boardId，缺省拒绝
- [ ] 工具名含 eval/shell/fs/exec 等禁词时投影报错
- [ ] 结果含 journal id / undoGroupId；无头模式全流程不启动渲染窗口；跟随模式操作实时可见
