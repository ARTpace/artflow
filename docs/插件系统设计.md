## 1. 设计目标与不可变原则

以下原则是**立基决策，任何后续迭代不得违背**：

| # | 原则 | 内容 | 业界依据 |
|---|---|---|---|
| 1 | 一切皆插件 | 内置功能与第三方插件走**同一 manifest 通道**，无特殊路径 | AssetLibrary `src/builtin/` 11 个内置功能全带 manifest；dsh 连 llm/session 核心都是 patch 行 |
| 2 | 内核零业务逻辑 | `plugins/` 只做机制（注册/校验/装载/分发），不出现任何具体功能 | dsh 启动器仅三件事：boot/插件管理/别名 |
| 3 | 数据优先 | 能用 JSON 声明的贡献（皮肤/格式声明）绝不写代码；数据型贡献在宿主重构中存活率最高 | Blender bl_info→toml 演进轨迹；VS Code 声明式 contributes |
| 4 | 可逆性 | `register/provide/on` 全部返回 disposer，卸载即逐项撤销，插槽清空（冒烟已验证） | AssetLibrary/Cordis register 语义 |
| 5 | 命名空间隔离 | 贡献 id 强制 `<ns>.<name>`，同 id 同插槽不可重复 | Blender 4.2 因插件撞名被迫加 `bl_ext.<仓库>` 前缀；Obsidian 命令 id 自动加插件前缀 |
| 6 | 契约只加不改 | 契约类型演进只允许新增可选字段（详见 §5） | VS Code「大版本更新不坏插件」的核心纪律 |
| 7 | UI 必须走贡献通道 | 任何新面板 / Settings section / 浮层 / 工具栏一律以 `ui_panels` / `settings_sections` / `canvas_widgets` / `ui_toolbar` 贡献项落地，禁止硬编码进 App；机制缺失时**先建机制再上功能**，确需先行出功能的必须在台账登记「插件化欠条」并进《插件化迁移清单》P2 | R18–R22 五面板先例：机制未建就写进本体，形成 5 项待迁债务（2026-09-22 审计） |

## 4. Manifest v1 契约

已实现（`plugins/manifest.ts`，手写严格校验、未知字段拒绝）：

| 字段 | 说明 |
|---|---|
| `id` / `name` / `version` | 身份三元组；id 即命名空间 |
| `capabilities` | 能力声明，枚举：`format.handler / canvas.card / canvas.tool / ui.panel / ui.settings / ui.skin / command / ai.provider / exporter` |
| `config` schema | 可配置字段及类型（boolean/number/string），供设置面板自动渲染 |
| `resourceBudget` | maxActiveInstances / maxMemoryMB / maxConcurrentJobs |
| `host` | 单个受控 host：worker / renderer / main（v1 是 singular，非 `hosts`） |
| `contributes` | manifest 可 JSON 表达的贡献数据；executable format parser 在 activate 中注册 |
| `minHostVersion` | ✅ 可选 plugin contract API 最低版本；不兼容 builtin 单独跳过并警告 |

**后续新增**：

| 字段 | 说明 | 依据 |
|---|---|---|
| `permissions`（P4 用） | 第三方能力申请 | Blender 4.2 manifest 权限声明制 |

## 5. 契约演进策略 ——「宿主更新不影响插件」（核心章节）

**结论先行：插件因大版本更新失效不是宿命，是维护投入的选择。** VS Code 用四条纪律做到大版本基本不坏插件；Blender 反面（快升级+人工迁移）。Artflow 立基规矩六条：

1. **契约只加不改不删**：所有对外契约（SkinTokens/FormatHandler/manifest 字段）只允许新增**可选**字段；禁止改名、删除、收紧已有类型。做到这条，老插件对宿主永久兼容。
2. **manifest 版本并行窗口**：`MANIFEST_VERSION` 出 v2 时，loader 同时支持 v1+v2 渡过整个过渡期，绝不"切换即断"。
3. **引擎区间**：manifest 声明 `minHostVersion`；loader 装载时校验，不兼容→插件列表中标注"需更新"并跳过激活，给出原因。
4. **弃用周期**：要移除插槽/字段/能力时，先打 `deprecated` 标记 + 控制台警告，**至少保留两个小版本**才可移除。
5. **数据优先**：新插槽设计时先问"能否纯 JSON 表达"；React 组件类贡献只授予受信插件（§8），因为组件 = 宿主权限，天然易碎。
6. **版本钉死可回退**（P4）：第三方插件版本进 lockfile（dsh profile 模式）；宿主升级后旧插件环境保持可复现，用户自选升级时机。

**三方各自的责任**：
- 宿主：守契约纪律、弃用警告、minHostVersion 校验
- 内置插件：随宿主同仓升级，永远兼容（同 lock）
- 第三方插件：声明 minHostVersion、依赖随包自带（**禁止 import 宿主未导出的内部模块**，loader 可静态检查）

## 6. 冲突消解（多插件声明同一能力）

适用于所有插槽（两个插件都支持 PDF、都贡献 pdf 卡片、都能生图……）：

| 规则 | 内容 |
|---|---|
| ① 注册共存 | id 不同即不冲突，插槽照单全收；同 id 重复才 throw（那是 bug） |
| ② 静默分发按优先级 | 分发沿 `list()`（内核已按 `priority` 降序排序）取第一个匹配者，确定性无歧义 |
| ③ 用户绑定最高 | settings 存「扩展名→handlerId」绑定表，用户指名谁就用谁（dsh patch 模式） |
| ④ 冲突可见性 | 设置面板展示重叠声明：「PDF 当前由 X 处理，另有 Y 声明支持」。**分发可以静默，冲突必须可见**——Blender 零提示导致社区被迫造 Deconflicter 的教训 |

远期红利：共存 + ③ 可自然长出「打开方式」右键菜单。

## 7. 插件开发流程（更简单更便捷）

**现状三步**（已被两个内置插件验证）：

```
1. builtin/<name>/manifest.json   （能力/配置/资源预算声明）
2. builtin/<name>/index.tsx       （可选：activate(ctx) 注册贡献）
3. builtin/index.ts               （追加一行）
```

无构建管线（vite 直吃源码）、HMR 秒生效（优于 Blender 关开重载 / Obsidian 重打包）、与宿主共享依赖（builtin 特权）。

**DX 工具箱（P0 随机制层一起交付）**：

| 工具 | 作用 |
|---|---|
| `definePlugin()` | ✅ 最小类型化 builtin definition helper；runtime manifest 仍由严格 validator 裁决 |
| 插件模板目录 | `builtin/_template/`：后续最小可跑样例，复制改名即起步 |
| 调试口 | 控制台 `__bpKernel`（查插槽/贡献/服务）、`__bpSkinEngine`（换肤）；✅ R28 Command Palette 是统一用户入口 |
| 契约测试 | 冒烟脚本固化为 npm script（装载/注册/卸载全链路），宿主与插件 CI 共用 |

**依赖策略**：builtin 插件共享宿主依赖（同源码同 lock，天然一致）；第三方插件（P4 起）依赖**必须随包自带**（Blender wheel / Obsidian esbuild 打包同款规则），杜绝"插件 A 升级依赖搞坏插件 B"。

## 8. 信任模型（三档，P4 完整落地）

| 档 | 运行环境 | 能力 | 对应 |
|---|---|---|---|
| `builtin` | 进程内直跑 | 全部（含 React 组件贡献） | 现状 ✅ |
| `restricted` | 沙箱（QuickJS + JSON-only RPC + iframe UI） | 仅数据型贡献（皮肤/格式声明/命令），**不得提供 React 组件** | AssetLibrary ADR-001 + sandbox.ts（263 行可复用） |
| `unrestricted` | 独立进程 | 宿主授权的能力面 | 远期 |

开放第三方前必须定 ADR：组件贡献 = 宿主权限，restricted 档不给。

### §8.1 unrestricted 档落地记录（ADR，2026-10-10）

**裁决**：组件贡献 = 宿主权限。第三方插件申请 client.js 组件贡献（画布卡片 / 覆盖层 / 面板的 React 组件）时，安装流程必须弹风险确认；确认即授权，卸载即撤销。sandboxed（restricted）默认档保留，两档并存。

**机制**：
1. **capabilities 声明**：manifest 白名单 `['components', 'format', 'commands', 'panels', 'assets']`；`components` 是组件贡献的显式申请（带 client.js 即视为申请），缺省 = 仅数据型贡献
2. **安装确认**：`inspectPluginDirectory` → main.cjs 安装 handler 弹 `showMessageBox`（warning + 能力清单 + 数据权限），拒绝即中止安装
3. **大数据通道**：plugin.js `Artflow.files.storeInput() / store(bytes)` → 主进程 `plugin-store/<pluginId>/<sha256>.bin`（内容寻址去重，单文件 ≤512MB）→ client.js 组件 `Artflow.storage.read(ref)` 读回；卡片 fields 只放 ref 不放字节（100KB fields 上限不变）
4. **parse 上限**：8MB → 512MB；`pendingParseInputs` 暂存原始输入，`storeInput()` 免二次传输
5. **边界声明**：pluginId 隔离是**契约层**（external-runtime 绑定 + 主进程格式校验防路径穿越），非强安全边界——强边界仍在 plugin.js 沙箱层；渲染进程本身是 trusted 域（与 builtin 同级）
6. **插件漫画档案通道**：plugin.js `Artflow.files.openArchiveInput()` 一步完成「暂存输入落仓 → ZIP 引擎解析页清单」，返回 `{ref, pageNames, pageCount}`；client.js 组件 `Artflow.storage.readPage(ref, index)` 按页拉取——与内置阅读器**同一 ZIP 随机访问引擎**（原生 zlib + 句柄/页双层 LRU），第三方阅读器与 builtin 性能持平。归入 `format` + `components` 能力，不新增 capability 档位

**验证**：check-core-foundations（数据仓单元断言 + 插件档案通道端到端 + 信任契约源码断言）。

## 9. 生命周期

```
discover → validate(manifest 严格校验) → register(contributes 逐项入插槽)
        → activate(ctx) → [运行] → disable/dispose(disposer 逐项撤销)
```

- compatibility 隔离：`minHostVersion` 不兼容的 builtin 单独跳过并警告；其他 manifest / activation 异常在 v1 仍显式失败，避免静默吞掉可信 builtin 的编程错误
- `disabled` 支持（P4 用户 patch 层）：用户层记录 `{id, disabled}`，装载最后叠加、后写胜出——核心插件也可被用户关（dsh 实证）
- 热更新：builtin 随 vite HMR 白赚；第三方（P4）参照 dsh `patchReload: live`

## R30 实施注记：`ui-plugin-manager` staged Settings profile（verified）

- `settings_sections` is a generic trusted-renderer contribution surface. `CanvasSettings` only lists registered label/component entries; it neither imports nor names the manager, profile storage or any builtin id.
- `builtin.ui-plugin-manager` uses only `kernel.use(PLUGIN_PROFILE_MANAGER_SERVICE)`. It presents manifest/profile status and stages enable overrides through the already-existing user profile patch, while startup/reload remains the only loader activation path.
- No hot unload, marketplace, external plugin execution, config editor or permission center was smuggled into this UI. A narrow bootstrap recovery rule prevents its sole Settings recovery section from disabling itself. Remote `typecheck`、`check:foundations`、production full `check` and canonical read-back passed.

## R29 实施注记：`formats-book` bounded EPUB plain-text ReaderCard（verified）

- 同一 trusted `builtin.formats-book` 同时贡献 extension-only `.epub` format handler 和 existing `reader` card。`epubParser.ts` 独占 `fflate`、OCF container、OPF manifest/spine、安全 local href/path 以及 archive/text/chapter/output bounds；generic `.zip` 没有改变路由。
- Only `ReaderElement.sourceFormat: 'epub'` crosses the generic boundary. Importer materializes bounded plain text and CanvasElement still discovers the card generically; it contains no EPUB/ZIP/OPF/parser/card business. ReaderCard labels the result `EPUB → text`, not a rich XHTML surface.
- R29 deliberately rejects/omits rich layout, CSS/resource/media/fonts, external links/scripts/DRM, TOC/chapter UI, pagination/progress/annotations/search and archive persistence. Remote `typecheck`、`check:foundations`、production full `check` and canonical read-back passed.

## R28 实施注记：`commands-workspace` Command Palette（verified）

- `plugins/commands.ts` and `command-palette.tsx` only consume ordered `commands` contributions. They contain no builtin id/title/action business; `Ctrl/⌘K` is the generic palette trigger and normal registry priority/id resolves an exact shortcut collision.
- `builtin/commands-workspace` is a normal `command` capability plugin. It calls only `kernel.use(workspace.command-actions)` at invocation; App exposes a narrow live renderer action proxy rather than importing plugin code or inspecting command ids.
- R28 deliberately preserves existing undo/redo/copy/delete/presentation hotkeys. Capture dispatch stops a contributed shortcut before legacy listeners; user binding persistence/conflict settings/macros and toolbar/menu/tool migration remain separate P2/P4 work. Remote `typecheck`、`check:foundations` and production full `check` passed.

## R27 实施注记：`formats-comic` bounded CBZ ComicCard（verified）

- 一个 trusted builtin must contribute both `format_handlers` and `canvas_node_types`; CBZ parsing, `fflate`, data URI generation and page navigation never enter generic host files.

## 12. 插件间协作（互操作设计）

**铁律：插件之间禁止直接 import——一切协作经宿主中介的三个通道。**

| 通道 | 机制 | 现状 |
|---|---|---|
| 服务 | `provide(serviceId, api)` / `use(serviceId)`；use 不存在时返回 undefined（优雅降级） | ✅ 内核原语已有 |
| 事件 | `on(event, cb)` / `emit(event, payload)` | ✅ 内核原语已有 |
| 共享数据模型 | 插件读写画布元素字段，消费端只认数据不认来源（Blender datablock 模式） | ✅ 元素即数据模型 |

**UI 组合点（规划）**：新增 `node_actions` 插槽——插件贡献 `{target: 'canvas_node_type:<type>', label, icon?, handler}`；卡片渲染时查询该插槽渲染动作按钮。配合服务通道实现跨插件功能组合，如「贴图生成插件 + 3D 预览器」：贴图插件贡献动作 + provide 服务 → 动作调服务生成贴图 → 写入元素 textureUrl → emit 更新 → 3D 卡片重渲染。两插件互不感知，可独立启用（缺失时按钮不渲染，功能变少而非报错）。

**守则**：① 特性检测查能力/服务，禁止查插件 id（Obsidian 插件直连 dataview.api 的连锁死亡反例）；② 服务契约与贡献契约同受 §5「只加不改」约束；③ 跨插件写入元素数据须走约定字段（考虑 P2 加字段命名空间 `<ns>.<field>` 防撞）。

**画布连通的四件套**（互操作落到画布的具体接线）：

| 件 | 机制 | 状态 |
|---|---|---|
| 元素数据 | 连接点：插件字段带 `<ns>.` 前缀写入元素（如 `texturegen.textureUrl`） | 约定 |
| `node_actions` 查询 | 卡片渲染时查插槽出动作按钮（ActionHost，全卡片通用） | 规划 |
| `ctx.updateElement(id, patch)` | **唯一新增宿主 API**：插件写元素必须经此（走 React 状态 + 历史/撤销），禁止直接改 element 对象 | 规划（包装 useElementActions 现有逻辑） |
| props 回流 | 元素更新 → React 状态 → 卡片 props → 自动重渲染 | 现有机制 |

事件只做通知不做数据传输（数据以元素为准，防状态分叉）。

## 13. 组合交互范式（决策：四层阶梯，不做全局节点图）

**背景**：节点图（ComfyUI/Blender GN 式）把拓扑暴露给用户，节点一多使用难度陡增。业界替代方案的本质都是「把拓扑藏起来」。**决策：Artflow 不做全局节点图，采用四层组合阶梯**——插件间协作沿用 §12 四件套，交互触发器按用户投入程度分四层：

| 层 | 交互 | 触发器 | 机制 | 适用 | 业界实证 |
|---|---|---|---|---|---|
| 1 自动组合（默认） | 零操作 | 功能以按钮出现在该出现的卡片上 | `node_actions` 插槽 | 80% 日常场景 | Obsidian/Figma 插件 |
| 2 磁贴拖放 | 直觉空间操作 | 拖 A 卡到 B 卡槽位，悬停高亮，松手生效 | `card_slots` 插槽（node_actions 姐妹）：卡片声明 `{slots:[{id, accepts, onDrop}]}`；拖拽命中检测挂在现有 useCanvasInteractions 上 | 「素材喂给处理器」类二元组合 | FCPX 磁性时间线 / OBS / Notion 嵌套 / iPadOS 拖放 |
| 3 动作链 + 配方 | 进阶 | 把多步操作排成线性链，存为一键配方 | 基于 `commands` 注册表（P2 后可用），列表 UI 而非画布 | 多步流水线（磁贴嵌套 5 层以上的场景） | Apple 快捷指令 / Zapier / Photoshop 动作 |
| 4 AI 编排 | 一句话 | 用户说意图，AI 调用服务/命令组合执行 | 内核注册表直接暴露为 agent 工具（dsh agent loop + cordis 模式），Gemini 通道现成 | 「我想要结果」型用户 | dsh / Raycast AI |

**磁贴层细则**：
- 停靠显示为**芯片/引用**（存源卡片 elementId，点击定位），不整卡内嵌——避免嵌套卡片的选中/层级/布局复杂化
- 拖出芯片 = 解除（清字段，disposer 语义）
- 槽位可发现性：悬停高亮 + 空槽虚线占位 + 拖动时的 drop 提示
- 底层与 §12 四件套完全同构：磁贴只是"按钮"之外的第二种触发器，数据落点仍是 `ctx.updateElement` + 命名空间字段

**节点图的定位**：只在单个插件**内部**作为领域可视化编辑器出现（如未来材质编辑器），插件**之间**的协作永远走本阶梯——Blender 的分工先例（几何节点是节点图，插件协作不是）。

**依赖关系**：层 1 随 P1（node_actions）；层 2 依赖拖拽系统改造，P2 起；层 3 依赖 P2 commands；层 4 依赖 P3 ai_providers。

## 14. 插件增强操作能力（快捷键与画布工具）

**背景**：Blender 生态证明插件不只是"加内容"，还能**改造操作方式**——快捷键、专属交互模式（modal operator，如 BoxCutter 画切割线）。Artflow 分两档承接：

**轻改档：commands + keybinding（对标 Blender operator + keymap）**

| Blender 插件 | Artflow 对应 |
|---|---|
| 注册 operator（`bl_idname` 命名空间） | 贡献 `commands`：`{id: '<ns>.<name>', title, handler, keybinding?}` |
| keymap 绑定 | command 的 `keybinding` 字段（插件给**默认建议值**，非最终裁决） |
| 用户 keymap 覆盖 | 用户绑定表最高优先（§6 规则③） |

**重改档：`canvas_tools` 插槽（对标 Blender modal operator）**

- 插件贡献 `{id, cursor, onPointerDown/Move/Up, onKey}`；工具栏自动出现该工具按钮
- 用户激活后，内核 useCanvasInteractions 把指针/键盘事件**转发**给该工具；工具退出（Esc / 失焦 / 超时）后控制权归还内核
- **红线：事件转发，不是事件劫持**——内核始终是调度方，插件拿到的是租借窗口；Esc 与超时强制归还，保证任何第三方的交互再激进也抢不走画布基础稳定性
- 激活中的工具有视觉态（光标 + 状态栏提示），同一时刻至多一个工具激活

**冲突裁决**：快捷键与工具冲突沿用 §6 四规则（注册共存 / 优先级分发 / 用户绑定 / 冲突可见性），Blender 的「用户 > 插件 > 内置」分层即规则③的实现。快捷键冲突提示在 P2 命令面板中展示。

**信任边界**：交互型贡献（指针事件流）比数据型贡献权限更深，第三方（restricted 沙箱）默认只给 commands/keybinding 级；`canvas_tools` 建议主要作为内置插件开发（Blender 插件操作方式自由的前提是 Python 全权限裸奔，Artflow 的对应物就是 builtin 档）。

## 15. 内容型卡片（WebApp 卡与 Python 脚本卡）

**产品隐喻**：画布即桌面、卡片即应用——拖入网页游戏即可玩、拖入 `.py` 即可运行。两者是同一插件模式（内容类型→卡片）的两个实例：

| 拖入内容 | 插件通道 | 落成卡片 |
|---|---|---|
| `.html` / 游戏 zip（HTML5 / Unity WebGL / Godot web 导出） | `format_handlers` 注册解析 + `canvas_node_types` 贡献 | **WebAppCard**：iframe 内嵌 |
| `.py` 脚本 | `format_handlers` 注册 `.py` + 脚本卡贡献 | **PythonCard**：编辑器 + 运行输出 |

### 15.1 WebApp 卡技术要点

1. **服务方式**：iframe 直连 `file://` 受限（相对资源 / fetch / wasm 流式编译均不可用）。Electron 侧注册自定义协议 `bpapp://<elementId>/` 指向该元素的资源目录，iframe 内即"真网站"——Electron 嵌本地网页的标准解法
2. **沙箱**：`sandbox="allow-scripts allow-pointer-lock allow-fullscreen"`，无 nodeIntegration——第三方网页内容天然被 §8 信任边界兜住
3. **交互冲突**（关键坑）：游戏要吃键盘鼠标，画布也要。复用 §14 的 `canvas_tools` 控制权协议——卡片默认"未激活"（可拖动选中），点击"进入"后事件租借给游戏（指针锁定 + 键盘全给），**Esc 退出归还**。工具与游戏共用同一份事件租借机制，机制层只写一次
4. 音频 / 指针锁定由 iframe 属性开启，无需特殊处理

### 15.2 Python 脚本卡（对应此前设计的运行时双轨）

- 形态：`builtin/script-python` 插件 `provide('python', {run})` + PythonCard；输入输出走 §12 四件套（元素数据进出，脚本与其他卡片平级协作）
- 双轨运行时：**Pyodide**（WASM，零安装、天然沙箱、numpy 可用但慢 2-5 倍）为默认；**本机 Python**（Electron utility process + IPC，全速 + 完整 pip）为增强档
- 脚本能调用的 API 只有显式桥接面（读元素 / 写元素 / 发事件），非全量宿主——`bpy` 式受限领域 API

### 15.3 边界与本质

- **脚本 ≠ 插件**：脚本没有 manifest、不进插槽、不注册快捷键，只是 PythonCard 里运行的内容。若让脚本进插件体系，"任意执行的 Python"会直接击穿 §8 信任三档
- **方案 B 必须走主进程**：渲染进程禁止 child_process；脚本崩只崩自己的 utility process
- **可扩展性本质**：宿主内核只认三张通用契约——文件进（format_handlers）、卡片出（canvas_node_types）、事件租借（canvas_tools 协议）。在此之上"拖进来的东西能不能用"不再是宿主功能清单，而是插件生态的广度（游戏 / Python / 未来的 Jupyter、表格、Figma 嵌入……均不改内核）

**排期建议**：WebApp 卡（bpapp:// 协议 + 事件租借激活）与 PythonCard（Pyodide 档）互不依赖，可并行；建议排在 P2 canvas_tools 之后（复用事件租借协议），Pyodide 增强档（本机 Python）依赖 P4 的主进程 IPC 约定。

### 15.4 应用卡资源生命周期（内存预算）

应用卡（WebApp / Python / 游戏）与普通媒体卡的本质区别：**每个实例都是一套活的运行时**。单实例内存量级参考：

| 实例类型 | 实现方式 | 单卡内存量级 |
|---|---|---|
| WebApp 卡（iframe） | bpapp:// + iframe | 基础 JS 堆 + DOM 约 50–150MB；跨域内容 Chromium 拆独立进程（OOPIF），另有进程开销 |
| HTML5 游戏 / Unity WebGL | 同上 + wasm 堆 + 纹理 | 200MB–1GB+ |
| Python 卡（Pyodide） | WASM 解释器 | 解释器本体约 30–80MB，numpy 加载后再涨；**解释器全局共享一个实例**，多卡只隔离脚本上下文 |
| 本机 Python（增强档） | utility process | 独立进程 ~30MB + 脚本自身开销；崩只崩自己 |

结论：画布里应用卡总数不决定内存，**同时处于激活态的数量**才决定。三层兜底机制：

1. **激活预算 + LRU 淘汰**：同时激活的应用卡设硬上限（首期建议 3–5，实测校准），归属 §9.3 富媒体预算的扩展项；超出预算时最久未交互的实例自动降级，UI 必须可见地告知（复用 §6 冲突可见性原则），点击快照即重新唤醒并排队。
2. **视口驱动生命周期**：卡片滚出视口或降至 LOD 低档 → 冻结（挂起 iframe / 暂停 rAF 与音频 / 停 Pyodide 执行）；回到视口恢复。挂在 Phase 3 Hybrid renderer 的 LOD 分档上，不另造机制。
3. **状态保留档位由卡片声明**：WebApp 插件 manifest 新增 `stateful` 字段（布尔或档位）——
   - `stateful: false`（浏览器类、工具页）→ 降级为**静态快照**（截图 + 缩略图），进程与内存几乎归零，应用内部状态丢失可接受；
   - `stateful: true`（游戏、有状态交互应用）→ 降级为**冻结挂起**，内存保留但 CPU/渲染归零，状态完整保留。

降级顺序与 §9.3 富媒体预算共用同一套 LRU：视频 / 3D / 音频 / 应用卡在同一预算池内竞争，按「最近交互时间 + 单卡内存成本」排序淘汰。

**工程边界**：快照截图走 Electron capturePage / 离屏渲染；冻结 iframe 用 `src` 置空，状态恢复由应用自行处理——浏览器层无法可靠序列化第三方网页内部状态，不做承诺。本节排期跟随 P2 canvas_tools 之后的 WebApp 卡落地，预算上限值在 §4 性能契约的压测阶段校准。

## 16. 多人共享画布（协作插件设计）

**定位**：画布可经插件扩展为多人实时协作（对标 Excalidraw 房间 / Miro / Figma 多人模式）。协作引擎本体不碰内核内核业务——CRDT 用现成轮子（Yjs），传输用现成库（trystero 免信令服务器 / y-webrtc）——**内核只新增一个「文档同步面」+ 一个覆盖层插槽**，机制增量约 300-500 行。

**四层能力归属**：

| 层 | 干什么 | 归属 |
|---|---|---|
| 传输 | 房间连接 / 打洞 / 断线重连 | 插件自含（trystero 走公共信道，无需自建信令服务器） |
| 状态同步 | 元素增删改多端一致 | 插件用 Yjs：元素 JSON ↔ Y.Map，增量同步 |
| **文档同步面** | 内核把画布状态喂给同步层 | ⚠️ 内核新增（见下） |
| 存在感层 | 远端光标 / 选区高亮 / 头像 / 视口指示 | ⚠️ 内核新增 `canvas_overlays` 插槽 |

### 16.1 内核同步面（四个增量 API）

| # | API | 作用 | 关键点 |
|---|---|---|---|
| 1 | 细粒度变更事件 | `element:added/updated/removed`（带 patch） | 现在元素更新只在 React 状态里，插件拿不到增量——同步层靠它喂数据给 Yjs |
| 2 | `applyRemoteOps(ops)` | 远端变更批量回写 | **必须绕过本地撤销栈**——否则 B 的 Ctrl+Z 会撤销到 A 的操作上；与 `ctx.updateElement` 并列的新宿主 API |
| 3 | `canvas_overlays` 插槽 | 非交互装饰层（SVG/HTML 浮层） | 远端光标/选区/头像渲染于此，不进元素数据、不参与交互命中 |
| 4 | 选区多归属（后置） | 「我选了什么」从全局单份改为按用户分 | 对 useCanvasInteractions 动一小刀；一期可用「远端只显示光标不显示选区」绕过 |

### 16.2 已知坑与对策（Excalidraw 趟过的路）

| 坑 | 对策 |
|---|---|
| 两人同时拖同一元素 | Yjs 保证最终一致但过程打架；拖动中加锁 / 光标跟随缓解 |
| 并发改 z-order | CRDT 可收敛但视觉可能跳；接受即可 |
| 广播 = 画布全部数据出网 | **协作插件必须 builtin 档开发**——它看得见一切，不开放给第三方 |
| 撤销栈污染 | 规则 2 的 applyRemoteOps 专为此设计 |

### 16.3 架构与分期

```
builtin/collab-yjs/        ← 一个普通内置插件
├── manifest.json           contributes: { service: 'collab', canvas_overlays }
├── index.tsx               provide('collab', {join(room), leave, onPresence})
└── sync/
    ├── yjs-bridge.ts       元素 JSON ↔ Yjs 文档双向桥（消费同步面四 API）
    └── transport.ts        trystero / y-webrtc
```

分期：① 光标共享（只读存在感，最小可用）→ ② 元素级同步（读写全量）→ ③ 选区共享 + 房间管理 UI（第一个真正的 ui_panels 复杂住户）。排期建议 P2 之后（依赖同步面与 overlays 落地），与 §15 内容型卡片可并行。

## 18. 画布浮动件（界面按键、电子宠物与虚拟角色）

**两层需求，两种机制**：

**① 界面按键——完全由现有插槽覆盖，零新增**：

| 按键位置 | 插槽 |
|---|---|
| 顶部/侧边工具栏按钮 | `ui_toolbar`（P2） |
| 右键菜单项 | `ui_menus`（P2） |
| 卡片上的动作按钮 | `node_actions`（§12） |
| 可停靠面板 | `ui_panels`（P1） |
| 自定义交互模式（非按钮） | `canvas_tools`（§14） |

**② 电子宠物 / 虚拟角色——新概念 `canvas_widgets`（画布浮动件）**

宠物与卡片的本质区别：卡片是**画布数据**（元素、参与拖拽/选中/撤销），宠物是**画布伴生物**（自有动画循环、不进元素数据模型、不受选区影响）。

```
canvas_widgets 插槽（规划）：插件贡献
{ id, layer: 'pet' | 'hud',     ← 渲染层级（角色层 / HUD 层）
  component,                     ← 完全自主的 React 内容
  active }                       ← 显隐（用户可开关）
```

**技术选型（全现成）**：

| 形态 | 方案 | 成本 |
|---|---|---|
| 精灵图宠物 | 序列帧 / CSS steps 动画 | 最轻 |
| 二次元 Live2D | `pixi-live2d-display`（PixiJS 渲染） | 中 |
| 3D 虚拟角色 | `@pixiv/three-vrm`（VRM 模型，three.js 宿主已有依赖） | 中 |

**能力接线（全部走既有机制）**：
- 智能：接 `ai_providers`（P3）+ TTS → 宠物 = 角色 skin + AI 对话；订阅 `on('element:added')` 等事件做反应式互动
- 与画布互动：指针事件用 `canvas_tools` 租借协议；操作元素走 `ctx.updateElement`——宠物与普通插件在权限模型中平级
- 持久化：宠物位置/状态存 localStorage（useSettings 模式），**不进画布文档**——协作时默认不跨用户同步（远期可作为 presence 趣味扩展广播"我的宠物"）

**性能红线**：widget 动画循环由插件自管，宿主提供**挂起钩子**（画布失焦/最小化时暂停 rAF）；多 widget 并存时 GPU 预算入 `resourceBudget` 约定。

**排期**：`canvas_widgets` 机制层很薄（一个浮层 + 显隐管理，约百行），可随 P1 PanelHost 顺带；宠物/角色插件本体依赖 P3 ai_providers 才"活"，纯形象展示则随时可做。

## 19. 皮肤与插件 UI 主题化（token 中转站）

**核心原理**：皮肤不认识"界面"，只认识 token。换肤 = 皮肤插件重新声明一组 SkinTokens → SkinEngine 展开为 `--bp-*` CSS 变量 → 全应用任何 UI（**无论本体还是插件渲染**）只要消费变量就自动跟随。因此"美化到插件"不靠给每个插件做皮肤，靠以下三条规则：

### 19.1 规则一：插件 UI 必须消费 token

`ui_panels` / `ui_toolbar` / `canvas_widgets` 贡献的按钮、面板、浮层，样式一律写 `var(--bp-accent)` 等 token 变量，禁止写死色值。与 §1 原则 #7（UI 必须走贡献通道）同级别的开发纪律。

### 19.2 规则二：插件个性化色走 accents 同款机制

卡片已有先例（`--bp-card-accent-<type>`，未声明回落全局 accent）。插件同理：manifest 声明品牌强调色 → 展开为 `--bp-plugin-accent-<ns>` → 皮肤作者**可覆盖也可放行**。插件个性与皮肤全局不打架。

### 19.3 规则三：SkinTokens 扩容清单（契约只加不改，全部新增可选字段）

现有 token（cardBg/cardBgAlt/accent/accentSoft/border/textPrimary/radius/accents）只够美化卡片，不足以美化按键与面板。扩容（老皮肤不填回落 DEFAULT_SKIN，零破坏）：

| 新增 token | 用途 |
|---|---|
| `panelBg` / `panelBgAlt` | 插件面板底色 / 次级区 |
| `btnHover` / `btnActive` / `btnDisabled` | 按键三态（按键美化的主体） |
| `fontFamily` / `fontSizeBase` | 全站字体 |
| `shadow` / `spacing` | 面板阴影、间距节奏 |

### 19.4 零成本兜底：预置语义 CSS 类

SkinEngine 附带一组语义类：`bp-btn` / `bp-panel` / `bp-chip` / `bp-input`。插件开发者**套类名即自动跟随所有皮肤**，一行样式不用写；皮肤作者只管 token。参照 Obsidian CSS variables 体系与 shadcn 语义类——皮肤作者与插件作者互不接触对方代码。

### 19.5 写死颜色的插件（残余容忍）

机制管不死、也不必管死：内置插件我们自己遵守 token 纪律；第三方插件到 P4 沙箱阶段把「token 覆盖率」列为审核质量项。Obsidian 对硬编码插件同样无解，社区接受该残余。

**排期**：token 扩容与预置类属 SkinEngine 机制层小改（contributions.ts + skin-engine.ts 各一段），建议随下一个触碰 UI 的 FDD 顺带落地；`panelBg`/按键三态在 P2 UI 外壳迁移时为硬前置（迁移本体面板同样要消费它们）。
