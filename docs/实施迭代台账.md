## P1-B' 相机瞬时通道（滚动/缩放解耦）

- 根因：平移/滚轮缩放/拖动都逐帧写顶层 `boards` → App 整棵函数体重跑（全项目只有 CanvasElement/SVGDefs/GalaxyStarLayer 做了 memo），叠加每帧 O(元素数) 派生数据（workspaceMetrics 的 reduce+filter、viewport-index.update 的逐项扫描、isElementVisible 的 find 找 parent）与每帧强制同步布局（悬浮工具条 effect、滚轮每事件量布局、getCanvasPoint 每帧两次量布局）。相机写入还会把项目标脏，只挪视角 1.5s 后触发自动保存。见 ADR-038。
- 新增 `utils/viewport-store.ts`：相机三通道——live（每帧，只通知相机图层 transform / 导航器小地图）、renderState（驱动裁剪/LOD/叠加层，发布策略＝位移 ≥120px 或缩放 ≥8% 立即发布、≤100ms 时间上限兜底、40ms 节流下限防抖；进入手势不额外发布，避免 mousedown 瞬间多挂载一圈卡片）、document（手势结束/显式 flush 提交一次）。四个阈值常数可标定。
- MainCanvas 相机图层 `<g>` 的 transform 改为 imperative 独占（React 不再渲染 translate3d）；视口尺寸改为 ResizeObserver 变化时才测量（原 viewportRect useMemo 每帧量布局）。
- 平移：mousedown 记基准相机+起点，逐帧只写瞬时绝对值，mouseup 提交一次；滚轮：事件按 rAF 合并、一手势只量一次 SVG 布局、静默 200ms 提交一次；缩放指数模型 `exp(-Δ·ln(1.05)/100)`——保留"鼠标一格 = ×1.05"的原有总量，触控板连续 delta 变平滑。
- 相机手势期间裁剪加 overscan（屏幕短边 30% 折算世界单位，最小 200），只覆盖 120px 阈值所需的余量（按半视口算会把可视卡片数放大约 5 倍）；背景底板改为世界原点锚定的固定跨度矩形（网格 pattern 是 userSpaceOnUse，底板不需要相机值）。
- `usePresentation.zoomToBounds` 的 600ms 动画（原先每帧写 boards）改走瞬时通道，结束提交一次、被打断先提交当前位置；`getCanvasPoint` 改为缓存 rect + 读 live 相机（ResizeObserver/window resize 失效）。
- 悬浮工具条：交互期间不再做 `getSelectionBounds` + 量布局 + setState；拖动期间冻结、相机手势期间隐藏，手势结束后重算一次。
- 变更追踪改为"忽略相机键"逐项引用比较：只有 panOffset/zoom 变化不算内容变化（未知/新增字段仍按内容对待），于是只挪视角不再标脏、不再触发自动保存，相机仍随下一次保存落盘。
- 切换画板前先 `endInteraction()` 提交旧画板相机（提交走 activeBoardId 闭包，必须在 setActiveBoardId 之前）；`beforeunload` 把未提交的 live 相机补进保存快照。
- 新增检查：`scripts/check-viewport-transient.cjs`（提交语义/节流/相机无关变脏/源码守卫）、`scripts/check-renderer-ssr.cjs`（App 全树 SSR 冒烟 + imperative 契约）；两者并入 `npm run check` 链；`check:interaction-media` 与 benchmark:viewport 未回归。
- 无 store 时逐帧写 boards 的旧路径全部保留（向后兼容 + 便于按文件回滚）；备份在 `.performance-backups/2026-09-23-batch2/`（按源目录结构）。
- 本轮范围只到拖动之外：dragElements 仍逐帧写 elements 并触发 App 重绘，属 P1-B（拖动会话临时态）范围，本批已把共享基建（瞬时通道 + 手势结束单次提交 + imperative 呈现）备好。
- 未验证：实际帧率、GPU 状态、触控板手感、SmartToolbar 隐藏行为、长按平移稳定性、内存。需按实施计划第 4 节在 Electron 真机实测。

## P1-B 拖动会话瞬时通道（拖动与文档状态解耦）

- 根因：元素拖动**逐帧** `setElements` 写 Board（文档状态）→ App 整树重绘 + viewport 索引每帧重建 + 每帧新数组/新元素对象 + defs 每帧重建 + 项目每帧被标脏 + 撤销基线被反复污染。代价与"整个工作区规模"成正比，而拖动其实只改了 N 个元素的两个数字。见 ADR-039。
- 新增 `utils/drag-session-store.ts`：会话 = 拖动 id 集合（**会话内引用稳定**）+ 位移 + 对齐参考线。`begin` 刻意不发布（起点位移为 0，发布只会在 mousedown 白重绘）；`end()` 交出最终值并复位预览；**零位移也交出会话**（点一下落在 Frame 内的元素要走父级解析，这是既有行为）；`cancel()` 供切画板/卸载。
- 新增 `utils/drag-offset.ts`：`applyDragOffset` 是"位移作用到元素上"的唯一实现（path/arrow/line 的位置在 `points` 里，预览与提交分成两份实现会让点集元素在松手瞬间跳位置）；`applyDragPreview` 只替换会话内元素、其余保持原引用 —— 这是 `CanvasElement` 的 memo 只重绘被拖动元素的前提。
- 新增 `utils/drag-commit.ts`：松手时先整体应用位移，再在**位移后的列表**上解析 Frame 父级（拿拖动前的位置判断归属，跨 Frame 拖入会完全失效）；Frame 自身不参与父级解析。整个会话只写一次文档、只产生一条撤销记录，基线是拖动前。
- `MainCanvas`：`presentElements`（全量，group 的包围盒要递归子元素）/`visiblePresentElements`（渲染用）；SelectionHandles、ToolbarOverlay、**SVGDefs** 全部接呈现层；裁剪白名单改为「选中集 ∪ 拖动集」——拖动中新位置只存在于通道里、视口索引还是拖动前的位置，只放行选中集会让被拖 Frame/Group 的后代一出视口就掉块。
- 对齐参考线走会话通道（唯一消费者 `CanvasOverlays` 就在 MainCanvas 内），于是拖动路径上 App **零 setState**；无通道时退化为"内容不变就不 setState"。
- 提交时显式放弃 R14 候选索引（传 `null` 回退全量扫描）：拖动期间位置没写回文档，快照指向拖动前的位置，拿它窄化候选会让跨 Frame 拖入失效。其余旧路径（resize/rotate/lasso 等）仍按原样用保守索引；`check-core-foundations` 对应断言恢复原状并注明归属。
- 顺手修一个真回归：`SVGDefs` 的 clipPath 是**绝对坐标**，拖动圆角图片时裁剪区留在原地会把图片裁没。比较语义从"数组引用变就重绘"改为按圆角图片几何比较（新增可测的 `hasSameRoundedImageGeometry`），顺带让"拖非圆角图片"不再重建 defs 子树。
- 已知降级（有意接受）：拖动中小地图不跟手、Galaxy 星点不跟手、侧栏属性面板的 x/y 不刷新（松手后更新）。手势结束仍只有 mouseup / mouseleave 两条路径（无 pointercancel / Esc），属既有 gap，本批未扩大。
- 新增 `scripts/check-drag-session.cjs`：会话语义 + 预览/提交几何一致性 + defs 比较语义 + **渲染级断言**（SSR 渲染 MainCanvas：位移后的 x/y、圆角 clipPath 跟手、会话结束回到文档位置、远视口外元素"能出现"只可能是拖动白名单生效）+ 源码守卫；并入 `npm run check`。三条关键断言均已反证（改坏实现能让对应断言失败，不是假绿）。
- 备份 `.performance-backups/2026-09-23-batch3/`（按源目录结构）。未验证：拖动手感与帧率、吸附（参考线 + 网格）在会话内的表现、跨 Frame 拖入/拖出真实归属、嵌套 Group、拖动中缩放、原生拖出（Alt+拖拽）、插件卡片。

## P1-D 滚轮缩放手感（倍率 / 平滑追随 / 不再降级 LOD）

- 起因：主人拿 PureRef 对比实测 —— "滚动缩放完全没卡顿、1~2 次就能放大看到整图"，本工具要滚 4~6 次且偶有掉帧。
- 根因是**三个独立问题叠在同一条路径**上，不是一个慢函数：
  1. **幅度**：`WHEEL_ZOOM_EXPONENT_PER_DELTA = ln(1.05)/100` → 鼠标一格（deltaY = 100）只放大 5%（PureRef 约 1.25/格）。"要滚 4~6 次"是算术结果。
  2. **不丝滑**：滚轮是离散事件（间隔还不均匀），把每个事件的结果直接写成相机值 → 视觉是"跳 → 停 → 跳"。
  3. **掉帧**：`handleWheel` 置 `isInteracting = true`，而它是 ADR-036 图片 LOD 的降级开关（`eligibleForHighRes` 要求 `!isInteracting`）→ **滚轮第一下就 release 掉所有高清原图、降级到 1024px 代理**，静默 200ms 后又全部重新请求 + 解码。两轮全量解码就是"掉帧感"的主因。叠加"每跨 8% 缩放重算一次裁剪 + 挂载/卸载卡片"。
- 新增 `utils/wheel-input.ts`：`normalizeWheelDelta`（行/页 deltaMode → 像素；行模式下原实现一格只有 0.7% 缩放，等于滚轮失效）+ `resolveWheelZoomFactor`（指数换算，1.25/格）。抽成纯函数因为这两个数"改错却不报错"，但能被自检直接验证。
- 倍率 1.05 → **1.25/格**；触控板连续小 delta 与整格共用同一曲线（十次 -10 严格等于一次 -100，已断言的恒等式）。
- **平滑追随**：`viewport-store` 新增 `setSmoothTarget` / `getTarget`，滚轮只写目标，live 每帧指数逼近（系数 0.45，相对差 0.4% / 0.4px 收敛）后自动停 rAF；`endInteraction` / `flush` 未收敛时先对齐目标再提交（不能停在半路）；`setTransient` / `syncDocument` 接管时取消追随并对齐目标（否则下次滚轮从过期目标起算）。
- 缩放**基于目标累积**：追随期间 live 只走了一部分，拿它当基准会"越滚越黏"。
- **滚轮不再置 `isInteracting`**：缩放是 GPU 变换，继续用已准入的高清纹理比"降级→解码→恢复→再解码"划算（PureRef 行为），同时消除"越放大越糊、停下才清晰"。工具条冻结条件扩为 `isInteracting || isViewportGesture`（否则滚轮期间每次渲染通道发布都多一次布局读取 + setState）。
- **方向感知的渲染通道发布**：缩小 6%（可见世界范围变大，滞后就露白）/ 放大 30% + 250ms 上限（放大时可见集只会变小，多挂着的卡片无害）→ 连续放大几乎不碰 React 渲染树。
- 滚轮平移（触控板两指）保持 1:1 跟手，不加平滑。
- **锚点稳定性**（本批唯一数学风险）：滚轮目标由"鼠标下世界点不动"定出，pan 是 zoom 的仿射函数；两者用同一系数插值时中间帧世界点与 f 无关，精确不动。写成了自检断言（误差阈 0.01px）。
- 新增 `scripts/check-wheel-zoom.cjs`（输入换算 / 平滑语义 / 锚点不漂移 / 源码守卫）并接入 `npm run check`；`check:viewport-transient` 的缩放发布断言改为方向感知。**上一批写的"工具条冻结条件"守卫拦下了本批改动**，按新语义更新并写明理由。
- 三条关键断言做了反证：pan 系数与 zoom 不同 → 锚点断言失败（世界点漂到 440.45）；`setSmoothTarget` 直接跳变 → 渐进断言失败；滚轮加回 `setIsInteracting` → LOD 守卫失败。
- 备份 `.performance-backups/2026-09-23-batch4/`。未验证：手感与帧率、连续滚动舒适度、触控板表现、跨 LOD 阈值的视觉滞后、以及"不降级 LOD"在大项目中是否反而更重（视口内原图上限仍受 zoom > 1.0 + LRU 50 约束）。

## P1-E 原图准入预算与定向通知（图片数量维度的卡顿）

- 起因：主人反馈**"现在图片一多，滚动就变得很卡"**。这正是上一批留下的悬念 —— P1-D 的"未验证"里就写着"不降级 LOD 在大项目中是否反而更重"。见 ADR-041。
- **先推翻一个错误假设**（值得留档）：第一反应是"相机变换写在 SVG `<g>` 上，每帧要重新光栅化整层内容"。写了对照探针 `scratch/probe-transform-compositing.mjs`，把同一份内容的相机变换分别放在 SVG `<g>` / `<svg>` 自身 CSS transform / 外层 div 上，在 50 / 200 / 400 张图下测帧间隔 —— 三者完全一致（软件光栅化下均 16.7ms、p95 17.8ms、零长帧）。Chromium 会复用 SVG 内容已光栅化的结果，transform 只改变换矩阵。**假设被推翻**，省下了一次大范围架构改造（该改法还会连带破坏全部"用 `svg.getBoundingClientRect()` 换算世界坐标"的路径）。两条测量学教训一并记下：无头浏览器没有 vsync（都测出 6.1ms），窗口移出屏幕则根本不产生帧 —— 这两种环境下的"好成绩"都不构成证据。
- 转到 JS 侧量化（真实 `ImageLRUCache`，`npm run benchmark:lod`）：一次"跨过放大阈值时整屏图片同时准入"，300 张 = **90,000 次 listener 调用、550 次真实状态翻转**；800 张 = **640,000 次、1,550 次**。调用量随图片数**平方**增长。
- 根因一：**准入条件是"缩放级别"的代理** —— `eligibleForHighRes` 只要求 `zoom > 1.0`，于是 zoom 一过 1.0 整屏图片同时 eligible 去抢 50 个配额。这与"这张图需不需要更多像素"无关（300px 的小卡片在 zoom=2 时只需 600px）。
- 根因二：**通知是广播** —— `request()` 每次都向全部订阅者推送 `activeIds` 快照；容量只有 50，图片超过 50 张必然"准入 → 驱逐 → 再准入"，每次 request 都是一轮全体唤醒。
- 放大因素三：**每张图各自一个 180ms 定时器** → 同一批变化落在几百个独立任务里，React 的自动批处理（只合并同任务内更新）失效 → 550 次独立重渲染。这一条解释了为什么"掉了 5 倍性能"会表现为"很卡"而不是"略微掉帧"。
- 修复一（准入语义）：新增 `isFullResolutionWantedAtZoom(width, height, zoom)`，门槛 `FULL_RES_DISPLAY_PX_THRESHOLD = 1024` 与标准代理长边**同源**；保留 `zoom > DETAIL_ZOOM_THRESHOLD` 条件，避免出现"占着配额却渲染不出原图"的错配（`resolveImageLODSource` 仍以 `zoom > 1` 为准）。这条正是实施计划 P2 里写的第一条（"LOD 依据卡片屏幕像素尺寸，而不是仅凭全局 zoom"）。
- 修复二（定向通知）：新增 `subscribeAdmission(id, listener)`，`request` 只通知"新驻留的 id + 被挤掉的 id"，复杂度 O(1)；旧的 `subscribe` 整体广播保留给测试与兼容用，热路径不再走它。
- 修复三（批量提交）：准入先进队列（`scheduleAdmission`），180ms 后由**一个任务**统一 request → 同一批 `setState` 落在同一任务，React 只提交一次。
- 修复四（优先级顺序）：flush 按屏幕最长边**升序**请求。LRU 是"后请求者驻留"，升序才能让最需要清晰度的那批最终留在配额里；否则留下谁纯粹取决于遍历顺序（很可能留下最不需要原图的）。
- 修复五（memo 同源）：`CanvasElement` 图片比较器改调 `isFullResolutionWantedAtZoom`，替换"按 zoom 猜档位"的 `prev.zoom < 0.25 / > 1.0` 三元式。两边不同源就会出现"准入状态变了但卡片不重绘"。
- 修复六（小地图）：不再逐帧订阅 live —— 投影/marker 改用节流渲染态，只有取景框走 imperative 每帧写 4 个属性（有通道时故意不设 `x/y/width/height`，由 rAF 独占，避免 React 覆盖）。旧实现每帧 diff 整棵树（含最多 240 个 marker 矩形），图片一多就成了滚动时的主要 JS 开销。
- 效果：一次批量准入调用量 **90,000 → 550（164×）**，量级 **O(N²) → O(N)**；准入范围在 zoom=2 时从 300 张降到 90 张（`npm run benchmark:lod` 可直接复现）。
- 新增 `scripts/check-image-lod-budget.cjs`（准入按屏幕像素 / 通知精确性 / 复杂度上界 / 旧通道兼容 / 源码守卫）并接入 `npm run check`（现 7 项全绿）。
- 两处关键断言做了**反证**：`request` 改回广播 → "a 准入时只该收到 1 次通知"失败；准入改回"只看缩放级别" → "小卡片放大到 600px 屏幕尺寸时不应该准入原图"失败。确认不是假绿。
- 备份 `.performance-backups/2026-09-23-batch5/`。未验证：真机帧率与手感、数百张同屏时的实际表现、阈值附近（1024 边界）来回缩放是否会引发 LOD 反复切换。已知边界：`zoom ≤ 1` 时即便屏幕像素超预算也不升级原图（与既有 `resolveImageLODSource` 一致，本批刻意不扩大）；配额 50 仍是硬上限。

## P1-F 图片档位的切换时机与冻结（滚动缩放卡顿的真凶）

- 起因：主人复测后反馈**"一个界面里出现几百张图时，滚动缩放还是会出现卡顿、不顺滑"** —— P1-E 修的是准入广播，体感没变。见 ADR-042。
- **先做了硬件对照，直接推翻上一批的测量前提**：上一批的探针跑在 `--disable-gpu`（软件光栅）下，本轮在同一台机器上开真实 GPU（RTX 5080）重测，300 张图、每帧改变换、外加项目同款"40 万 × 40 万 pattern 网格底板"，结果是**光栅 0.16ms/帧、解码 0.3 次/帧，rAF 跑到 166fps** —— 软件光栅下同一场景报的是 10ms/帧、64 次解码/帧。**渲染管线在真实 GPU 下根本不是瓶颈**，上一批"三种挂载方式一致"的结论只在软光栅下成立（结论方向恰好还是对的，但依据不可靠）。若按"重光栅化"假设去把渲染迁到 HTML 层，就是又一次大而无用的改造。
- 测量方法学上又踩了三个坑，一并记下：① 同一配置在不同轮次会从 0ms 飘到 16ms（合成层纹理缓存随内存压力被丢弃）→ **单次结果不可信**，必须交替重复 + 每次独立浏览器进程；② 无头环境 rAF 跑到 166fps，**帧间隔测不出掉帧**；③ 探针脚本 kill 主进程会留下 renderer/gpu 孤儿进程，收尾要 `taskkill /T`。
- 真凶定位到**换档时机与规模**：`resolveImageLODSource` 的档位由**全局缩放级别**决定（`zoom < 0.25` 全部缩略图 / `zoom > 1` 全部原图），而 ADR-040 为了让滚轮缩放"不降级图片"刻意让滚轮期间 `isInteracting` 为假 → **每次跨阈值都是整屏换 href**。实测（真实 GPU，300 张）：整屏换档 = href 赋值 + 等待解码 = **179.3ms**。
- 复刻用户场景量化（隔离页面、交替重复、连续缩放 1.5s + 每 250ms 换一轮档）：**滚动中换档 → 均值 11.0ms、最长帧 78.3ms、43 帧里 13 帧超 32ms；滚动中不换档 → 均值 4.8ms、最长帧 16.9ms、0 长帧**（总耗时都是 474ms，说明差别纯粹在卡顿分布）。
- 顺带发现一个真实 bug：`transient`（未提交手势标记）**只有 `endInteraction()` 会复位，而滚轮缩放没有 mouseup** → 滚过一次之后裁剪 overscan 永久放大（可见集变大 → 更多解码）、工具条位置永久冻结、LOD 档位永远不会解冻。
- 修复一（选档口径）：新增纯函数 `resolveImageLODTier`，按 `屏幕最长边 = 世界最长边 × zoom` 选"够用且最小"的档，取代全局缩放阈值；尺寸未知的调用点回退旧口径（既有契约不回归）。
- 修复二（滞回）：门槛附近留 ±15% 带（升档 > 门槛 ×1.15，降档 < 门槛 ×0.85，无历史时用纯门槛）。自检实测：0.27 → 0.23 微缩跨过 0.25 阈值，需要换档的图片数 **300 → 8**；门槛附近来回滚 8 次，换档 **8 次 → 0 次**。
- 修复三（冻结）：`useImageLOD` 新增 `frozen`，手势中沿用上一次提交的档位、不换 href、也不改准入配额；手势结束后的第一次渲染一次性结算。`CanvasElement` 新增 `lodFrozen`，`MainCanvas` 接 `viewport.transient`。
- 修复四（解冻）：`stepSmooth` 收敛时复位 `transient` 并发布最终渲染态。**不新增提交点** —— `check-wheel-zoom` 的"收敛本身不是提交时机（手势结束才提交）"契约保持不变。
- 修复五（memo 同源）：`CanvasElement` 的 memo 改调 `resolveImageLODTier` 比较理想档位，并新增"冻结开关切换必须重绘"。
- 新增 `scripts/check-lod-tier-stability.cjs`（按像素选档 / 滞回 / 换档规模 / 旧口径兜底 / 冻结与收敛源码守卫）并接入 `npm run check`（现 9 项全绿）。
- 三处**反证**：去掉滞回 → "已是代理时 1100px 仍在升档线内"失败；取消 `frozen` 冻结 → "hook 必须在 frozen 时沿用上一次提交的档位"失败；不复位 `transient` → "平滑追随收敛时必须结束手势"失败。确认不是假绿。
- 备份 `.performance-backups/2026-09-23-batch6/`。未验证：真实 Electron 窗口下的成帧率与手感（无头测不出手感；本批帧数据来自隔离页面，真实项目还有 React 重渲染与 DOM 属性更新成本）；缩小时不再整屏降级到缩略图（按像素判定下大图仍用代理，纹理量比旧口径大，但 GPU 下光栅化不是瓶颈）。

## 2026-09-23 P1-G：回退"手势标记进元素"的回归（恒定 overscan / 无历史选档）

- 起因：主人复测后反馈**"为啥改完这一次滚动缩放反而更卡了，上一次还能流畅滚动缩放，只是图片一多才卡顿"** —— P1-F 引入了回归。见 ADR-043（部分回退 ADR-042）。
- 定位方式：拿改动前的备份做**精确 diff**（`.performance-backups/2026-09-23-batch6/` 对比现状），逐条排查"每次手势 / 每次滚动都要付一遍"的新增成本。
- **主因**：`lodFrozen={viewport.transient}` 进了每个 `CanvasElement` 的 props，memo 里"标记一变就无条件重绘" → 每次滚轮手势（开始 + 收尾各翻转一次）让**当时可见的每个元素**都重绘，与"这张图的档位是否真的变了"无关。量化（`npm run benchmark:churn`，一次"0.25 → 1.6"手势 10 格）：**被迫重绘 440 次 vs 真正需要重绘 15 次（29.3×）**。它发生在滚动开始时（感知最明显的位置），这也解释了"为什么图片少时也变卡"。
- 第二处：档位冻结把位图停在低档 —— 手势开始时 zoom 小 → 档位锁在缩略图/小代理 → 之后放大到 3~5× 仍用同一张位图，又糊又贵（ADR-040 当初特意让滚轮不置 `isInteracting`，正是为了避免"越放大越糊"）。
- 第三处：`imageRendering` 被顺手从 `zoom > 1` 改成按 `tier` —— 放大时只要档位不是 original 就用 `optimizeQuality`，而改动前放大一律 `auto`。
- 第四处：裁剪 overscan 依赖手势标记 → 每滚一次"多挂一圈 → 收尾卸掉 → 下次再挂回来"。量化（1440×900 / 300 张）：平均 **23 张/次**（zoom=0.2 时 84 张）→ 改恒定后抖动归零、稳态 9 张。
- 挖出一个**真 bug（纯函数自检测不到的）**：滞回依赖的"上一次档位"只存在于 hook 的 `useRef`，memo 看不到 → 两边口径不同源，memo 会把滞回窗口内"该升档"的那次重绘**直接拦掉**，href 永远停在滞回前的值（画面糊着不换）。反证实测：两边不同源时，60 张图 × 12 个缩放级别里 **124 处判定不一致**。
- 又证伪了自己上一批的一个前提：ADR-042 断言"滚轮没有 mouseup，所以 transient 永不复位" —— 实际上 `useCanvasInteractions` **本来就有** `WHEEL_GESTURE_IDLE_MS = 200` 的空闲收尾调用 `endInteraction()`；而平滑收敛（约 167ms）比它更早，于是那个"修复"反而把收尾提前、多翻转一次标记。
- 修复：① 删除 `lodFrozen`/`frozen` 整条链路（**手势标记不得进入任何元素的渲染依赖**）；② 删除滞回，`resolveImageLODTier` 保持**无历史状态**（memo 与 hook 各自独立计算必然同源）；③ 裁剪 overscan 改为**恒定**（由 `RENDER_PUBLISH_MOVE_PX × 1.25` 推导，≈150 CSS 像素，取值比原来的"屏幕短边 30%"更小）；④ 恢复 `imageRendering` 原有判据；⑤ 回退 `stepSmooth` 收敛复位（状态收尾只在交互层空闲定时器一处）。**保留 ADR-042 真正有效的部分**：按屏幕像素选档、尺寸未知时回退旧口径。
- 新增 `scripts/benchmark-zoom-churn.cjs`（`npm run benchmark:churn`：换档规模 / 挂载抖动 / 重绘规模三节）。`scripts/check-lod-tier-stability.cjs` 重写为四节 + 五组源码守卫：按像素选档、抖动波及面（旧口径 300 张 → 按像素 20 张）、**memo 与 hook 判定逐点一致（720 个采样点）**、旧口径兜底；守卫禁 `lodFrozen` / `previousTier` / `frozen`，禁 overscan 依赖手势标记，要求滚轮有空闲收尾、收敛不得抢收尾。
- 四处**反证**：加回 `lodFrozen` → "CanvasElement 不得接收手势标记"失败；overscan 依赖手势标记 → 守卫失败；hook 带历史而 memo 不带 → "判定必须逐点一致（实测 124 处不一致）"失败；收敛处复位 `transient` → "不得抢手势收尾"失败。确认不是假绿。
- 备份 `.performance-backups/2026-09-23-batch7/`。未验证：真机手感与帧率（本批量化的是"每次滚动的工作量"，不是帧率）。已知边界：滚动中仍会换档（按像素口径单格平均约 28 张、最坏 65 张），但已从"整屏同步的两次大停顿（单格 240 张 ≈ 130ms）"变成"逐图分散的小批量"；再往下平滑的正确方向是**预解码 / 摊帧**，而不是把手势标记塞给每个元素。

## 2026-09-23 批次 P1-H：选中状态不得影响渲染驻留（真机复测仍卡）

- 起因：主人复测后反馈**"测试了，还是卡顿"**，并指出 P1-G 的结论覆盖不全："9 项全绿 + 换档数量下降只证明部分逻辑通过了测试，不能证明整条缩放链路省下了足够的工作"。见 ADR-044。
- 方法调整：不再做假设式优化。先把"与全量资产数成正比"的路径逐条量化成可复现数字（新增 `npm run benchmark:hotpaths`），再按代价排序修。
- **① 裁剪被全选绕过（主因）**：`hooks/useFileHandlers.ts` 导入即 `setSelectedElementIds(所有新元素)`，而 `MainCanvas` 的裁剪白名单是"选中集 ∪ 拖动集" → 屏幕外选中元素照样挂载。实测（真实 `createViewportIndex`，视口 1440×900）：视口内只需 **8 张**，全选 1000/5000 张后返回 **1000/5000 张**。修复：白名单只放行**拖动集（含后代）/ 文本编辑中 / 裁剪中 / AI 旋转中**——选中是语义状态，不是"必须渲染"的声明（手柄与工具条都从全量 `presentElements` 按几何绘制，不依赖挂载）。保留"导入即全选"的既有交互。
- **② 选区边界是平方级查找**：`getSelectionBounds` 旧口径"每个选中 id 一次 `allElements.find`" → 全选 5000 张 = **12,502,500 次**比较（约 38ms 一次），而它有 **10 个调用点**（SelectionHandles / ToolbarOverlay / useSmartToolbar / 拖动帧 …），相机渲染态一更新就重复付。修复：id → 元素 走索引 + 按 `(allElements, selection)` 引用做 1 槽缓存。实测：**38.5ms → 冷算 4.37ms → 命中缓存 0.029ms**。已核查无"就地改写几何"的代码，缓存前提与 `viewportIndexCache` 一致。
- **③ ADR-043 的"共用选档函数"不完整**：影响输出的判定有三个，`desiredTier` 之外还有 `eligibleForOriginal`（含 `zoom > 1.0`，选档函数里没有）与 `samplingMode`。实测两个 memo 漏判案例：1600×900 图 zoom 0.9→1.1（准入 false→true 但档位没变 → **申请原图的更新被拦掉**）；400×225 图 zoom 0.9→1.1（档位都是 standard 但 `imageRendering` 该从 optimizeQuality 变 auto → **样式停在旧值**）。修复：新增 `resolveImageRenderRequirement` + `isSameImageRenderRequirement`，memo 比整个判定、hook 取同一函数的 `eligibleForOriginal`、`imageRendering` 取 `samplingMode`。
- **④ 滚轮 delta 被覆盖（输入丢失）**：`pendingWheelRef.current = {...}` 整体覆盖，而 `deltaX/deltaY` 是**相对增量**。实测每帧 3 个事件时最终只放大到应有值的 **5.3%（丢失 94.7%）**，且机器越忙丢得越多 —— 直接对应"发黏、不跟手"。修复：增量累加、锚点保留最新；同帧切换操作模式时先结清旧样本。`resolveWheelZoomFactor` 是指数模型、平移是线性模型，故"累加后应用一次"与"逐个应用"**数学等价**（是精确修复，不是手感调参）。
- **等宽导入布局的澄清**：真实导入列宽固定 400（`useFileHandlers.ts`），同尺寸图共用缩略图门槛（`400 × zoom > 256`，即 zoom 0.64）→ "逐图分散换档"的前提不成立，最坏单步 **300 张同时换档**（尺寸分散布局 75 张，4×）。P1-G 台账里"最坏 65 张"是尺寸分散场景下的数字，不作为当前应用上限。但**裁剪修好后换档集合被收敛到视口内**：最坏单步 1000 张 → **32 张（31.3×）**，所以"有界预解码 + 分批换源"的优先级下降。
- 查过但**故意不改**：`CanvasElement` memo 里的 `selectedElementIds.includes` 在"全选 5000 + 挂载 30"下是 0.19ms —— 量级不足（Set 化能提速 100×，但绝对值无意义）。先量化再决定，避免又一次无效改动。
- 新增 `scripts/benchmark-scale-hotpaths.cjs`（`npm run benchmark:hotpaths`，6 节）与 `scripts/check-scale-hotpaths.cjs`（`check:scale-hotpaths`，并入 `npm run check`，现 **10 项**）。同步更新 `check-drag-session.cjs`（白名单断言改为新语义，仍守"拖动集必须在白名单里"）与 `check-image-lod-budget.cjs` / `check-lod-tier-stability.cjs`（同源断言升级为"整个渲染需求"）。
- 四处**反证**：选中集塞回白名单 → 失败；选区边界改回 `find` 口径 → 失败；memo 退回"只比档位" → 失败；滚轮改回覆盖语义 → 失败。确认不是假绿。
- 备份 `.performance-backups/2026-09-23-batch8/`。未验证：真机帧率与手感（本批全部数字来自"调用真实模块"的合成场景，**不是 FPS 测量**）；真实项目还有 React 重渲染与 DOM 属性更新成本。下一步应按调研建议录真实 Performance trace，按"脚本 / React、图片解码 / Raster / Paint、合成 / 内存压力"三类归因后再动手。

## 2026-09-23 P2 真机证伪回退：相机 transform 回内层 `<g>` + 滚轮手势边界（ADR-051）

- 背景：主人真机复测 P2（ADR-049）：**"不仅很闪，滚动和拖动的操作还会突然失效"**。
- 排除：transform 挂 svg 根破坏命中测试（scratch/probe-svg-root-hit-test.html 证否，无头可复现）；坐标换算漂移（diff 复核 12 处全走 getCanvasScreenRect）；prepared 换源空窗（队列语义自洽）。
- 根因 1（闪/消失/失效）：`<svg>` 根被提升为合成层后 bounds 覆盖 overflow:visible 下全部世界内容（巨型单层），缩放时栅格比例失配——旧比例瓦片（发软/闪）、未栅格化瓦片（消失）、整层重栅格期间主线程/合成器饱和（输入停滞）。ADR-049 注释里"稳定后按新比例重栅格"正是它想省的成本。
- 根因 2（拖动失效）：滚轮手势 200ms 空闲定时器会在拖动进行中触发 endWheelGesture，无条件 setIsInteracting(false) 打断鼠标手势；滚轮后 200ms 内开始拖动必踩。
- 改动：①transform 回内层 `<g>`（store imperative / 无 store React，与 P2 前一致），`<svg>` 根禁带相机样式；②保留 512px 中档纹理（`<g>` 每帧重栅格成本压到 1/4，对"图片一多才卡"的正确解）与 getCanvasScreenRect 统一换算；③endWheelGesture 仅在无鼠标手势时复位 isInteracting；④handleMouseDown 入口结清悬着的滚轮手势（取消 rAF/定时器、flush 末样本）；⑤check-camera-compositing 断言翻转为"`<g>` 载体"契约。
- 验证：完整 `npm run check` exit=0。真机验收归主人：滚动缩放闪烁/图片消失/输入失效应消失，流畅度应恢复到"P2 前基线 × 中档纹理收益"。
- 备份：`.performance-backups/2026-09-23-canvas-p2/`（P2 前原文件）。合成层思路封存：除非按视口切多个有界小层，否则"巨型单层+连续缩放"在 Chromium 无出路。

### 为什么是"多卷"而不是"一个文件装完"

单文件卷的写入语义是**重写整篇**。布局是"点一下面板就写一次"的高频写，偏好里装的却是语言、快捷键这类低频小值 —— 混在一个文件里，等于每次展开/收起面板都顺带重写一遍全部偏好（写放大）。切分口径因此是 **写入频率 + 敏感度**，而不是功能归类：

| 卷 | 文件 | 写入频率 | 为什么单独成卷 |
|---|---|---|---|
| `preferences` | `config/preferences.json` | 低 | 语言 / 快捷键等低频小值 |
| `workspace` | `config/workspace.json` | **高**（每次布局交互） | 与低频值分家，避免写放大 |
| `recent-files` | `config/recent-files.json` | 低 | 机器本地路径，**不进预设** |
| `secrets` | `config/secrets.json` | 低 | 敏感度：单独收权限 / 单独加密 |

新卷的成本被压到两处：主进程加一行 `createConfigStore` + 一行 `configStores` 白名单；渲染层加一行 `createConfigVolume(name)`。这决定了"以后再加一个卷"是配置动作而非重构动作。

### 各项实现要点

- **`workspace` 布局持久化**：键清单收在 `plugins/workspace-layout.ts`（`panel.side` / `panel.project` / `panel.viewBookmarks` / `panel.canvasFinder` / `panel.board` / `settings.activeSection`），键名不散落成魔法字符串。读回来的是用户可手改的 JSON，一律当**不可信输入**校验（`isSidePanelState` / `isSettingsSectionId`），半截对象会让面板渲染直接崩。
- **`lastCommitted` 写守卫**（`hooks/useWorkspaceLayout.ts`）：只在"当前值与**上一次真正写进磁盘的值**不同"时才写。这个"上一次落盘值"的基线选得很讲究 —— 两个坑各自能坑死一种做法：
  - 无条件写 → 从没碰过布局的用户也会凭空多一个脏文件，且 **React StrictMode 双跑 effect** 会把默认值写进去；
  - 拿**首帧值**当基线 → 用户把面板改回原值时静默丢写。
  - 取"最后一次落盘值"同时躲开两者。探针第一轮 28/37 里的两处 FAIL 就是这里，`index.tsx` 的 `React.StrictMode` 让 effect 跑两遍、首版一次性 `primed` 标志失效。
- **最近工程**：路径只来自主进程 `dialog`，渲染层只拿到 `projectName`（不越权）。去重在 **Windows 上大小写不敏感**（`C:\a` 与 `c:\A` 是同一个工程）；目录已不存在的条目**置灰而非隐藏** —— 隐藏会让用户以为"记录丢了"，置灰才说明得了"文件没了"。上限 12 条。
- **预设（`main/presetLibrary.cjs` + `builtin/config-manager/presets-section.tsx`）**：
  - 文件名白名单 `/^[A-Za-z0-9][A-Za-z0-9._-]*$/` 在根上消灭路径穿越（首字符不允许 `.`，`..` 与 `../escape` 都进不来）；
  - `PRESET_VOLUMES = ['preferences','workspace']` 是**安全边界**而非功能裁剪：预设是可分享物，带 `secrets` = 泄钥，带 `recent-files` = 换机后满屏死链；
  - `list()` 按 `kind='artflow.preset'` 过滤 —— 否则往 `presets/` 里丢一个任意 JSON，它就会以"预设"身份出现在列表里，等于邀请用户去点一个必然失败的"应用"（探针实测抓到这个）；
  - **导入的生效时机是"落盘 + 需重启"**：语言/外观/皮肤活在模块级单例里，重写文件不会让它们重新求值。与其给一个"改了一半"的迷惑状态，不如说实话 + 提供一键 `restartApp()`。
- **存储管理面板**：逐卷展示字节数 / 条目数 / 来源 / 最后写入时间，外加 `inPreset`（会不会被预设带走）、`encrypted`（是否密文）、`degraded`（是否有解不开的条目）三个徽标。"清空缓存"只动 `userData/temp`，**主进程路径守卫**（`basename === 'temp'` 且位于 `userData` 之下）—— 渲染层传什么路径都越不了界。
- **密钥加固（`main/secretCodec.cjs`）**：加密做成 `createConfigStore` 的 **`valueCodec` 值级钩子**，而不是整文件级。理由具体：存储管理面板要数"键名与字节数"，整文件加密后 `stats()` 就读不出这两项。密文用**自描述前缀** `enc:v1:` —— "是否密文"不依赖任何额外元数据，所以 P1/P2 已经落盘的明文 `secrets.json` **零迁移**就能读；将来换算法只需 `enc:v2:`。
  - **`preserved` 映射**：某个键 `decode` 抛错时，它从 `values` 里移除（渲染层永远看不到密文），但原始文本留在 `preserved` 里，写回时**原样合并**。不做这件事的话，"用户正常保存一次"就会把磁盘上的密钥抹掉 —— 不可逆。
  - **钥匙串不可用时 `encode` 抛错，绝不静默写明文**。"用户以为加密了其实没有"是最坏结果，这是"同步抛错契约"里唯一一处刻意的不对称。
  - `restrictPermissions` → `chmod 0600`：POSIX 上有效；Windows 上近于空操作（那里真正的守卫是 DPAPI），**显式记下来**免得后人以为漏做了。

## R46 完成边界（桌面启动链：无控制台 + 启动动画 + GPU 崩溃回退）

需求原文（用户）：`@"H:/AI-Tools/artflow/启动 Artflow.lnk" 这个启动 需要支持启动动画和 不要显示命令窗口`。

**排查结论先说**：这两项能力代码里**都已经有了**（`branding/splash.html` + `main.cjs` 的 `createSplashWindow()`；`start-artflow.vbs` 无窗口 VBS→node 启动器）。用户看到的是两个**缺陷**，不是一个缺失功能：

| 用户感知 | 真实原因 | 证据 |
|---|---|---|
| "显示命令窗口" | 快捷方式指向 `start-electron.cmd`，其第 54 行 `start "Artflow" ... electron.cmd` 必须由 `cmd /K` 承载，**黑窗整个会话都开着** | 进程导出：`cmd.exe  /K ""node_modules\.bin\electron.cmd""  . ` |
| "没有启动动画" | 本机 GPU 子进程必崩，Electron 在 0.5~3s 内退出，**splash 还没上屏** | `GPU process exits exit_code=-1073741819` ×9 → `FATAL … GPU process isn't usable. Goodbye.` → 退出码 `2147483651` |

### 各项实现要点

- **快捷方式改指向 `.vbs`（等长字节补丁，不重建）**：
  - `.lnk` 的目标存在**四处**（IDList ANSI / IDList UTF-16 / LinkInfo `LocalBasePath` / StringData `RELATIVE_PATH`），四处必须一致，脚本 `scratch/2026-10-09_launch-ux/patch-shortcut.cjs` 逐个替换并回读校验残留数（旧名 0 处 / 新名 ASCII 2 处 + UTF16 1 处），907 字节 → 907 字节。
  - **为什么不等价于重建**：手工拼的最小 MS-SHLLINK（无 `LinkTargetIDList`）被 `Start-Process` 以「没有应用程序与此操作的指定文件有关联」拒绝，而 Explorer 生成的原件能正常启动 —— 重建这条路实测走不通，等长替换则不用改任何长度字段。
  - **文件名长度是承重的**：`start-electron.vbs` 与 `start-electron.cmd` 必须同为 18 字符。原件备份在 `scratch/2026-10-09_launch-ux/启动 Artflow.lnk.orig`。
- **`.cmd` 不再派生第二个控制台**：`start "Artflow" ... electron.cmd` → `call "node_modules\.bin\electron.cmd" .`。`call` 复用当前控制台。（`.cmd` 定位为**调试入口**：看得见 Electron 实时日志。）
- **前端与 Electron 并行拉起**（`scripts/launch-desktop.cjs`）：旧顺序"先等前端就绪再拉窗口"，冷启动那几秒屏幕上什么都没有。现在 Electron 一起来就上 splash，前端就绪与否由 `main.cjs` 的 `waitForDevServer` 在 dev 下自己轮询；启动器侧的就绪等待降级为**纯诊断**（不阻塞窗口，失败只落日志并回收前端进程）。
- **splash 兜底计时器延迟起表**：`armSplashTimeout()` 只在 `loadURL`/`loadFile` **之后**调用。写在 `whenReady` 里的话，dev 冷启动"等前端服务"那段会先把 15s 预算吃光，窗口在渲染层就绪前被强制显示，用户看到一个空壳。
- **GPU 崩溃一次性回退**：`exitCode !== 0` ∧ `runtimeMs < 10s` ∧ `electron.log` 含崩溃原文签名（`GPU process isn't usable` / `gpu_process_host.cc`）→ 用 `--no-sandbox --disable-gpu --in-process-gpu` 重启一次，并把崩溃那次的日志另存 `logs/electron-gpu-crash.log` 作为证据。**不默认关 GPU**：GPU 正常时它换来的是画布拖拽性能，不能因偶发崩溃就写死。
- **Vite 内部 `net use` 的黑窗（`scripts/vite-preload-hide-console.cjs`）**：这是**最后一个残留的命令窗口**，也是排查中最费劲的一环 —— 它不在我们的代码里。
  - 定位过程：先按"进程表 diff"抓到 `cmd.exe:500 parent=<node vite.js> :: /d /s /c "net use"`，`visible=[500]`；再全库搜 `net use` 只命中 `node_modules/vite/dist/node-cjs/publicUtils.cjs` 的 `optimizeSafeRealPathSync()` —— Vite 在 Windows 上**无条件**执行它来探测映射网络盘（因为 Node 的 `realpathSync.native` 在映射盘上会解析成 UNC）。
  - 机制：我们为了消掉 Vite 的控制台用了 `windowsHide: true`（= `CREATE_NO_WINDOW`，**该进程没有控制台**）；Vite 再 exec 出来的 `cmd.exe` 无处继承控制台，Windows 只能**新分配**一个，而新分配的控制台默认**可见**。
  - 修法：`node --require` 预加载一个小 shim，只把命令匹配 `/^\s*net\s+use\b/i` 的那次 `exec` 的 `windowsHide` 强制为 true。`net use` 照常执行、stdout 照常回给 Vite 的解析回调，**判定逻辑一字不改**；本机 `net use` 列表为空、H: 不是网络盘，走的本来就是 `realpathSync.native` 那条分支，行为零变化。修复后实测 `visibleHandle=0`。
- **启动器自身的两处健壮性**：
  - `log()` 改成**先落文件、再尽力回显 stdout，两处各自 try/catch**。双击场景 stdout 随时可能断（EPIPE），日志失败绝不能升级成启动失败。
  - `waitForExit` 必须把结果交给 `resolve`（见下节）。

### 本轮自己踩进去又爬出来的一个坑（必须记）

改 GPU 回退时把 `waitForExit` 写成了 `child.once('exit', settle)` —— `settle` 只是"算出一个对象"，它的返回值被 EventEmitter **丢掉**，Promise 永不 settle。症状极具迷惑性：**日志里"Electron 已退出"整行凭空消失**，窗口早就没了（进程表里 electron 已清零），启动器却一直卡在 `await`，回退逻辑永远不跑；而同一时刻 `waitForServer` 的日志照常输出，"看起来进程还活着"。

排查它花了六轮：先后怀疑过『PowerShell 沙箱回收了进程树』『EPIPE 把启动器写死』『Vite 端口漂移』（甚至观察到 `waitForServer` 耗时从 5.4s 变成 17s，实为冷启动抖动），最后靠"一次启动里把 `waitForServer` 与 `waitForExit` 两条时间线并排看"才定位到是**行内写法的语义错误**，与取消/信号无关。教训是：`once(evt, fn)` 里 `fn` 的返回值语义 = 无，要传结果必须显式 `resolve(...)`。

- `node --check` 通过；`--dry-run` 输出的计划里已含 `--require …vite-preload-hide-console.cjs`。

### 边界 / 后续入口

- **冷启动仍有 ~20s 是 Vite 首次转换模块图的开销**（本机实测 Vite 冷启动 17s）。常驻服务复用后无此代价；服务被外部杀掉时才重现。这一条是本项目既有的体量问题，不是本轮引入。
- 该情形下 `SPLASH_TIMEOUT_MS=15000` 会先到点、把主窗口提前放出来（`渲染层 15000ms 未报 ready，强制显示主窗口`）。要覆盖 20s 就需要把预算提到 ~25~30s，代价是真故障时用户要多盯 10s splash —— **未改**，留待用户定夺。
- **GPU 熔断记忆未做**：目前每次启动都要先赔上一次必然失败的 GPU 尝试（本机 ~0.5~3s）。可加一个跨启动状态（记崩溃时间戳 + 冷却期内直接软件渲染 + 到期再试一次），属"策略缝"。见 ADR-055「未采纳 / 待定」。
- `.lnk` 的四处目标字段目前靠脚本校验，**尚无门禁**把"快捷方式仍指向 `.vbs`"纳入 `npm run check`。
