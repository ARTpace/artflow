## 1. 本批解决什么

前一批已修复全选绕过裁剪、选区查找、memo 漏更新和滚轮增量覆盖。本批保留这些实现，不修改相机节流、overscan、手势收尾、选区和导入逻辑。

仍存在的换档峰值：等宽 400 的横图在相同 zoom 跨越 256px 需求阈值时，多个可见图片会同时改变目标 source。只减少 React 重渲染或合并 setState 不能自动消除图片读取、解码、SVG 绘制和 GPU 上传的工作。

因此在“决定目标 LOD”和“显示该资源”之间增加一个有界准备层：

```text
现有纯函数判断目标 LOD
    ↓
共享准备队列（去重、并发限制、背压）
    ↓
Image 加载 + decode() 完成
    ↓
按 rAF 分批通知组件更新 source
```

新图尚未就绪时保留上一张图；快速改变目标时取消旧订阅并拒绝迟到结果。没有重新加入 lodFrozen、手势结束前冻结清晰度或只有 hook 知道的选档滞回。

## 3. 默认资源策略

| 项目 | 默认值 | 实际含义 |
|---|---:|---|
| 活跃准备任务 | 2 | 队列同时拥有最多 2 个 loader Promise |
| 准备中 + 就绪待消费的不同资源 | 4 | 防止 UI 尚未消费时预解码无限领先 |
| 每次 rAF 通知消费者 | 2 | 包括同 URL 多卡片与缓存命中，不一次通知整屏 |
| 活跃任务估算字节许可 | 64 MiB | thumbnail 估 256²×4；standard 估 1024²×4；original 估 32 MiB |
| 完成后 HTMLImageElement 缓存 | ≤32 MiB，≤24 条 | 以 naturalWidth×naturalHeight×4 计账；超限释放本队列持有的引用 |
| 单次加载/解码超时 | 10 秒 | 超时结算为失败，保留上一张可用图 |

小代理准备优先于原图。当前没有加入“离屏 overscan 与真正屏幕内”的额外优先级，因为组件尚未接入此类身份；不要把现在的 tier 优先级描述成完整视口优先级系统。

### 保证范围

- 以上并发/通知/缓存是应用队列的保证，不是浏览器所有解码线程、实际纹理或整个进程内存的硬上限。
- 原图的 32 MiB 是调度估算，不代表其真实解码大小。未知大图、浏览器内部缓存以及 GPU 占用仍需进一步 profile/预算。
- `decode()` 完成不保证 SVG 随后的绘制完全复用位图，也不保证 GPU 上传零成本。
- rAF 每次最多通知 2 个消费者，不等于在任意浏览器/React 调度下严格保证每个最终显示帧只有 2 次 DOM 更新。
- 待处理项仅持有订阅和 URL 元数据，其数量由当前挂载组件请求决定；重资源就绪集合有背压，并非无条件预加载全项目。

## 4. 交互与故障语义

### 目标与显示

目标档位继续由现有共享纯函数决定；memo 的三个需求字段仍为 desiredTier、eligibleForOriginal、samplingMode。本批只改变图片资源何时显示，不更改这些需求判断。

已显示的标准图在新原图准备中继续显示，不切成空白。缩小需要另一张源时也通过同一队列，不进行同步整屏降档。

### 首次挂载

有 thumbnailHref 时以缩略图开始；没有缩略图时使用原有 href 作为初始标准来源。初始轻量图直接呈现，避免第一帧空白。

因此本批主要治理“换源峰值”，没有把所有首次挂载都改成队列，也不能消除首次大量缩略图或无代理原图的加载峰值。进入/退出极远景星系模式导致的整层挂载仍是独立待测边界。

### 取消与反向缩放

- 目标改变时清理上一请求的消费者租约。
- 同一 URL 多消费者共用 loader；取消一个不会误取消其他消费者。
- 最后消费者取消时 abort；活跃许可直到 Promise settle 才归还，不无限制造悬挂 loader。
- 已取消旧 Entry 的迟到结果只释放资源，不能覆盖后来同 URL 新请求。
- React layout-effect 清理配合局部 live 标记，避免旧结果更新已卸载/新资产组件。
- 当前资源身份使用 elementId + 基础 href；替换资产时立即使用新资产的 fallback，不闪现上一资产。

### 失败

加载、decode 拒绝或超时后继续保留当前图，并标记 error。没有每帧/每秒的自动重试循环；下次目标改变并重新请求时可再尝试。若原有 fallback 自身无效，本批不保证能凭空恢复缺失资产。

### 确定性队列测试

`scripts/check-image-preparation.cjs` 覆盖：
- 300 个同时目标变化请求全部完成，消费者通知分帧；
- 并发限制、估算许可、就绪结果背压、缓存条数/字节上限；
- 同 URL 去重，但消费者通知仍限流；
- 缓存命中不绕过通知队列；
- queued/active/ready 阶段取消；
- 旧请求取消后相同 URL 再请求，旧结果不能破坏新任务；
- 单个消费者报错不阻断队列；
- 解码失败、timeout、abort、事件/定时器清理；

- 等待期间保留旧图；
- 快速目标反转与旧结果迟到；
- 更换资产身份不显示旧资产；
- 组件卸载、失败保留旧图；
- 真正的浏览器 Image.decode()、无效图片与预取消。

48 张合成等宽图片从 zoom 0.3 到 0.7：
- 旧组件同步切换 48 张；
- 新组件同步切换 0 张，保留缩略图；
- 一次测试的逐帧完成数为 0、0、2、4……48；

## 7. 诊断方式

DOM 上新增：
- `data-lod-tier`：当前实际显示档位；
- `data-image-target-tier`：当前目标档位；
- `data-image-load-state`：ready / pending / error。

Vite 开发模式可在应用自身 DevTools 控制台使用：

```js
const m = await import('/utils/image-preparation-queue.ts');
m.getImagePreparationQueue().getStats();
```

该 import 仅适用于开发服务器，不适用于打包后的模块路径。不要在运行中的应用调用 dispose() 作为普通诊断动作；它会永久关闭该实例。

stats 仅含计数，不包含媒体 URL 或文件内容。持续很多秒 pending 且 active 不动时，检查资源请求/解码与超时；error 增长时应检查对应协议或图片源，不应直接放大并发掩盖问题。
