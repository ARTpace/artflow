# 画布渲染性能优化 P2 实施记录（2026-09-23）

## 问题

主人实测最新版：**一屏几百张高清图时，拖动与滚轮缩放仍卡**；指出 P1（相机瞬时通道 / LOD / 准入预算）没有根本解决。

## 根因（本次诊断）

1. **相机 transform 挂在 SVG 内层 `<g>`**：Chromium 不为 SVG 内部元素建独立合成层，`<g>` 的 transform 每变一次就重栅格化整片 SVG 内容（几百张已解码图），pan/zoom 每帧成本随图片数增长；`<g>` 上的 `will-change:transform` 对 SVG 内部元素被 Chromium 显式拒绝（40753139）。ADR-041 曾用无头探针"推翻"此假设，但无头窗口不产生真实帧，属测量环境失效（该 ADR 自己记录了此教训）。
2. **标准档固定 1024px**：密集多卡时每格屏幕仅 150~500px 却持 1024px 纹理，300 张 ≈ 0.9GB 显存，合成带宽与换档重栅格都按此付费。

## 验证状态

- 远程 `npm run check`（typecheck + build + 全部检查含 2 个新增）：**以部署后结果为准**（本记录写完即部署验证）。
- **真机帧率未验证**（本环境无法产生真实帧）。主人验收路径：
  1. 直接实测：几百张高清图一屏，拖动 / 滚轮缩放；
  2. `HEAD=1 node scratch/probe-transform-compositing.mjs`（改动前后各一次，对比 `<g>` 与 `<svg>` 挂载的帧间隔）。
- 若真机仍卡：按 ADR-049 Consequences 的下一步清单（DPR 像素预算、准入 zoom 门、RasterScale 提示）继续，不回头怀疑本批接线。
