# Artflow 画布交互性能优化实施计划

日期：2026-09-23  
范围：H:\AI-Tools\artflow  
定位：在已有《无限画布与海量资产架构优化方案》及 R11–R36 优化之上，补充实际交互热路径治理；不替换既有架构文档。

## 1. 目标与边界

目标：资产总量增长时，单张/多张卡片拖动仍保持可用；让每帧工作尽量与移动对象、可见内容成正比，而非与整个项目资产量成正比。

不承诺未经测量的 60 FPS。不改变原始媒体、不迁移项目文件格式、不删除资产、不更改插件权限。按批交付，每批有检查与回滚点。

当前结论来自源码审查，不是用户场景的运行时 profile。既有 rAF、空间索引、memo、操作历史和图片代理继续保留，不能用注释中的“GPU 加速/60fps”作为性能证明。

## 2. 已确认的代码路径

| 路径 | 现状 | 风险 |
|---|---|---|
| useCanvasInteractions.ts 拖动分支 | 每帧 elements.map 并写 boards | 顶层 React、派生数据、索引一起更新 |
| viewport-index.ts update | 增量改格子前仍逐项比较元素 | 每帧 O(N) 验证 |
| App.tsx workspaceMetrics | boards 变化时扫描各画板资产 | 位置变化触发无关统计 |
| imageProxy.ts | 交互判断优先于远景缩略图 | 远景拖动反而升级 1024px 图 |
| CanvasElement memo | 交互中不检查图片 zoom 层级变化 | 可能冻结错误的图片层级 |
| 原图 LRU | 50 个元素 ID 的准入名单 | 不是实际纹理所有权，也不是字节预算 |
| video/audio | 可见媒体挂载真实播放器 | 不必要预加载和复杂 UI 成本 |
| main.cjs | 环境变量可关闭硬件加速 | 必须确认实际运行状态，不能推断已关闭 |

## 3. 分阶段实施

### P0：基线与保护
- 已完成修改前 npm run check：类型检查、生产构建、foundation checks 通过。
- 项目目录不是 Git 工作区；修改前将涉及文件保存在 `.performance-backups/2026-09-23-batch1/`。
- 待完成实际 Electron 场景 profile：记录 GPU feature status、分辨率/DPR、资产数量、可见数量、图片尺寸、播放数量、内存和帧耗时。
- 比较生产构建与开发模式，避免将 React 开发检查、HMR 等误认为生产性能。

### P1-A：低风险媒体交互策略（本批）
1. 远景缩略图优先于交互降级：zoom < 0.25 且有缩略图时，拖动继续用缩略图。
2. 交互中跨越 LOD 阈值也更新图片组件，避免 memo 忽略变化。
3. 原图准入延迟 180ms；新交互、组件卸载或层级改变时取消定时器。该延迟用于抑制连续操作间反复升级，不是全局解码并发队列。
4. 视频显式 `preload="none"`；音频从 metadata 改为 none。保留原生控制和播放行为。
5. 新增 `scripts/check-interaction-media.cjs`，覆盖 LOD 边界、缺失代理图、交互及原图准入组合、音频 SSR 与源码保护检查。

限制与体验变化：
- preload 是浏览器提示，不是绝对零 I/O 保证；本批仍挂载真实媒体元素，尚未实现封面/按需播放器池。
- 无已保存 duration 的音频，在用户播放前可能不显示正确总时长。
- 没有 poster 的视频可能先显示空白原生播放器；封面接入属于 P1-C。
- 未修改媒体源，不暂停已有播放，不修改持久化格式。
- 仍未消除每帧全局状态更新，不能据此宣称已解决大量资产拖动问题。

### P1-B'：相机瞬时通道（本批，已实施）
定位：先解决"拖动之外"的两件事——**滚动平移**与**缩放**（含帧间动画），并把 P1-B 需要的基建做出来。决策记录见 `docs/adr/ADR-038-相机瞬时通道与文档状态解耦边界.md`。

1. `utils/viewport-store.ts`：相机走三条通道——live（每帧，只通知 transform/小地图）、renderState（手势中"位移 ≥120px 或缩放 ≥8% 立即发布 / ≤100ms 兜底 / 40ms 下限"，驱动裁剪/LOD/叠加层；进入手势不额外发布）、document（手势结束提交一次）。
2. `MainCanvas` 相机图层 transform 改为 imperative 独占（React 不再渲染 `translate3d`）；视口尺寸改为只在 ResizeObserver 变化时测量。
3. 平移：mousedown 记基准、逐帧写瞬时值、mouseup 提交一次；滚轮：事件按 rAF 合并、一个手势只量一次布局、静默 200ms 提交一次；缩放指数模型 `exp(-Δ·ln(1.05)/100)` 保持"一格 = 1.05"的原有总量并让触控板连续。
   > 注：本段的"一格 = 1.05"与"无平滑"已被 P1-D 修正（1.25/格 + 平滑追随），见下文 P1-D。
4. 裁剪在相机手势期间加 overscan（屏幕短边 30% 折算世界单位，最小 200），兜住 120px 的发布滞后。
5. 背景底板改为世界原点锚定的固定跨度矩形（不再依赖相机值）。
6. `usePresentation.zoomToBounds` 的 600ms 动画走瞬时通道，结束提交一次。
7. `getCanvasPoint` 改为缓存 rect + 读 live 相机；悬浮工具条在交互期间不做布局计算。
8. 只挪视角不再把项目标记为未保存（相机变化不算内容变化），相机随下一次保存落盘。
9. 切画板前提交旧画板相机；`beforeunload` 把未提交的 live 相机补进保存快照。

体验变化（需实测确认可接受）：
- 相机手势期间悬浮工具条（SmartToolbar）隐藏，结束时回到选区旁。
- 手势中 LOD/叠加层按"位移 ≥120px / 缩放 ≥8% / 100ms"跟随，快速跨阈值缩放时图片层级切换可能晚一拍。
- 只挪视角不触发自动保存与"未保存"标记。
- 导航器小地图改为跟随 live 相机。
- 新增检查是逻辑/SSR/源码保护检查，不替代浏览器帧率、触控板手感与 GPU 状态验证。

### P1-B：拖动临时态与文档状态解耦（本批，已实施）
设计：pointer/rAF → 交互控制器临时位移 → 被拖动对象显示变换；mouseup → 一次文档坐标提交、parent 计算、空间索引更新与撤销记录。决策记录见 `docs/adr/ADR-039-拖动会话瞬时通道与提交边界.md`。

> 注：P1-B 的共享基建（相机/手势瞬时通道、手势结束单次提交、imperative 呈现层）已由 P1-B' 落地；P1-B 只剩"拖动对象"这一半。

本批实际做法：
1. `utils/drag-session-store.ts`：会话三要素 = 拖动 id 集合（会话内引用稳定）、位移、对齐参考线。`begin` 刻意不发布（起点位移为 0，发布只会在 mousedown 白重绘一次）；`end` 返回最终会话并复位预览；零位移同样交出会话（点一下落在 Frame 内也要归属）；`cancel` 用于切画板/卸载。
2. `utils/drag-offset.ts`：`applyDragOffset` 是"一次位移作用到元素上"的唯一实现（`path`/`arrow`/`line` 的位置在 `points` 里），`applyDragPreview` 只替换会话内元素、其余保持原引用（`CanvasElement` 的 memo 靠引用相等）。
3. `utils/drag-commit.ts`：松手时先整体应用位移，再在**位移后的列表**上解析 Frame 父级；Frame 自身不参与父级解析。整个会话只产生一条撤销记录，基线是拖动前状态。
4. `MainCanvas` 呈现层：`presentElements`（全量，供 group 递归求包围盒）/`visiblePresentElements`（渲染用）；`SelectionHandles`、`ToolbarOverlay`、`SVGDefs` 全部接呈现层。裁剪白名单 = 选中集 ∪ 拖动集。
5. 对齐参考线走会话通道（去掉热路径上的每帧 setState）；无通道时退化为"内容不变就不 setState"。
6. `SVGDefs` 的 memo 比较改为按"圆角图片几何"（clipPath 是绝对坐标，拖动圆角图片时不更新会把图片裁没）。
7. 无 `dragSessionStore` 时旧的逐帧 `setElements` 路径原样保留。

实施顺序：
1. 建立明确 DragSession：起始元素、ID 集合、原始 bounds、最终位移、取消状态。
2. 先优化普通平移；缩放/旋转/裁剪保持原路径，避免把所有手势一起重构。
3. 保留现有吸附快照；计算移动 bounds 时叠加临时位移。
4. 用独立交互层或元素外层 transform 呈现，不改变卡片内部媒体布局；处理选区/工具条同步。
5. 拖动时选中对象必须保持可见，防止基于旧文档坐标的裁剪卸载。
6. mouseup 先 flush 最后一个 pointer，再提交；pointer cancel、Esc、切换画板和卸载有明确结束规则。
7. 自动保存只读取已提交文档；若拖动途中触发保存，不能将临时坐标错误标记为已保存。

回归矩阵：单选、多选、Group、嵌套 Group、Frame、Path/Arrow、吸附、跨 Frame 拖入拖出、撤销重做、画布边缘、缩放后拖动、最后一个 pointer 样本、切换画板、原生拖出、插件卡片。

验收：常规拖动的每帧不再产生 boards 更新和整表 map；mouseup 只有一条历史记录。测试前不得删除旧回退路径。

### P1-D：滚轮缩放手感与方向感知发布（本批，已实施）

定位：P1-B' 把滚轮从"逐事件写文档"改成"瞬时通道 + 手势结束提交"之后，**幅度与丝滑度**离 PureRef 仍有明显差距（主人实测：要滚 4~6 格才有 PureRef 一两格的观感，且偶有掉帧）。本批只动滚轮这一条路径。决策记录见 `docs/adr/ADR-040-滚轮缩放手感与发布策略边界.md`。

诊断：三个独立问题叠在同一处。

1. **幅度**：`WHEEL_ZOOM_EXPONENT_PER_DELTA = ln(1.05)/100` → 鼠标一格（deltaY = 100）只放大 5%，从适应全图到看清细节要 4~6 格。
2. **不丝滑**：滚轮事件直接改写相机值。Windows 上滚轮是离散事件（一格一个），视觉上是"跳 → 停 → 跳"，不是连续运动；事件间隔不均时尤其明显。
3. **掉帧**：`handleWheel` 会置 `isInteracting = true`，而它是图片 LOD 的降级开关（`useImageLOD` 的 `eligibleForHighRes` 要求 `!isInteracting`）—— 于是**滚轮第一下就把所有高清原图 release 掉、降级到 1024px 代理**，滚轮停 200ms 后又全部重新请求 + 解码。一进一出两轮全量解码就是"掉帧感"的直接来源；再叠加"每跨 8% 缩放就重算一次裁剪 + 挂载/卸载卡片"。

本批做法：

1. 新增 `utils/wheel-input.ts`：`normalizeWheelDelta`（行/页模式折算成像素）+ `resolveWheelZoomFactor`（指数换算）。抽成纯函数是因为这两个数"改错却不报错"，但能被自检直接验证。
2. 倍率 1.05 → **1.25/格**（对齐 PureRef 量级）；触控板的连续小 delta 与整格共用同一条指数曲线（十次 -10 严格等价于一次 -100）。
3. **平滑追随**（`viewport-store.setSmoothTarget`）：滚轮只写"目标相机"，live 每帧向目标指数逼近（系数 0.45，相对差 0.4% / 0.4px 收敛），收敛后自动停 rAF。`endInteraction` 若未收敛则先对齐目标再提交（提交的必须是用户滚到的值，不能停在半路）；`setTransient` 接管时取消追随并对齐目标（否则下一次滚轮从过期目标起算）。
4. 缩放**基于目标累积**（`getTarget()`）而不是 live：追随期间 live 只走了一部分，拿它当基准会让"滚得越快、每格增量越小"。
5. **滚轮不再置 `isInteracting`**：缩放本身是 GPU 变换，继续用已准入的高清纹理更划算（PureRef 就是这个行为），同时消除"越放大越糊、停下才清晰"。工具条冻结条件相应改为 `isInteracting || isViewportGesture`，否则滚轮期间每次渲染通道发布都要读一次布局 + setState。
6. **方向感知的渲染通道发布**：缩小用敏感阈值（6% —— 可见世界范围在变大，滞后就在边缘露白），放大用迟钝阈值（30%）+ 更长的时间上限（250ms）。放大时可见集只会变小（多挂着的卡片无害），于是"连续放大"这条最常见的手势几乎不碰 React 渲染树。
7. 滚轮平移（触控板两指滑动）保持 1:1 跟手，不加平滑（否则有拖尾感）。

已知取舍（需实测确认可接受）：

- 放大方向的 LOD / 裁剪跟随按"30% / 250ms"滞后，手势结束立即补齐；跨 1.0 精度阈值后图片可能晚一拍变清晰。
- 平滑追随把"立刻到位"变成"约 0.1~0.15 秒内到位"，快速连滚时表现为一阶低通。

### P1-E：原图准入预算与定向通知（本批，已实施）

定位：P1-D 把滚轮本身做顺之后，主人反馈**"图片一多，滚动就变得很卡"**。本批只动两条"代价与图片数量成正比"的路径：原图准入（LRU）与小地图。决策记录见 `docs/adr/ADR-041-原图准入预算与定向通知边界.md`。

排查先排除了一个很诱人的错误假设：

- 起初怀疑"相机变换写在 SVG `<g>` 上，每帧都要重新光栅化整层内容"（听上去正好解释"图片越多越卡"）。于是写了对照探针 `scratch/probe-transform-compositing.mjs`：同一份内容、同样逐帧只改相机变换，把变换分别放在 **SVG `<g>` / `<svg>` 自身 CSS transform / 外层 div** 上，在 50 / 200 / 400 张图下分别测帧间隔。软件光栅化（无 GPU）下三者都是 **16.7ms，p95 17.8ms，零长帧**，没有任何差异 —— Chromium 会复用已光栅化的 SVG 内容，transform 变化只更新变换矩阵。**假设被推翻**，省下了一次大范围架构改造（那个改法还会连带破坏所有"用 `svg.getBoundingClientRect()` 换算世界坐标"的路径）。
- 转到 JS 侧量化：用真实 `ImageLRUCache` 复刻"跨过放大阈值时整屏图片同时准入"，300 张图 = **90,000 次 listener 调用、550 次真实状态翻转（≈ 550 次 React 重渲染）**，且随图片数**平方**增长（800 张 → 640,000 次）。量级与"很卡"的体感吻合。

根因两条：

1. **准入条件是"缩放级别"的代理**：`eligibleForHighRes = !isInteracting && zoom > 1.0 && originalHref` —— zoom 一过 1.0，整屏图片同时 eligible。这与"这一张到底需不需要更多像素"无关：一张 300px 的小卡片在 zoom = 2 时也只需要 600px。
2. **通知是广播**：`request()` 每次向**全部**订阅者推送 `activeIds`，而容量只有 50 —— 图片超过 50 张必然"准入 → 驱逐 → 再准入"。叠加"每张图各自一个 180ms 定时器"，同一批变化落在几百个独立任务里，React 的自动批处理（只合并同任务内的更新）完全帮不上忙，于是变成几百次独立重渲染。

本批做法：

1. 准入改按**屏幕像素需求**：`isFullResolutionWantedAtZoom = zoom > DETAIL_ZOOM_THRESHOLD && max(w, h) × zoom > 1024`。门槛 1024 与标准代理长边**同源**（代理本来就只有 1024px，屏幕用不到更多像素时换原图是纯浪费）。两个条件都保留：只按像素放宽会出现"占着配额却渲染不出原图"（`resolveImageLODSource` 仍以 `zoom > 1` 为准）。
2. 新增**定向订阅** `subscribeAdmission(id, listener)`：`request` 只通知"新驻留的 id + 被挤掉的 id"，复杂度 O(1)。旧的 `subscribe` 整体广播保留（测试与兼容用），但热路径不再走它。
3. 新增**准入队列 + 一次 flush**：同一批 `setState` 落在同一个任务里，React 只提交一次。
4. flush 按优先级（屏幕最长边）**升序**请求：LRU 是"后请求者驻留"，升序才能让最需要清晰度的那批最终留在配额里（否则留下谁纯粹取决于遍历顺序）。
5. `CanvasElement` 的 memo 重绘条件与准入判定**同源**（都调 `isFullResolutionWantedAtZoom`），避免"准入状态变了但卡片不重绘"的错位。
6. **小地图不再逐帧订阅 live**：投影 / marker 改用节流后的渲染态，只有**取景框**走 imperative（每帧写 4 个属性）。旧实现每帧 diff 整棵树（含最多 240 个 marker 矩形），图片一多就成了滚动时的主要 JS 开销。

效果（`npm run benchmark:lod`，300 张图一次批量准入）：调用量 **90,000 → 550（164×）**，量级 **O(N²) → O(N)**；准入范围在 zoom = 2 时从 300 张降到 90 张。

已知边界：

- 准入仍保留 `zoom > 1` 这道门（与 `resolveImageLODSource` 保持一致），因此"世界尺寸很大但 zoom ≤ 1"的图片仍不会用原图 —— 与改动前相同，本批未扩大范围。
- 原图配额 50 仍是硬上限，超出部分用 1024px 代理（大图放大时略糊）。这是资源约束，不是回归。

### P1-F：图片档位的切换时机与冻结（已实施，其中"滞回 / 冻结 / 收敛复位"已被 P1-G 回退）

定位：P1-E 修掉"准入广播 O(N²)"之后，主人复测仍是**"几百张图时滚动缩放卡、不顺滑"**。本批改用真实 GPU 重做测量，结论与 P1-E 完全不同——**卡顿来自换档的时机与规模，不是画得慢**。决策记录见 `docs/adr/ADR-042-图片档位切换时机与冻结边界.md`。

先把上一批的测量前提补上：P1-E 的探针跑在 `--disable-gpu`（软件光栅）下。本轮在真实 GPU（RTX 5080）下重测同一场景（300 张图 + 每帧改变换 + 项目同款巨型网格底板），**光栅 0.16ms/帧、解码 0.3 次/帧、rAF 166fps**；而软件光栅下同一场景是 10ms/帧、64 次解码/帧。**渲染管线在真实 GPU 下不是瓶颈**，把渲染迁到 HTML 层这类改造是白做。

真凶：档位由**全局缩放级别**决定（`zoom < 0.25` 全部缩略图 / `zoom > 1` 全部原图），配合 ADR-040"滚轮期间不降级图片"（滚轮时 `isInteracting` 为假），导致**每次跨阈值都是整屏换 href**。实测整屏换档 = href 赋值 + 等待解码 = **179.3ms / 300 张**。

复刻用户场景（连续缩放 1.5s，每 250ms 换一轮档，隔离页面 + 交替重复）：

| | 均值帧 | 最长帧 | 超 32ms 帧数 |
|---|---|---|---|
| 滚动中换档 | 11.0 ms | 78.3 ms | 13 / 43 |
| 滚动中不换档 | 4.8 ms | 16.9 ms | 0 / 43 |

本批做法：

1. 选档改按**屏幕像素需求**（`resolveImageLODTier`：`世界最长边 × zoom` 对比 256 / 1024 两个门槛），取代全局缩放阈值；尺寸未知的调用点回退旧口径。**（保留——这是本批唯一真正有效的部分）**
2. ~~门槛附近加 ±15% 滞回带~~ → **已回退（P1-G）**：滞回需要"上一次的档位"这份历史，而它只有 hook 看得到、memo 看不到 → 两边口径不同源，memo 会把滞回窗口内"该升档"的那次重绘拦掉（反证实测 124/720 处不一致）。
3. ~~视口手势中冻结档位~~ → **已回退（P1-G）**：`lodFrozen={viewport.transient}` 让每次手势翻转都迫使**当次可见的每个元素**重绘（量化 440 次 vs 实际需要 15 次），且冻结让位图停在低档（放大时又糊又贵）。
4. ~~平滑追随收敛即结束手势~~ → **已回退（P1-G）**：前提被证伪 —— 滚轮**本来就有**收尾机制（`WHEEL_GESTURE_IDLE_MS = 200` 的空闲定时器调用 `endInteraction()`）；收敛（约 167ms）比它更早，于是等于把收尾提前、多翻转一次标记。
5. `CanvasElement` 的 memo 与档位判定**同源**（共用纯函数）。**（保留，P1-G 强化为"逐点一致"断言）**

效果（自检可复现）：跨 0.25 阈值微缩时需换档的图片数 **300 → 8**；门槛附近来回滚 8 次换档 **8 → 0**；模拟用户场景的最长帧 **78.3ms → 16.9ms**（0 长帧）。

已知边界：手势结束后的那一次结算仍是一次整屏换档（约 179ms 的解码等待，发生在静止时）；缩小时不再整屏降级到缩略图（大图按像素判定仍用代理，纹理量比旧口径大，但 GPU 下光栅化不是瓶颈）。

### P1-G：回退"手势标记进元素"的回归（本批，已实施）

定位：主人复测后反馈**"为啥改完这一次滚动缩放反而更卡了，上一次还能流畅滚动缩放，只是图片一多才卡顿"**。用改动前后的备份做精确 diff，再配合三个量化口径，找到四处"每次手势 / 每次滚动都要付一遍"的新增成本。决策记录见 `docs/adr/ADR-043-视口手势标记不得进入元素渲染依赖.md`。

| 新增成本 | 量化（`npm run benchmark:churn`） | 本批处理 |
|---|---|---|
| 手势标记进元素 props：每次手势翻转（开始 + 收尾）迫使当时可见的**每个**元素重绘 | 一次"0.25 → 1.6"手势：**被迫重绘 440 次 vs 实际需要 15 次（29.3×）** | 删除 `lodFrozen` 整条链路 |
| 档位冻结让位图停在低档：手势开始时 zoom 小 → 档位锁在缩略图/小代理，之后放大到 3~5× 仍用同一张位图 | 又糊又贵，且与 ADR-040"滚轮不降级图片"的初衷冲突 | 删除 `frozen` |
| `imageRendering` 从按 `zoom` 改成按 `tier` | 放大时只要档位不是 original 就用 `optimizeQuality`（改动前放大一律 `auto`） | 恢复原判据 |
| 裁剪 overscan 依赖手势标记 | 每滚一次多挂 / 卸 **23 张**（zoom=0.2 时 84 张） | 改恒定（`RENDER_PUBLISH_MOVE_PX × 1.25 / zoom`，抖动归零、稳态 9 张） |

另外两处是上一批自己引入的问题：① 滞回与 memo 不同源 → 升档被 memo 拦死（反证 124/720 处判定不一致）；② "滚轮没有 mouseup，所以 transient 永不复位"这个前提**被证伪** —— 滚轮本就有 `WHEEL_GESTURE_IDLE_MS = 200` 的空闲收尾，收敛复位（约 167ms）反而更早，等于多翻转一次标记。

本批之后滚动路径上的工作量是**净减少**（连 overscan 的取值都比原来的"屏幕短边 30%"更小），并新增五组源码守卫防止再犯：禁 `lodFrozen` / `previousTier` / `frozen`、禁 overscan 依赖手势标记、收敛不得抢收尾。

已知边界：滚动中仍会换档（按像素口径单格平均约 28 张、最坏 65 张 —— 注意这是**尺寸分散**场景下的数字，等宽导入布局下最坏是整批，见 P1-H），但已从"整屏同步的两次大停顿（单格 240 张 ≈ 130ms）"变成"逐图分散的小批量"。再往下平滑的正确方向是**预解码 / 摊帧**，而不是把手势标记塞给每个元素。

### P1-H：选中状态不得影响渲染驻留（本批，已实施）

起因：主人复测仍反馈**"还是卡顿"**，并指出 P1-G 的结论覆盖不全 —— "9 项全绿 + 换档数量下降只证明部分逻辑通过了测试，不能证明整条缩放链路省下了足够的工作"。

做法改变：不做假设式优化。先把"与全量资产数成正比"的路径逐条量化（`npm run benchmark:hotpaths`，调用真实模块），再按代价排序修。决策记录见 `docs/adr/ADR-044-选中状态不得影响渲染驻留.md`。

| 路径 | 量化 | 本批处理 |
|---|---|---|
| 裁剪白名单 = 选中集 ∪ 拖动集，而导入即全选 | 视口内只需 **8 张**；全选 1000/5000 张 → 返回 **1000/5000 张** | 白名单只放行拖动 / 编辑 / 裁剪 / 旋转 |
| `getSelectionBounds` 每 id 一次 `allElements.find`（10 个调用点） | 全选 5000 张 = **12,502,500 次**比较（38ms/次） | 索引 + 引用缓存：**38.5ms → 4.37ms → 0.029ms** |
| memo 只比"选档"，漏 `eligibleForOriginal` / `samplingMode` | 两个真实漏判案例（该申请原图 / 该换采样被拦掉） | 抽 `resolveImageRenderRequirement` 作单一真相源 |
| 滚轮 `pendingWheelRef` 整体覆盖相对增量 | 每帧 3 个事件时输入丢失 **94.7%** | 增量累加 + 模式切换先结清 |

等宽导入布局（列宽固定 400）澄清：同尺寸图共用门槛（zoom 0.64），最坏单步 **300 张同时换档**（P1-G 台账的"最坏 65 张"是尺寸分散场景的数字）。但裁剪修好后换档集合被收敛到视口内：最坏单步 1000 张 → **32 张（31.3×）**。

查过但故意不改：memo 里的 `selectedElementIds.includes` 在"全选 5000 + 挂载 30"下是 0.19ms，量级不足。

### P1-C：播放器按需激活
- 视频非激活态显示缓存封面；音频显示静态封面/预计算波形。
- 播放操作才挂载或激活播放器；活动播放器数量有限且策略明确。
- 离屏播放是否继续由产品策略决定，不能粗暴卸载导致背景音乐意外中断。
- 动态播放 UI 与卡片位置层拆分；drag 不使音频控制面板重新生成整棵子树。

## 4. 性能验证方法

同一机器、同一窗口尺寸和同一场景分别测试修改前后；每项预热后重复 3 次，拖动持续 10 秒。

场景（P1-H 补充两条，上一轮的基准缺了它们）：
- 100 / 1,000 / 5,000 张普通图片，固定可见数量；
- 相同总量、不同可见密度；
- **等宽导入布局**（真实导入把列宽固定为 400，同尺寸图会共用 LOD 门槛），而不是只用尺寸高度分散的素材；
- **无选择 / 单选 / 全选**三种选区状态，而不是只测空选区；
- 图片 + 视频 + 音频混合，分别无播放/单个播放；
- 高分辨率原图、zoom 0.1 / 0.5 / 2；
- 多选、Group 和 Frame；
- 导入进行中与导入结束后分开记录。

记录：frame time p50/p95、超过 50ms 的长任务、React commit 次数、脚本/布局/绘制耗时、JS heap、进程内存、实际媒体请求数量。60Hz 屏幕以每帧约 16.7ms 为目标预算，不将某个纯算法 benchmark 当作整机 FPS。

**归因分流（录完 trace 后按此判断下一步，别凭印象挑）**：
- 卡在 Scripting / React → 继续减少计算与提交（选区、派生数据、索引）；
- 卡在 Image Decode / Raster / Paint → 处理资源队列与绘制（有界预解码、分批换源、合成层）；
- 卡在 Compositing 或内存压力 → 检查图层数量、滤镜、播放器与资源预算。

开发者工具操作：Performance 录制 → 连续拖动 10 秒 → 停止；观察 Main、Frames、Layout/Paint 与 React 提交。用 Network 检查空闲播放器加载；在渲染器选择一个 `[data-lod-tier]` 图片，验证远景拖动前后仍是 thumbnail。
